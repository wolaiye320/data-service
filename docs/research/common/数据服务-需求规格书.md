# 数据服务需求规格书

## 1. 文档目的

本文档为数据服务项目唯一正式需求文档，用于定义可实施、可验证、可追踪的需求规格，明确系统目标、范围、业务场景、功能需求、非功能需求、边界与验收标准，作为后续架构设计、详细设计、开发、测试和验收的依据。

本文档关注“系统应做什么”和“应达到什么程度”，不展开具体技术选型、实现细节和代码级设计；相关内容由后续架构设计文档和详细设计文档承接。

## 2. 背景与目标

当前应用系统需要从不同类型数据库获取数据，并以统一 API 形式对外提供查询能力。现有数据分散在不同数据库、不同库实例甚至不同数据库类型中，调用方需要分别接入和处理，接入成本高、关联查询困难、重复开发较多。

本系统建设目标如下：

- 统一封装异构数据库的数据查询能力
- 通过标准 API 对外暴露查询结果
- 支持跨数据库联邦查询
- 支持批量查询能力
- 支持查询缓存以提升性能
- 支持数据库连接和 SQL 的配置化管理
- 支持一个服务直接维护一条联邦 SQL
- 支持联邦 SQL 的优化能力，包括 Join Reorder、Filter Pushdown、Project Pushdown
- 支持更复杂表达式与 SQL 方言兼容
- 支持逐步演进为自助式 SQL 数据服务平台
- 降低业务系统接入复杂度，提高复用性

本项目采用稳扎稳打的瀑布式实施方法，先完成需求、架构、设计、开发、测试、验收各阶段，再推进下一阶段建设，不采用边开发边频繁改范围的方式。

## 3. 适用范围

本文档适用于以下需求范围：

- 异构数据库统一查询服务
- 数据服务配置管理
- 单次查询、联邦查询、批量查询
- 查询结果缓存
- 前端配置管理界面
- 联邦 SQL 服务定义与发布
- 联邦 SQL 校验、优化与执行
- 服务版本管理与发布管理
- 平台权限控制与审计能力
- 自助式 SQL 数据服务平台能力

本文档不包含以下内容：

- 数据新增、修改、删除能力
- 数据同步、ETL、离线计算能力
- 报表分析和 BI 展示能力
- 通用数据开发平台能力
- 工作流审批能力

## 4. 文档适用原则

为便于评审、设计、开发和验收，本文档遵循以下适用原则：

- 文档中的“必须”表示强制性要求，默认纳入设计、开发和验收范围
- 文档中的“应”表示重要要求，原则上应满足；如无法满足，需在后续设计或评审中说明原因
- 文档中的“支持”表示系统需具备相应能力，但具体实现方式可在设计阶段确定
- 本文档中的范围边界、阶段边界和业务规则高于一般描述性表述
- 若后续设计文档与本需求规格发生冲突，应以本需求规格书为准，除非需求评审会明确批准变更

## 5. 前置假设

本文档默认以下前置假设成立：

- 接入的数据源均为业务允许访问的合法数据库实例
- 数据源网络连通性、账号权限和基础环境由外部系统或运维侧保障
- 调用方具备调用统一 API 所需的网络与认证条件
- 目标数据以在线查询为主，不以大规模离线分析为主要使用模式
- 平台部署形态以单机独立部署可运行为基础，后续是否扩展为分布式部署不影响本期基础能力定义

## 6. 术语定义

| 术语 | 定义 |
| --- | --- |
| 数据服务 | 对外暴露的统一查询能力，由系统配置后通过 API 提供 |
| 数据源连接 | 用于连接某类数据库实例的连接配置 |
| 目标库 | 数据源连接下可访问的 database 或 schema |
| 配置化 SQL | 由系统维护的查询语句，而非在代码中写死 |
| 关联查询 | 对多个来源的数据进行关联后统一返回 |
| 联邦查询 | 由系统对多个异构数据源进行统一解析、优化和执行后返回结果 |
| 联邦 SQL | 由系统解析和执行的一条跨来源 SQL |
| 批量查询 | 一次请求中按多组输入条件批量查询数据 |
| 查询缓存 | 对查询结果进行缓存，以减少重复查询开销 |
| 服务版本 | 数据服务在某次发布时固化形成的可调用版本 |
| 发布 | 将服务定义从草稿状态转为可对外调用状态的操作 |
| 草稿态 | 服务定义可编辑但不可对外调用的状态 |
| 已发布态 | 服务定义已生效并可对外调用的状态 |
| 已停用态 | 服务定义不可再对外调用的状态 |
| 自助式 SQL 数据服务平台 | 管理员或授权用户通过界面定义、校验、发布和管理数据服务的能力平台 |

## 7. 用户、角色与使用场景

### 7.1 目标用户与角色职责

- 平台管理员
  - 配置数据源连接
  - 配置数据服务
  - 维护联邦 SQL
  - 发布和停用数据服务
  - 管理权限与审计信息
- 数据服务开发人员
  - 编写和调试联邦 SQL
  - 验证服务定义、参数和输出结构
  - 查看校验结果、执行计划和诊断信息
- 业务系统
  - 调用统一 API 获取数据结果
- 测试与运维人员
  - 验证接口可用性
  - 排查查询异常与性能问题
  - 查看日志、调用轨迹与关键诊断信息

### 7.2 核心使用场景

#### 场景一：统一查询单个数据库中的业务数据

业务系统通过一个统一 API 调用某个已配置的数据服务，系统从指定数据库执行 SQL 并返回结果。

#### 场景二：跨不同数据库进行联邦查询

业务系统调用一个已配置的数据服务，系统将不同数据库中的数据进行关联处理，并返回统一结果。

#### 场景三：批量查询多组业务数据

业务系统一次提交多组查询条件，系统批量执行查询并返回结果集合。

#### 场景四：复用同一连接访问多个目标库

管理员为某类数据库配置一次连接，系统在该连接下管理多个目标库，多个数据服务复用该连接能力。

#### 场景五：热点查询命中缓存

业务系统重复查询同一组数据时，系统优先返回缓存结果，以减少数据库访问压力并提升响应效率。

#### 场景六：一个服务直接维护一条联邦 SQL

管理员或数据服务开发人员通过系统维护一条联邦 SQL，系统完成解析、校验、发布和执行，对外仍以统一数据服务方式暴露。

#### 场景七：系统自动优化联邦 SQL

管理员维护联邦 SQL 后，系统在执行前自动进行 Join Reorder、Filter Pushdown、Project Pushdown 等优化，以降低联邦查询执行成本。

#### 场景八：自助式配置和发布数据服务

管理员或授权用户通过平台界面完成数据源接入、联邦 SQL 配置、参数定义、结果定义、校验、发布和停用，无需每个服务都通过后端代码定制开发。

## 8. 总体需求

### 8.1 产品能力要求

- 系统必须对外提供统一的数据查询 API
- 系统必须支持 Oracle、MySQL、PostgreSQL 等不同类型数据库
- 系统必须支持通过配置方式维护数据库连接
- 系统必须支持通过配置方式维护查询 SQL
- 系统必须支持联邦查询
- 系统必须支持批量查询
- 系统必须支持查询结果缓存
- 系统必须提供前端配置管理界面
- 系统必须支持一个服务直接维护一条联邦 SQL
- 系统必须支持联邦 SQL 解析、校验与发布
- 系统必须支持联邦 SQL 自动优化
- 系统必须支持服务版本管理
- 系统必须支持平台权限控制与审计能力
- 系统必须支持自助式 SQL 数据服务平台能力

### 8.2 业务约束

- 系统仅提供查询能力，不提供写入能力
- 数据服务必须先配置并发布后才能被调用
- 一个数据库服务连接必须能够连接多个目标库
- 调用方不需要感知底层数据库类型和物理位置
- 联邦 SQL 必须由系统统一解析、校验、发布与执行
- 联邦 SQL 仅允许用于只读查询，不允许包含写入、DDL、存储过程调用或其他具有副作用的语句
- 所有调用参数必须通过平台定义并按参数化方式传入，不允许通过字符串拼接形成可执行 SQL
- 系统必须支持在普通单台服务器上独立部署和运行，不依赖分布式集群才能提供基础能力
- 平台能力建设采用分阶段实施，前一阶段验收完成后才能进入下一阶段

### 8.3 建设阶段要求

本系统采用瀑布式实施，按以下阶段建设：

#### 第一阶段：数据服务基础能力建设

目标：

- 建立统一数据服务基础框架

- 打通异构数据库接入、配置管理、统一查询 API、批量查询、缓存、前端配置界面

- 形成可发布、可调用、可测试、可验收的基础系统

范围：

- 数据源连接管理

- 目标库管理

- 数据服务配置管理

- 单次查询

- 批量查询

- 基础跨库关联能力

- 查询缓存

- 前端配置界面

- 基础版本管理与发布管理

阶段边界说明：

- 第一阶段中的基础跨库关联能力，指由平台预定义的数据服务完成有限范围的跨源组合查询

- 第一阶段不要求提供通用联邦 SQL 自助编辑能力

- 第一阶段不要求提供完整的联邦 SQL 优化器、方言兼容和执行计划诊断能力

- 第一阶段的跨源能力应以可交付、可验证、可控复杂度为原则，不以通用 SQL 平台能力为目标

#### 第二阶段：联邦 SQL 平台能力建设

目标：

- 支持一个服务直接维护一条联邦 SQL
- 支持联邦 SQL 自动优化
- 支持更复杂表达式和 SQL 方言兼容
- 将系统升级为自助式 SQL 数据服务平台

范围：

- 联邦 SQL 编辑、校验、发布、执行
- 联邦 SQL 优化能力
- 联邦 SQL 方言兼容能力
- 联邦查询计划展示与诊断
- 平台级服务自助配置能力
- 完整服务版本管理与可追溯发布能力
- 平台权限控制与审计能力完善

阶段边界说明：

- 第二阶段以联邦 SQL 作为数据服务核心定义方式之一
- 第二阶段中，服务的数据来源应能够由联邦 SQL 解析结果自动识别，并用于校验、执行和诊断
- 若服务显式配置的数据来源与联邦 SQL 解析结果不一致，系统必须给出校验提示，并以发布规则定义的校验结果为准

## 9. 功能需求

### 9.1 数据源连接管理

系统必须支持数据库连接配置管理。

功能要求：

- 支持新增数据库连接
- 支持编辑数据库连接
- 支持启用和停用数据库连接
- 支持测试数据库连接可用性
- 支持在一个连接下配置多个目标库
- 支持不同数据库类型的连接配置
- 支持对连接配置进行脱敏展示
- 支持记录连接配置的变更信息

约束：

- 数据库连接信息必须可复用
- 一个连接配置应可服务多个数据服务
- 连接凭据不得以明文方式对普通使用者展示

### 9.2 数据服务配置管理

系统必须支持数据服务定义与维护。

功能要求：

- 支持创建数据服务
- 支持编辑数据服务
- 支持停用数据服务
- 支持维护数据服务对应的 SQL
- 支持维护数据服务依赖的数据来源
- 支持维护数据服务的输入参数定义
- 支持维护数据服务的输出结果定义
- 支持维护数据服务的调用标识、名称、说明和状态
- 支持数据服务发布
- 支持服务草稿态、已发布态和已停用态管理
- 支持为一个数据服务维护一条联邦 SQL
- 支持联邦 SQL 校验
- 支持联邦 SQL 预览或执行验证

约束：

- 未发布数据服务不得对外提供调用
- SQL 必须由配置管理，不得要求每个服务都通过代码开发实现
- 输入参数必须定义名称、类型、是否必填及校验规则
- 输出结果应可定义字段名称、类型、是否可空及说明

### 9.3 联邦 SQL 管理

系统必须支持联邦 SQL 的统一管理能力。

功能要求：

- 支持为一个数据服务定义一条联邦 SQL
- 支持联邦 SQL 的语法校验
- 支持联邦 SQL 的来源解析
- 支持联邦 SQL 的执行计划生成
- 支持联邦 SQL 发布前校验
- 支持联邦 SQL 版本管理
- 支持联邦 SQL 预览执行
- 支持显示联邦 SQL 的校验、发布和执行结果

业务要求：

- 联邦 SQL 作为数据服务核心定义之一被管理
- 联邦 SQL 的维护过程应可视、可校验、可发布
- 调用方无需感知 SQL 背后的多源执行细节
- 联邦 SQL 仅允许定义只读查询逻辑，不允许出现写入类或副作用类语句
- 第二阶段中，联邦 SQL 解析出的数据来源应作为服务发布校验的重要依据之一

### 9.4 统一查询 API

系统必须对外提供统一查询入口。

功能要求：

- 业务系统通过统一 API 调用数据服务
- 系统根据服务标识定位对应服务配置
- 系统执行查询后返回统一结构结果
- 调用方无需感知底层数据库类型差异
- 支持单次查询与批量查询使用统一的调用规范
- 支持返回标准化错误信息
- 支持返回服务版本、执行状态、耗时、缓存命中标识等元信息

接口要求：

- 统一 API 必须定义稳定的请求结构、响应结构和错误结构
- 请求结构至少应包含服务标识、调用参数和调用上下文信息
- 批量查询请求结构至少应支持多组参数输入
- 响应结构至少应包含结果数据、结果状态、错误信息和元信息
- 错误返回应能够区分参数错误、配置错误、数据源错误、校验错误、执行错误和资源保护错误

期望结果：

- 不同数据服务的调用方式保持一致
- 不同底层数据库返回结果的接入方式保持一致

### 9.5 联邦查询

系统必须支持联邦查询能力。

功能要求：

- 支持同类型数据库之间的关联查询
- 支持不同类型数据库之间的关联查询
- 支持同一数据服务组合多个数据来源
- 支持将关联结果统一返回给调用方
- 支持一个服务直接通过一条联邦 SQL 定义多源查询逻辑
- 支持联邦查询中的复杂表达式
- 支持多数据源联邦查询的统一执行
- 支持联邦查询计划优化

业务要求：

- 调用方只感知统一结果，不感知底层关联细节
- 关联查询结果应满足业务查询需要
- 系统应自动优化联邦查询执行过程
- 第一阶段联邦查询能力以预定义、可控复杂度的跨源组合查询为主
- 第二阶段联邦查询能力以通用联邦 SQL 驱动的解析、优化和执行为主

### 9.6 联邦查询优化

系统必须支持联邦查询优化能力。

功能要求：

- 支持 Join Reorder
- 支持 Filter Pushdown
- 支持 Project Pushdown
- 支持根据数据源能力选择可下推操作
- 支持在无法下推时由系统侧完成补充处理
- 支持展示关键优化结果或优化说明

业务要求：

- 优化过程应以提升查询性能和降低跨源数据传输成本为目标
- 优化结果不应改变查询语义
- 优化行为应可诊断、可追踪

### 9.7 SQL 表达式与方言兼容

系统必须支持联邦 SQL 的表达式与方言兼容能力。

功能要求：

- 支持常见查询表达式
- 支持聚合、过滤、排序、投影、关联等基础 SQL 能力
- 支持不同数据源的方言差异处理
- 支持统一 SQL 到目标数据源执行语义的适配
- 支持对不兼容语法给出明确校验或转换提示

业务要求：

- 平台不要求用户分别维护不同数据库方言版本的服务定义
- 平台应尽量屏蔽底层数据库语法差异
- 对无法兼容的表达式，系统必须给出明确限制说明或校验失败原因

### 9.8 批量查询

系统必须支持批量查询能力。

功能要求：

- 支持一次请求中提交多组查询条件
- 支持系统批量执行查询
- 支持按统一格式返回批量结果
- 支持在批量场景下识别单条结果与输入条件的对应关系
- 支持对批量规模进行控制

业务要求：

- 批量查询应减少调用方的多次请求成本
- 批量查询结果应便于调用方进行映射和处理
- 系统应能够限制单次批量请求规模，避免单次请求占用过多资源

### 9.9 查询缓存

系统必须支持查询缓存能力。

功能要求：

- 支持对查询结果进行缓存
- 支持重复查询命中缓存
- 支持缓存失效
- 支持按数据服务维度控制是否启用缓存
- 支持按服务配置缓存时间或失效策略
- 支持通过服务标识、服务版本和参数形成缓存键
- 支持在响应结果中标识是否命中缓存

业务要求：

- 缓存用于提高查询性能
- 缓存不能导致错误结果长期返回
- 对时效性要求高的数据服务应支持关闭缓存或缩短缓存时间

### 9.10 前端配置界面

系统必须提供前端配置管理能力。

功能要求：

- 支持数据源连接配置界面
- 支持目标库配置界面
- 支持数据服务配置界面
- 支持 SQL 配置界面
- 支持联邦 SQL 编辑界面
- 支持联邦 SQL 校验结果展示界面
- 支持联邦查询计划或执行说明展示界面
- 支持参数配置界面
- 支持返回结果配置界面
- 支持缓存策略配置界面
- 支持服务发布与停用操作
- 支持自助式服务创建与维护操作
- 支持版本信息展示
- 支持关键审计信息展示

业务要求：

- 管理员可通过界面完成配置，不依赖直接改代码
- 具备相应权限的用户可在界面完成服务维护、校验和发布

### 9.11 平台化能力

系统必须具备向自助式 SQL 数据服务平台演进的能力。

功能要求：

- 支持通过平台界面自助创建数据服务
- 支持通过平台界面自助维护联邦 SQL
- 支持通过平台界面完成校验、发布、停用
- 支持服务版本管理
- 支持执行结果、校验结果和诊断信息展示
- 支持数据服务的规范化沉淀与复用

业务要求：

- 平台应尽量减少单服务单开发的建设模式
- 平台应支持规范化、标准化地沉淀数据服务

### 9.12 权限与审计管理

系统必须支持平台权限与审计能力。

功能要求：

- 支持区分平台管理员、数据服务开发人员、调用方等角色的权限范围
- 支持控制谁可以查看、编辑、发布、停用数据服务
- 支持控制谁可以查看连接配置、测试连接、执行预览验证
- 支持对敏感信息进行脱敏展示
- 支持记录配置变更、发布、停用、测试连接、执行验证等关键操作日志
- 支持按服务、用户、时间等维度查询审计记录

业务要求：

- 权限控制必须覆盖配置、发布、调用和查看诊断信息等关键操作
- 审计记录应满足问题追踪和责任定位需要

### 9.13 服务版本与发布管理

系统必须支持服务版本与发布管理能力。

功能要求：

- 支持对数据服务进行版本化管理
- 支持记录每次发布对应的服务定义、参数定义、输出定义和 SQL 定义
- 支持查看当前生效版本和历史版本信息
- 支持停用已发布服务
- 支持将发布行为纳入审计记录

业务要求：

- 调用方应调用到明确、可追溯的服务版本
- 发布后的服务版本应与草稿编辑状态相互隔离
- 版本管理应支持问题回溯、变更审计和验收确认

## 10. 非功能需求

### 10.1 性能需求

- 高频查询场景应支持通过缓存提升响应效率
- 批量查询应优于多次单条请求的总体成本
- 系统应尽量减少重复建立数据库连接的开销
- 联邦 SQL 执行应尽量减少跨源数据搬运
- 系统应支持通过优化降低联邦查询成本
- 系统在普通单台服务器配置下应可稳定运行，基线资源按 4 核 CPU、16G 内存考虑
- 系统设计不得默认依赖大内存机器或分布式扩容才能避免内存溢出
- 对大结果集、跨源 Join、批量查询和联邦 SQL 补算场景，系统必须提供资源保护机制，避免单次请求导致进程内存耗尽
- 系统应支持通过限流、受控并发、中间结果落盘、结果集上限、超时控制等方式保障单机运行稳定性
- 系统应支持配置单次查询结果上限、批量查询规模上限和执行超时阈值

### 10.2 可用性需求

- 数据服务发布后应可稳定对外提供访问
- 数据源不可用时系统应返回明确错误
- 配置错误时系统应能提示配置问题
- 联邦 SQL 校验失败时系统应返回明确原因
- 联邦查询执行失败时系统应能定位到来源、阶段或规则问题
- 在单机资源不足、结果集过大或执行超出资源阈值时，系统应优先进行受控失败，而不是出现进程崩溃或内存溢出
- 受控失败时应返回明确的错误类别和原因说明

### 10.3 可维护性需求

- 连接配置、SQL 配置、服务定义应解耦
- 新增数据服务应尽量通过配置完成
- 新增数据库类型时应具备扩展空间
- 联邦 SQL 解析、优化、执行应分层设计
- 平台能力建设应支持按阶段扩展，而不推翻前一阶段成果
- 服务定义、版本、发布记录和审计记录应具备可追溯性

### 10.4 安全性需求

- 数据库连接凭据必须安全存储
- 查询执行过程必须防止 SQL 注入
- 敏感配置展示时应做必要保护
- 联邦 SQL 的执行过程必须受系统统一控制，不允许绕过平台直接拼接危险语句执行
- 平台必须仅允许执行只读查询，不允许执行写入语句、DDL、存储过程调用或多语句混合执行
- 所有调用参数必须采用参数化绑定方式，不得直接拼接到 SQL 文本中执行
- 平台应对危险语句、危险函数或不允许的语法进行校验拦截

### 10.5 可观测性需求

- 系统应记录服务调用日志
- 系统应记录配置变更日志
- 查询异常应便于排查定位
- 系统应记录联邦查询计划、优化和执行的关键诊断信息
- 系统应能够区分缓存命中、校验失败、数据源失败、资源保护触发等典型事件

## 11. 业务规则

- 一个数据库连接配置可以连接多个目标库
- 一个数据服务至少对应一个数据来源
- 关联查询场景下，一个数据服务可对应多个数据来源
- 一个数据服务可以直接维护一条联邦 SQL
- 数据服务必须先发布再使用
- 查询 SQL 必须通过配置维护
- 查询缓存仅作用于查询结果，不改变业务数据本身
- 联邦 SQL 的解析、优化、校验和执行必须纳入平台统一管理
- 联邦 SQL 只能定义只读查询逻辑，不能执行写入类或副作用类操作
- 服务调用必须基于已定义参数进行参数化执行
- 发布后的服务版本应作为可追溯调用基线
- 第二阶段建设必须在第一阶段验收完成后启动

## 12. 约束与边界

### 12.1 范围内

- 数据查询服务
- 连接配置管理
- SQL 配置管理
- 联邦查询
- 联邦 SQL 管理
- 联邦查询优化
- SQL 方言兼容
- 批量查询
- 查询缓存
- 前端配置界面
- 服务版本管理与发布管理
- 权限控制与审计能力
- 自助式 SQL 数据服务平台能力

### 12.2 范围外

- 数据写入接口
- 工作流审批
- 数据清洗与数据治理流程
- 数据同步链路建设
- 报表分析和 BI 展示
- 存储过程编排能力
- 通用离线计算平台能力

## 13. 验收标准

### 13.1 功能验收

- 第一阶段验收：
- 能配置至少一种 Oracle 数据源并成功查询
- 能配置至少一种 MySQL 数据源并成功查询
- 能配置至少一种 PostgreSQL 数据源并成功查询
- 能基于统一 API 成功调用已发布数据服务
- 能完成至少一个跨数据库关联查询场景
- 能完成至少一个批量查询场景
- 能在重复查询场景下命中缓存
- 能通过前端界面完成数据服务配置和发布
- 能体现服务草稿、发布、停用等基本状态流转

- 第二阶段验收：
- 能为一个数据服务直接维护一条联邦 SQL
- 能完成联邦 SQL 的语法校验与发布
- 能完成至少一个同类型数据库联邦 SQL 场景
- 能完成至少一个异构数据库联邦 SQL 场景
- 能体现 Join Reorder、Filter Pushdown、Project Pushdown 的优化能力
- 能支持更复杂表达式和 SQL 方言兼容
- 能通过平台界面完成联邦 SQL 数据服务的自助创建、发布和管理
- 能展示联邦 SQL 的校验结果、执行计划或关键诊断信息
- 能体现权限控制和关键操作审计能力

### 13.2 结果验收

- 调用方能够通过统一方式获取查询结果
- 调用方不需要关注底层数据库差异
- 管理员能够通过配置完成服务维护
- 系统能够明确反馈连接失败、配置错误、查询失败等异常情况
- 系统在结果集过大、批量规模超限、执行超时或资源受限时，能够返回受控错误而非进程崩溃
- 平台能够支撑从“配置驱动查询系统”逐步演进为“自助式 SQL 数据服务平台”

### 13.3 评审关注点

本需求规格书在评审时应重点确认以下事项：

- 第一阶段与第二阶段的边界是否清晰且被各方接受
- 统一 API、服务定义、联邦 SQL、缓存、权限和审计的范围是否完整
- 只读边界、参数化要求和安全限制是否明确
- 单机部署、资源保护和受控失败要求是否满足建设目标
- 验收标准是否能够支持后续测试设计和项目验收

## 14. 验收指标与测试口径

### 14.1 总体原则

- 本章节用于补充功能验收和结果验收的测试口径，作为测试设计、联调验证和项目验收的依据
- 本章节优先定义“如何验证”，不强制规定具体实现方案
- 若后续测试方案与本章节存在冲突，应以本章节为准，除非评审明确调整
- 本章节中的“建议值”可在项目评审后固化为测试基线；未固化前，测试应至少覆盖相应类别场景

### 14.2 测试环境口径

- 单机部署验收应以普通单台服务器环境为基础，推荐基线为 4 核 CPU、16G 内存
- 测试环境应至少包含 Oracle、MySQL、PostgreSQL 三类数据源中的可用实例
- 联邦查询测试应覆盖同构数据源场景和异构数据源场景
- 批量查询、缓存、权限、审计、发布等能力应在与真实部署方式一致的环境中验证

### 14.3 功能测试口径

#### 14.3.1 数据源连接管理

- 应验证新增、编辑、启用、停用、测试连接功能可正常使用
- 应验证一个连接可绑定多个目标库
- 应验证连接信息对非授权用户以脱敏方式展示
- 应验证连接变更产生审计记录

#### 14.3.2 数据服务配置与发布

- 应验证服务可从草稿态进入已发布态，并可从已发布态进入已停用态
- 应验证未发布服务不可被统一 API 调用
- 应验证已发布服务可被统一 API 正常调用
- 应验证服务参数定义、输出定义、SQL 定义在发布后形成可追溯版本

#### 14.3.3 统一查询 API

- 应验证不同数据服务通过统一的调用方式访问
- 应验证单次查询与批量查询使用统一接口规范或统一协议风格
- 应验证返回结构中包含结果数据、执行状态、错误信息和元信息
- 应验证错误返回能够区分参数错误、配置错误、数据源错误、校验错误、执行错误和资源保护错误

#### 14.3.4 联邦查询与联邦 SQL

- 第一阶段应验证至少一个预定义跨源组合查询场景
- 第二阶段应验证至少一个同构联邦 SQL 场景和至少一个异构联邦 SQL 场景
- 应验证联邦 SQL 可完成语法校验、来源解析、发布校验和执行
- 应验证联邦 SQL 与服务显式配置来源不一致时，系统可给出明确校验提示

#### 14.3.5 缓存与批量查询

- 应验证重复请求可命中缓存，且响应中能识别缓存命中状态
- 应验证不同参数、不同服务版本形成不同缓存键
- 应验证批量查询结果能够与输入条件建立对应关系
- 应验证批量规模超出阈值时触发受控失败或明确限制提示

#### 14.3.6 权限与审计

- 应验证不同角色拥有不同的查看、编辑、发布、停用、测试连接和预览执行权限
- 应验证非授权用户无法查看敏感配置信息明文
- 应验证配置变更、发布、停用、测试连接、预览执行等关键操作产生审计记录
- 应验证审计记录至少支持按服务、用户、时间维度检索

### 14.4 非功能测试口径

#### 14.4.1 性能与资源保护

- 应验证在单机基线资源下，系统能够稳定完成单次查询、批量查询和联邦查询场景
- 应验证系统具备结果集上限、批量规模上限、执行超时、受控并发等资源保护能力
- 应验证大结果集、跨源 Join、联邦补算等场景不会直接导致进程崩溃或内存溢出
- 应验证资源保护触发后返回明确错误，而不是无响应或异常退出

#### 14.4.2 可用性与可观测性

- 应验证数据源不可用时，系统返回明确错误信息
- 应验证配置错误、校验失败、执行失败时，可定位问题类别和关键阶段
- 应验证日志中能区分缓存命中、校验失败、数据源失败、资源保护触发等事件
- 应验证联邦查询计划、优化说明和关键执行诊断信息可查看

#### 14.4.3 安全性

- 应验证平台仅允许执行只读查询，不允许执行写入、DDL、存储过程调用或多语句混合执行
- 应验证调用参数通过参数化方式传入，恶意输入不会被直接拼接执行
- 应验证危险语句或不允许语法在校验或执行前被拦截
- 应验证敏感配置在展示、日志和审计中不会以不受控方式泄露

### 14.5 建议量化指标

以下指标作为建议测试基线，最终可在详细设计或测试方案中固化：

- 单次查询结果上限：应支持配置，建议默认不超过 10000 行
- 批量查询规模上限：应支持配置，建议默认不超过 100 组条件
- 单次查询超时阈值：应支持配置，建议默认不超过 30 秒
- 联邦查询超时阈值：应支持配置，建议默认不超过 60 秒
- 审计日志保留周期：应支持配置，建议不少于 180 天
- 缓存时间：应支持按服务配置，建议默认按分钟级或小时级设置，不得写死为全局固定值

说明：

- 上述建议值用于统一测试口径，不表示必须采用该默认值
- 若项目评审确认其他阈值，应以评审确认结果替换本节建议值
- 若某项指标因业务场景特殊而不同，应在对应服务设计中单独说明

### 14.6 验收结论判定口径

- 当强制性功能项全部通过，且不存在阻断上线的安全、稳定性、权限或数据正确性问题时，可判定功能验收通过
- 当非功能测试中不存在进程崩溃、内存溢出、权限失控、敏感信息泄露等重大问题时，可判定非功能验收通过
- 当发现问题但不影响主流程、可控且有明确整改计划时，可列为遗留问题进入整改跟踪
- 当存在阶段边界不清、核心场景未覆盖、关键能力缺失或重大安全稳定性缺陷时，不应判定验收通过
