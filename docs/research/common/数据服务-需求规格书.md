# 数据服务需求规格书

## 1. 文档目的

本文档为 `data-service` 项目的正式需求规格书，用于定义 SQL-first 数据服务平台的目标、范围、业务规则、功能需求、非功能需求和验收口径，作为后续架构设计、详细设计、开发、测试和验收的依据。

本文档只描述系统必须提供的正式能力，不保留已废弃的目标库维护、来源手工配置、字段手工配置、参数手工配置、过渡方案和讨论过程。

## 2. 背景与目标

当前业务系统需要从不同数据库中获取数据，并通过统一 API 对外提供查询能力。现有数据分散在不同数据库类型、不同实例和不同连接中，调用方接入成本高，跨源查询复杂，重复开发较多。

本系统建设目标如下：

- 统一封装异构数据库的数据查询能力
- 通过统一 API 对外暴露查询结果
- 支持单源 SQL 与联邦 SQL
- 支持批量查询能力
- 支持查询结果缓存
- 支持数据库连接配置管理
- 支持以 SQL 作为数据服务定义的唯一事实来源
- 支持在保存时自动解析来源、参数和字段
- 支持在发布时完成完整校验并生成版本快照
- 支持在运行时按已发布快照执行
- 支持联邦 SQL 优化能力，包括 Join Reorder、Filter Pushdown、Project Pushdown
- 必须支持常见数据库之间的异构联邦查询能力
- 必须支持复杂表达式与 SQL 方言兼容能力，对无法兼容的语法或表达式必须明确失败
- 必须支持 SQL 预览执行能力，用于保存和发布前的受控验证
- 支持自助式 SQL 数据服务平台能力
- 支持多租户调用上下文透传，并预留多租户相关元数据字段
- 降低业务系统接入复杂度，提高复用性

## 3. 适用范围

本文档适用于以下需求范围：

- 异构数据库统一查询服务
- 数据源连接管理
- SQL-first 数据服务定义与管理
- 单次查询、联邦查询、批量查询
- 查询结果缓存
- 前端配置管理界面
- SQL 保存、校验、发布、停用
- 服务版本管理与快照管理
- 联邦 SQL 优化、执行计划与诊断
- 平台权限控制与审计能力
- 多租户调用上下文支持与隔离元数据预留

本文档不包含以下内容：

- 数据新增、修改、删除能力
- 数据同步、ETL、离线计算能力
- 报表分析和 BI 展示能力
- 工作流审批能力
- 旧模型迁移方案

## 4. 文档适用原则

- 文档中的“必须”表示强制性要求，纳入设计、开发、测试和验收范围
- 文档中的“应”表示重要要求，原则上应满足；若无法满足，需在评审中明确说明
- 文档中的“支持”表示系统需具备该能力，具体实现方式可由设计文档承接
- 本文档中的业务边界、只读边界、数据模型边界和验收口径高于一般描述性表述
- 若后续设计文档与本需求规格书冲突，应以本需求规格书为准，除非评审已批准变更

## 5. 前置假设

- 接入的数据源均为业务允许访问的合法数据库实例
- 数据源网络连通性、账号权限和基础环境由外部系统或运维保障
- 调用方具备调用统一 API 所需的网络与认证条件
- 目标场景以在线查询为主，不以离线计算为主要使用模式
- 系统以单机独立部署可运行为基础，后续扩展方式不影响本期正式需求定义

## 6. 术语定义

| 术语 | 定义 |
| --- | --- |
| 数据服务 | 对外暴露的统一查询能力，由系统保存、发布后通过 API 提供 |
| 数据源连接 | 用于连接某类数据库实例的连接配置，只表达数据库连通能力 |
| 简单 SQL | 在一个默认连接内执行的 SQL，SQL 中必须显式写 `schema.table` 或 `database.table` |
| 联邦 SQL | 由系统解析和执行的跨连接 SQL，允许使用平台 DSL `connection_code@schema_or_database.table_name` |
| SQL-first | 以 SQL 作为服务定义唯一事实来源的模式 |
| 来源快照 | 系统在保存或发布时从 SQL 中解析得到的连接、schema、table 等来源信息 |
| 参数快照 | 系统在保存或发布时从 SQL 模板中解析得到的参数信息 |
| 字段快照 | 系统在保存或发布时从最终 `select` 输出中解析得到的字段信息 |
| 服务版本 | 数据服务在某次发布时固化形成的可调用版本 |
| 发布 | 将草稿服务校验通过后固化为可运行版本的操作 |
| 草稿态 | 服务可编辑但不可对外调用的状态 |
| 已发布态 | 服务已生效并可对外调用的状态 |
| 已停用态 | 服务不可再对外调用的状态 |
| 查询缓存 | 对查询结果进行缓存，以减少重复查询开销 |
| SQL 预览执行 | 在草稿保存后或发布前，对当前 SQL、参数和连接或联邦解析结果进行一次受控只读执行验证的能力 |
| 调用上下文 | 统一查询 API 请求中携带的附加信息，包括但不限于租户标识、调用方标识、链路追踪标识等 |
| 多租户元数据预留 | 系统在接口契约、缓存隔离、审计记录和元数据模型中预留租户相关字段或摘要信息的能力；当前不要求所有元数据表立即强制落租户字段 |
| 自助式 SQL 数据服务平台 | 管理员或授权用户通过界面完成 SQL 编写、校验、发布、运行和管理的能力平台 |

## 7. 用户、角色与使用场景

### 7.1 目标用户与角色职责

- 平台管理员
  - 配置数据源连接
  - 创建、编辑、发布、停用数据服务
  - 管理权限与审计信息
- 数据服务开发人员
  - 编写和调试简单 SQL、联邦 SQL
  - 确认参数类型
  - 查看校验结果、执行计划和诊断信息
- 业务系统
  - 通过统一 API 调用数据服务
- 测试与运维人员
  - 验证接口可用性
  - 排查查询异常与性能问题
  - 查看日志、调用轨迹与关键诊断信息

### 7.2 核心使用场景

#### 场景一：统一查询单个数据库中的业务数据

业务系统通过统一 API 调用某个已发布数据服务，系统在默认连接上执行简单 SQL 并返回结果。

#### 场景二：跨不同数据库进行联邦查询

业务系统调用某个已发布联邦数据服务，系统解析联邦 SQL，访问多个连接中的数据并返回统一结果。

#### 场景三：批量查询多组业务数据

业务系统一次提交多组查询条件，系统批量绑定参数并返回结果集合。

#### 场景四：保存 SQL 时自动解析服务结构

管理员或数据服务开发人员保存服务时，系统自动解析 SQL 中的来源、参数和输出字段，并生成草稿快照。

#### 场景五：发布前完成严格校验

管理员发布服务时，系统重新解析 SQL，校验连接、对象存在性、只读规则、参数类型、能力边界和执行计划，校验通过后生成新版本。

#### 场景六：运行时按快照执行

业务系统调用已发布服务时，系统只读取当前发布版本快照执行，不再依赖手工维护的来源、字段或参数配置。

#### 场景七：热点查询命中缓存

业务系统重复查询同一服务、同一版本、同一组参数时，系统优先返回缓存结果。

#### 场景八：自助式配置和发布数据服务

管理员或授权用户通过平台界面完成数据源接入、SQL 编写、校验、发布和停用，无需后端为每个服务单独开发代码。

## 8. 总体需求

### 8.1 产品能力要求

- 系统必须对外提供统一的数据查询 API
- 系统必须支持 Oracle、MySQL、PostgreSQL 等不同类型数据库
- 系统必须支持通过配置方式维护数据库连接
- 系统必须支持通过配置方式维护简单 SQL 与联邦 SQL
- 系统必须支持以 SQL 作为服务定义唯一事实来源
- 系统必须支持在保存时自动解析来源、参数和字段
- 系统必须支持在发布时完成完整校验并固化版本快照
- 系统必须支持运行时按已发布快照执行
- 系统必须支持联邦查询
- 系统必须支持批量查询
- 系统必须支持查询结果缓存
- 系统必须提供前端配置管理界面
- 系统必须支持联邦 SQL 解析、校验、优化与发布
- 系统必须支持常见数据库之间的异构联邦查询
- 系统必须支持复杂表达式与 SQL 方言兼容
- 系统必须支持 SQL 预览执行
- 系统必须支持服务版本管理
- 系统必须支持平台权限控制与审计能力
- 系统必须支持多租户调用上下文透传与元数据预留
- 系统必须支持自助式 SQL 数据服务平台能力

### 8.2 业务约束

- 系统仅提供查询能力，不提供写入能力
- 数据服务必须先保存并发布后才能被调用
- 数据源连接只表达连通能力，不表达目标库配置
- 简单 SQL 必须在 SQL 文本中显式写数据库内部全限定名
- 联邦 SQL 必须在 SQL 文本中显式写连接编码与全限定表名
- 联邦 SQL 必须由系统统一解析、校验、优化、发布与执行
- 联邦 SQL 仅允许只读查询，不允许包含写入、DDL、存储过程调用或其他具有副作用的语句
- 所有调用参数必须通过 SQL 模板占位符表达并按参数化方式传入，不允许通过字符串拼接形成可执行 SQL
- SQL 预览执行仅用于草稿保存后或发布前的受控只读验证，不形成正式发布版本
- 多租户能力当前以调用上下文透传和元数据字段预留表达，不要求当前所有元数据表立即强制增加 tenant_id 字段
- 查询缓存若使用调用上下文参与结果隔离，必须将关键上下文字段纳入缓存键
- 系统必须支持在普通单台服务器上独立部署和运行，不依赖分布式集群才能提供基础能力

## 9. 功能需求

### 9.1 数据源连接管理

系统必须支持数据库连接配置管理。

功能要求：

- 支持新增数据库连接
- 支持编辑数据库连接
- 支持启用和停用数据库连接
- 支持测试数据库连接可用性
- 支持不同数据库类型的连接配置
- 支持对连接配置进行脱敏展示
- 支持记录连接配置的变更信息

约束：

- 数据库连接信息必须可复用
- 一个连接配置应可服务多个数据服务
- 保存连接时必须验证 JDBC 连通性
- 连接凭据不得以明文方式对普通使用者展示
- 已停用连接不得用于服务发布和运行

### 9.2 数据服务管理

系统必须支持 SQL-first 数据服务定义与维护。

功能要求：

- 支持创建数据服务
- 支持编辑数据服务
- 支持停用数据服务
- 支持维护数据服务对应的 SQL
- 支持维护数据服务的调用标识、名称、说明、SQL 类型和状态
- 支持数据服务保存
- 支持数据服务发布
- 支持服务草稿态、已发布态和已停用态管理
- 支持为一个数据服务维护一条简单 SQL 或联邦 SQL
- 支持在保存时自动解析来源快照、参数快照和字段快照
- 支持在保存后展示解析结果供用户确认
- 支持在发布前执行重新校验

约束：

- 未发布数据服务不得对外提供调用
- SQL 必须由平台管理，不得要求每个服务都通过代码开发实现
- 服务定义不得再单独维护目标库、来源、字段或参数表单
- 复杂表达式输出列若无别名，系统必须保存失败

### 9.3 SQL 管理

系统必须支持简单 SQL 与联邦 SQL 的统一管理能力。

功能要求：

- 支持为一个数据服务定义一条 SQL
- 支持区分简单 SQL 与联邦 SQL
- 支持 SQL 语法校验
- 支持 SQL 来源解析
- 支持 SQL 参数解析
- 支持 SQL 输出字段解析
- 支持 SQL 执行计划生成
- 支持 SQL 发布前校验
- 支持 SQL 预览执行
- 支持返回 SQL 预览执行结果、执行耗时和关键诊断信息
- 支持对 SQL 预览执行施加权限、结果集上限、超时和资源保护控制
- 支持显示 SQL 的校验、发布和执行结果

业务要求：

- SQL 是数据服务的唯一事实来源
- SQL 的维护过程应可视、可校验、可发布
- SQL 预览执行用于验证当前草稿 SQL 的可执行性和结果形态，不替代正式发布校验
- SQL 预览执行必须受审计和只读约束控制
- 调用方无需感知 SQL 背后的多源执行细节
- SQL 仅允许定义只读查询逻辑，不允许出现写入类或副作用类语句

### 9.4 SQL 语法约束

系统必须对 SQL 语法提供明确约束。

功能要求：

- 简单 SQL 必须支持数据库内部全限定名写法，如 `schema.table_name`
- 联邦 SQL 必须支持平台 DSL 写法，如 `connection_code@schema_or_database.table_name`
- 参数模板必须支持 Doma 风格占位符
- 条件拼装必须支持 Doma 风格条件块
- 系统必须对不符合约束的 SQL 给出明确错误提示

业务要求：

- 简单 SQL 不允许依赖连接外部配置补充 schema 或 database 信息
- 联邦 SQL 不允许省略连接编码
- `/* */` 仅允许用于模板语法，不允许作为普通块注释使用

### 9.5 统一查询 API

系统必须对外提供统一查询入口。

功能要求：

- 业务系统通过统一 API 调用数据服务
- 系统根据服务标识定位当前发布版本
- 系统执行查询后返回统一结构结果
- 调用方无需感知底层数据库类型差异
- 支持单次查询与批量查询使用统一的调用规范
- 支持返回标准化错误信息
- 支持返回服务版本、执行状态、耗时、缓存命中标识等元信息

接口要求：

- 统一 API 必须定义稳定的请求结构、响应结构和错误结构
- 请求结构至少应包含服务标识、调用参数和调用上下文信息；调用上下文至少应支持租户标识、调用方标识和链路追踪标识
- 系统必须支持基于调用上下文进行权限校验、审计记录和缓存隔离扩展
- 批量查询请求结构至少应支持多组参数输入
- 响应结构至少应包含结果数据、结果状态、错误信息和元信息
- 错误返回应能够区分参数错误、配置错误、数据源错误、校验错误、执行错误和资源保护错误

### 9.6 联邦查询

系统必须支持联邦查询能力。

功能要求：

- 支持同类型数据库之间的联邦查询
- 支持不同类型数据库之间的联邦查询
- 支持一个服务通过一条联邦 SQL 定义多源查询逻辑
- 支持联邦查询中的复杂表达式
- 支持多数据源联邦查询的统一执行
- 支持联邦查询计划优化
- 支持执行计划或关键诊断信息展示

业务要求：

- 调用方只感知统一结果，不感知底层关联细节
- 常见数据库之间的异构联邦查询属于正式能力范围，不得作为后续扩展能力处理
- 系统必须支持异构联邦查询在保存、预览、发布和运行阶段的统一校验与执行
- 异构联邦查询失败时，系统必须明确定位到能力边界、方言差异、下推限制或执行计划问题，不得给出模糊失败结果
- 系统应自动优化联邦查询执行过程
- 系统必须能够在能力不足时明确失败，不得静默降级

### 9.7 联邦查询优化

系统必须支持联邦查询优化能力。

功能要求：

- 支持 Join Reorder
- 支持 Filter Pushdown
- 支持 Project Pushdown
- 支持根据数据源能力选择可下推操作
- 支持在无法下推时由系统侧完成补充处理，但不得改变查询语义，不得作为掩盖能力不足的静默降级手段；当系统无法在保持语义一致的前提下完成补充处理时，必须明确失败
- 支持展示关键优化结果或优化说明

业务要求：

- 优化过程应以提升查询性能和降低跨源数据传输成本为目标
- 优化结果不应改变查询语义
- 优化行为应可诊断、可追踪

### 9.8 SQL 表达式与方言兼容

系统必须支持 SQL 表达式与方言兼容能力。

功能要求：

- 支持常见查询表达式
- 支持复杂表达式，包括但不限于条件表达式、函数表达式、聚合表达式、`CASE WHEN`、类型转换、日期时间处理、字符串处理、CTE、子查询、`UNION` / `UNION ALL` 等
- 支持聚合、过滤、排序、投影、关联等基础 SQL 能力
- 支持不同数据源的方言差异识别、适配、重写或明确失败
- 支持统一 SQL 到目标数据源执行语义的适配
- 支持对不兼容语法给出明确校验或转换提示

业务要求：

- 平台不要求用户分别维护不同数据库方言版本的服务定义
- 平台不得将复杂表达式能力弱化为仅支持基础查询表达式
- 平台应尽量屏蔽底层数据库语法差异
- 对无法兼容的表达式、函数或语法，系统必须在保存、预览执行或发布阶段明确失败原因

### 9.9 批量查询

系统必须支持批量查询能力。

功能要求：

- 支持一次请求中提交多组查询条件
- 支持系统批量执行查询
- 支持按统一格式返回批量结果
- 支持在批量场景下识别单条结果与输入条件的对应关系
- 支持对批量规模进行控制

业务要求：

- 批量查询应减少调用方的多次请求成本
- 批量查询结果应便于调用方进行映射和处理
- 系统应能够限制单次批量请求规模，避免单次请求占用过多资源

### 9.10 查询缓存

系统必须支持查询缓存能力。

功能要求：

- 支持对查询结果进行缓存
- 支持重复查询命中缓存
- 支持缓存失效
- 支持按数据服务维度控制是否启用缓存
- 支持按服务配置缓存时间或失效策略
- 支持通过服务标识、服务版本、调用参数及必要的关键调用上下文字段形成缓存键
- 支持在响应结果中标识是否命中缓存
- 支持因服务新版本发布而使旧版本缓存失效
- 支持因服务停用而使对应缓存失效
- 支持因缓存策略变更而使相关缓存失效
- 支持因显式清理操作而使缓存失效
- 支持在关键调用上下文变化时隔离缓存

业务要求：

- 缓存用于提高查询性能
- 缓存不能导致错误结果长期返回
- 缓存不得跨租户或跨关键上下文错误复用
- 对时效性要求高的数据服务应支持关闭缓存或缩短缓存时间

### 9.11 前端配置界面

系统必须提供前端配置管理能力。

功能要求：

- 支持数据源连接配置界面
- 支持数据服务配置界面
- 支持 SQL 编辑界面
- 支持 SQL 解析结果展示界面
- 支持 SQL 校验结果展示界面
- 支持联邦查询计划或执行说明展示界面
- 支持缓存策略配置界面
- 支持服务发布与停用操作
- 支持自助式服务创建与维护操作
- 支持版本信息展示
- 支持关键审计信息展示

业务要求：

- 管理员可通过界面完成配置，不依赖直接改代码
- 具备相应权限的用户可在界面完成服务维护、校验和发布
- 界面不得要求用户手工维护目标库、来源、字段或参数表单

### 9.12 平台化能力

系统必须具备自助式 SQL 数据服务平台能力。

功能要求：

- 支持通过平台界面自助创建数据服务
- 支持通过平台界面自助维护简单 SQL 与联邦 SQL
- 支持通过平台界面完成保存、校验、发布、停用
- 支持服务版本管理
- 支持执行结果、校验结果和诊断信息展示
- 支持数据服务的规范化沉淀与复用

业务要求：

- 平台应尽量减少单服务单开发的建设模式
- 平台应支持规范化、标准化地沉淀数据服务

### 9.13 权限与审计管理

系统必须支持平台权限与审计能力。

功能要求：

- 支持区分平台管理员、数据服务开发人员、调用方等角色的权限范围
- 支持控制谁可以查看、编辑、发布、停用数据服务
- 支持控制谁可以查看连接配置、测试连接、执行预览验证
- 支持对 SQL 预览执行进行独立权限控制
- 支持对敏感信息进行脱敏展示
- 支持记录保存、发布、停用、测试连接、执行验证、SQL 预览执行等关键操作日志
- 支持按服务、用户、时间等维度查询审计记录
- 支持在审计记录中保留租户上下文摘要或等价隔离信息

业务要求：

- 权限控制必须覆盖配置、发布、调用、预览执行和查看诊断信息等关键操作
- 启用租户隔离的服务在调用上下文缺失租户标识或发生租户越权时，系统必须明确失败
- 审计记录应满足问题追踪和责任定位需要

### 9.14 服务版本与发布管理

系统必须支持服务版本与发布管理能力。

功能要求：

- 支持对数据服务进行版本化管理
- 支持记录每次发布对应的 SQL 原文、来源快照、参数快照、字段快照、校验快照和执行计划快照
- 支持查看当前生效版本和历史版本信息
- 支持停用已发布服务
- 支持将发布行为纳入审计记录

业务要求：

- 调用方应调用到明确、可追溯的服务版本
- 发布后的服务版本应与草稿编辑状态相互隔离
- SQL 预览执行结果不形成正式服务版本，仅保留必要的诊断信息和审计记录
- 版本管理应支持问题回溯、变更审计和验收确认

## 10. 非功能需求

### 10.1 性能需求

- 高频查询场景应支持通过缓存提升响应效率
- 批量查询应优于多次单条请求的总体成本
- 系统应尽量减少重复建立数据库连接的开销
- 联邦 SQL 执行应尽量减少跨源数据搬运
- 系统应支持通过优化降低联邦查询成本
- 系统在普通单台服务器配置下应可稳定运行，基线资源按 4 核 CPU、16G 内存考虑
- 系统设计不得默认依赖大内存机器或分布式扩容才能避免内存溢出
- 对大结果集、跨源 Join、批量查询和联邦补算场景，系统必须提供资源保护机制，避免单次请求导致进程内存耗尽
- 系统应支持通过限流、受控并发、中间结果落盘、结果集上限、超时控制等方式保障单机运行稳定性
- 系统应支持配置单次查询结果上限、批量查询规模上限和执行超时阈值

### 10.2 可用性需求

- 数据服务发布后应可稳定对外提供访问
- 数据源不可用时系统应返回明确错误
- 配置错误时系统应能提示配置问题
- SQL 校验失败时系统应返回明确原因
- 联邦查询执行失败时系统应能定位到来源、阶段或规则问题
- 在单机资源不足、结果集过大或执行超出资源阈值时，系统应优先进行受控失败，而不是出现进程崩溃或内存溢出
- 受控失败时应返回明确的错误类别和原因说明

### 10.3 可维护性需求

- 连接配置、服务定义、SQL 解析、发布快照和运行时执行应解耦
- 新增数据服务应尽量通过配置完成
- 新增数据库类型时应具备扩展空间
- SQL 解析、优化、执行应分层设计
- 服务定义、版本、发布记录和审计记录应具备可追溯性

### 10.4 安全性需求

- 数据库连接凭据必须安全存储
- 查询执行过程必须防止 SQL 注入
- 敏感配置展示时应做必要保护
- SQL 执行过程必须受系统统一控制，不允许绕过平台直接拼接危险语句执行
- 平台必须仅允许执行只读查询，不允许执行写入语句、DDL、存储过程调用或多语句混合执行
- 所有调用参数必须采用参数化绑定方式，不得直接拼接到 SQL 文本中执行
- SQL 预览执行必须遵守与正式查询一致的只读、参数化、权限控制和资源保护要求
- 多租户相关上下文字段必须由系统按调用上下文传递和校验，不得通过 SQL 文本拼接方式注入执行语义
- 缓存不得因租户上下文隔离缺失而造成跨租户数据泄露
- 平台应对危险语句、危险函数或不允许的语法进行校验拦截

### 10.5 可观测性需求

- 系统应记录服务调用日志
- 系统应记录配置变更日志
- 查询异常应便于排查定位
- 系统应记录联邦查询计划、优化和执行的关键诊断信息
- 系统应能够区分 SQL 预览执行、正式服务调用和发布校验等不同事件类型
- 系统应能够区分缓存命中、缓存失效原因、校验失败、数据源失败、资源保护触发等典型事件

## 11. 业务规则

- 一个连接配置可被多个数据服务复用
- 一个数据服务必须维护且只维护一条 SQL
- 一个数据服务可以是简单 SQL，也可以是联邦 SQL
- 数据服务必须先发布再使用
- 查询 SQL 必须通过平台配置维护
- 来源、参数和字段必须由 SQL 自动解析生成
- 查询缓存仅作用于查询结果，不改变业务数据本身
- SQL 的解析、优化、校验和执行必须纳入平台统一管理
- SQL 只能定义只读查询逻辑，不能执行写入类或副作用类操作
- SQL 预览执行不等同于服务发布，不产生正式可调用版本
- 常见数据库之间的异构联邦查询属于正式支持范围
- 复杂表达式与 SQL 方言兼容能力必须在保存、预览执行、发布和运行阶段保持一致的约束口径
- 多租户能力当前通过调用上下文和元数据预留表达，不要求当前所有元数据表立即强制增加 tenant_id 字段
- 查询缓存命中必须同时满足服务版本、请求参数和关键调用上下文一致
- 服务调用必须基于已定义参数模板进行参数化执行
- 发布后的服务版本应作为可追溯调用基线
- 运行时必须只依赖已发布版本快照

## 12. 约束与边界

### 12.1 范围内

- 数据查询服务
- 连接配置管理
- SQL-first 服务管理
- 简单 SQL 与联邦 SQL 管理
- 联邦查询
- 联邦查询优化
- SQL 方言兼容
- 批量查询
- 查询缓存
- 前端配置界面
- 服务版本管理与发布管理
- 权限控制与审计能力
- 自助式 SQL 数据服务平台能力

### 12.2 范围外

- 数据写入接口
- 工作流审批
- 数据清洗与数据治理流程
- 数据同步链路建设
- 报表分析和 BI 展示
- 存储过程编排能力
- 通用离线计算平台能力
- 旧模型兼容与迁移

## 13. 验收标准

### 13.1 功能验收

- 能配置至少一种 Oracle 数据源并成功查询
- 能配置至少一种 MySQL 数据源并成功查询
- 能配置至少一种 PostgreSQL 数据源并成功查询
- 能基于统一 API 成功调用已发布数据服务
- 能完成至少一个简单 SQL 场景
- 能完成至少一个同构联邦 SQL 场景
- 能完成至少一个异构联邦 SQL 场景
- 能完成至少一个包含复杂表达式和方言适配的 SQL 场景
- 能完成至少一个 SQL 预览执行场景并返回预览结果与诊断信息
- 能完成至少一个带租户调用上下文的服务调用场景
- 能完成至少一个批量查询场景
- 能在重复查询场景下命中缓存
- 能验证在发布新版本、停用服务或调整缓存策略后缓存按预期失效
- 能通过前端界面完成 SQL-first 数据服务配置和发布
- 能体现服务草稿、发布、停用等基本状态流转
- 能在保存时自动解析来源、参数和字段
- 能在发布时生成可追溯版本快照
- 能展示校验结果、执行计划或关键诊断信息
- 能体现权限控制和关键操作审计能力

### 13.2 结果验收

- 调用方能够通过统一方式获取查询结果
- 调用方不需要关注底层数据库差异
- 管理员能够通过配置完成服务维护
- 系统能够明确反馈连接失败、配置错误、查询失败等异常情况
- 系统在结果集过大、批量规模超限、执行超时或资源受限时，能够返回受控错误而非进程崩溃
- 平台能够支撑 SQL-first 自助式数据服务建设

### 13.3 评审关注点

- SQL-first 范围是否清晰且被各方接受
- 统一 API、服务定义、SQL 语法、缓存、权限和审计的范围是否完整
- 只读边界、参数化要求和安全限制是否明确
- 保存解析、发布校验、运行快照执行的闭环是否明确
- 单机部署、资源保护和受控失败要求是否满足建设目标
- 验收标准是否能够支持后续测试设计和项目验收

## 14. 验收指标与测试口径

### 14.1 总体原则

- 本章节用于补充功能验收和结果验收的测试口径，作为测试设计、联调验证和项目验收的依据
- 本章节优先定义“如何验证”，不强制规定具体实现方案
- 若后续测试方案与本章节存在冲突，应以本章节为准，除非评审明确调整
- 本章节中的“建议值”可在项目评审后固化为测试基线；未固化前，测试应至少覆盖相应类别场景

### 14.2 测试环境口径

- 单机部署验收应以普通单台服务器环境为基础，推荐基线为 4 核 CPU、16G 内存
- 测试环境应至少包含 Oracle、MySQL、PostgreSQL 三类数据源中的可用实例
- 联邦查询测试应覆盖同构数据源场景和异构数据源场景
- 批量查询、缓存、权限、审计、发布等能力应在与真实部署方式一致的环境中验证

### 14.3 功能测试口径

#### 14.3.1 数据源连接管理

- 应验证新增、编辑、启用、停用、测试连接功能可正常使用
- 应验证连接信息对非授权用户以脱敏方式展示
- 应验证连接变更产生审计记录

#### 14.3.2 数据服务配置与发布

- 应验证服务可从草稿态进入已发布态，并可从已发布态进入已停用态
- 应验证未发布服务不可被统一 API 调用
- 应验证已发布服务可被统一 API 正常调用
- 应验证保存时自动生成来源快照、参数快照和字段快照
- 应验证发布后形成可追溯版本快照

#### 14.3.3 SQL 解析与校验

- 应验证简单 SQL 必须写数据库内部全限定名
- 应验证联邦 SQL 必须写连接编码加全限定名
- 应验证参数模板可被正确解析
- 应验证不符合语法约束的 SQL 保存失败或发布失败
- 应验证只读限制、对象存在性和能力边界校验有效
- 应验证复杂表达式、方言差异表达式在支持范围内可被正确解析、校验或明确失败

#### 14.3.4 统一查询 API

- 应验证不同数据服务通过统一的调用方式访问
- 应验证单次查询与批量查询使用统一接口规范或统一协议风格
- 应验证返回结构中包含结果数据、执行状态、错误信息和元信息
- 应验证错误返回能够区分参数错误、配置错误、数据源错误、校验错误、执行错误和资源保护错误

#### 14.3.5 联邦查询

- 应验证至少一个同构联邦 SQL 场景和至少一个异构联邦 SQL 场景
- 应验证联邦 SQL 可完成语法校验、来源解析、发布校验和执行
- 应验证异构联邦 SQL 在保存、预览、发布和运行阶段使用一致的能力边界
- 应验证联邦 SQL 可生成执行计划并展示关键诊断信息
- 应验证数据源能力不足时系统明确失败

#### 14.3.6 SQL 预览执行

- 应验证 SQL 预览执行可基于当前草稿 SQL、参数和连接或联邦解析结果返回预览结果
- 应验证 SQL 预览执行受权限控制、只读限制、审计记录、结果集上限、超时和资源保护约束
- 应验证 SQL 预览执行不形成正式发布版本

#### 14.3.7 缓存与批量查询

- 应验证重复请求可命中缓存，且响应中能识别缓存命中状态
- 应验证不同参数、不同服务版本和不同关键调用上下文形成不同缓存键
- 应验证服务版本变化、策略变化、显式清理和调用上下文变化可触发缓存失效或缓存隔离
- 应验证批量查询结果能够与输入条件建立对应关系
- 应验证批量规模超出阈值时触发受控失败或明确限制提示

#### 14.3.8 权限与审计

- 应验证不同角色拥有不同的查看、编辑、发布、停用、测试连接和预览执行权限
- 应验证带租户调用上下文的权限与审计行为正确
- 应验证非授权用户无法查看敏感配置信息明文
- 应验证保存、发布、停用、测试连接、预览执行等关键操作产生审计记录
- 应验证审计记录至少支持按服务、用户、时间维度检索

### 14.4 非功能测试口径

#### 14.4.1 性能与资源保护

- 应验证在单机基线资源下，系统能够稳定完成单次查询、批量查询和联邦查询场景
- 应验证系统具备结果集上限、批量规模上限、执行超时、受控并发等资源保护能力
- 应验证大结果集、跨源 Join、联邦补算等场景不会直接导致进程崩溃或内存溢出
- 应验证资源保护触发后返回明确错误，而不是无响应或异常退出

#### 14.4.2 可用性与可观测性

- 应验证数据源不可用时，系统返回明确错误信息
- 应验证配置错误、校验失败、执行失败时，可定位问题类别和关键阶段
- 应验证日志中能区分缓存命中、校验失败、数据源失败、资源保护触发等事件
- 应验证联邦查询计划、优化说明和关键执行诊断信息可查看

#### 14.4.3 安全性

- 应验证平台仅允许执行只读查询，不允许执行写入、DDL、存储过程调用或多语句混合执行
- 应验证调用参数通过参数化方式传入，恶意输入不会被直接拼接执行
- 应验证危险语句或不允许语法在校验或执行前被拦截
- 应验证敏感配置在展示、日志和审计中不会以不受控方式泄露

### 14.5 建议量化指标

以下指标作为建议测试基线，最终可在详细设计或测试方案中固化：

- 单次查询结果上限：应支持配置，建议默认不超过 10000 行
- 批量查询规模上限：应支持配置，建议默认不超过 100 组条件
- 单次查询超时阈值：应支持配置，建议默认不超过 30 秒
- 联邦查询超时阈值：应支持配置，建议默认不超过 60 秒
- 审计日志保留周期：应支持配置，建议不少于 180 天
- 缓存时间：应支持按服务配置，建议默认按分钟级或小时级设置，不得写死为全局固定值

说明：

- 上述建议值用于统一测试口径，不表示必须采用该默认值
- 若项目评审确认其他阈值，应以评审确认结果替换本节建议值
- 若某项指标因业务场景特殊而不同，应在对应服务设计中单独说明

### 14.6 验收结论判定口径

- 当强制性功能项全部通过，且不存在阻断上线的安全、稳定性、权限或数据正确性问题时，可判定功能验收通过
- 当非功能测试中不存在进程崩溃、内存溢出、权限失控、敏感信息泄露等重大问题时，可判定非功能验收通过
- 当发现问题但不影响主流程、可控且有明确整改计划时，可列为遗留问题进入整改跟踪
- 当存在 SQL-first 闭环不成立、核心场景未覆盖、关键能力缺失或重大安全稳定性缺陷时，不应判定验收通过
