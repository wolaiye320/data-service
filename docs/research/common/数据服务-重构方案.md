# 数据服务-重构方案

## 1. 背景与目标

### 1.1 背景

当前后端工程采用 `data-service-app`、`data-service-interfaces`、`data-service-application`、`data-service-domain`、`data-service-infrastructure`、`data-service-federation`、`data-service-common` 的多模块结构。结合现有代码与文档现状，存在以下问题：

| 问题 | 现状分析 | 影响 |
| --- | --- | --- |
| 模块拆分过细 | 根 `pom.xml` 仍将 `interfaces/application/domain/infrastructure/federation` 作为独立 Maven 子模块管理 | 构建链路长，依赖关系复杂，日常开发与重构成本高 |
| 空包与轻量包较多 | `application` 下 `assembler/command/model/query` 等目录存在空目录；`domain` 下 `enums/event` 等目录存在空目录 | 目录层次与实际代码规模不匹配，增加理解负担 |
| 第二阶段能力已深度进入主链路 | `data-service-application` 已直接依赖 `data-service-federation`，`data-service-app` 也直接聚合 `federation` | 文档中的“第二阶段再引入 federation”与当前代码状态不完全一致 |
| 架构文档与实际工程绑定过深 | `docs/research/common/工程架构说明.md` 多处明确列出 5 个独立模块与目录树 | 若代码合并而文档不改，会出现文档失真 |
| 回归入口分散 | 现有测试报告中大量使用 `-pl data-service-application,data-service-federation,data-service-infrastructure` 等按模块执行命令 | 模块收敛后，测试命令、覆盖口径、报告描述都要同步调整 |

### 1.2 目标

本次重构的目标不是改变业务边界，而是把 `data-service-interfaces`、`data-service-application`、`data-service-domain`、`data-service-infrastructure`、`data-service-federation` 合并为**一个后端业务模块**，同时把原先偏“历史分层”的包组织改成更直接的业务域组织，保留：

| 保留模块 | 定位 |
| --- | --- |
| `data-service-app` | Spring Boot 启动入口与运行装配 |
| `data-service-common` | 公共异常、上下文、常量、工具 |
| `data-service-core`（建议新模块名） | 原 5 个业务模块合并后的统一业务模块，内部按业务域组织代码 |

> 若团队不希望引入新模块名，也可使用 `data-service-backend` 或 `data-service-server`。但建议避免继续使用 `data-service-application` 作为合并后总模块名，否则容易与旧分层语义混淆。

### 1.3 重构原则

| 原则 | 说明 |
| --- | --- |
| 不保留历史性分层壳 | 不再继续保留 `interfaces/application/domain/infrastructure` 这种为分层而分层的包骨架 |
| 按业务域收敛代码 | 以数据源、服务定义、查询执行、联邦、审计、安全等业务域为主组织代码 |
| 先改构建，再搬代码 | 先稳定 Maven 依赖与扫描配置，再执行源码迁移，避免大面积中间态不可编译 |
| 文档与代码同时收敛 | `工程架构说明.md`、相关测试报告、后续设计文档必须同步反映新结构 |
| 回归以真实链路为准 | Repository、数据源连接、联邦执行、Controller 链路都要跑真实回归，不能只做编译通过 |
| 不做顺手重构 | 本次只处理模块合并与包结构收敛，不额外改业务协议、数据库模型、前端接口 |

## 2. 现状分析

### 2.1 当前工程结构

| 模块 | 当前职责 | 代码现状 |
| --- | --- | --- |
| `data-service-app` | 启动入口、自动装配 | 通过 `@SpringBootApplication(scanBasePackages = "cn.dtkeys.dataservice")` 扫描全包；MyBatis 扫描固定在 `cn.dtkeys.dataservice.infrastructure.repository` |
| `data-service-interfaces` | Controller、DTO、响应模型 | 有实际代码，非空模块 |
| `data-service-application` | 用例编排、应用服务 | 有实际代码，但部分预留目录为空 |
| `data-service-domain` | 领域模型、运行时模型 | 有实际代码，但 `enums/event` 等目录为空 |
| `data-service-infrastructure` | Repository、数据源、执行器、缓存、审计、安全 | 代码量较大，是主要依赖承载模块 |
| `data-service-federation` | 联邦 SQL 解析、优化、执行编排 | 已有正式代码和测试，不再只是预留扩展位 |
| `data-service-common` | 公共基础能力 | 可继续独立保留 |

### 2.2 当前 Maven 依赖链

| 位置 | 当前依赖关系 | 说明 |
| --- | --- | --- |
| 根 `pom.xml` | 同时声明 7 个子模块 | 构建入口复杂 |
| `data-service-app` | 依赖 `application/interfaces/infrastructure/federation/common` | 启动模块需同时聚合多个业务子模块 |
| `data-service-application` | 依赖 `domain/infrastructure/federation/common` | 应用层已跨多个模块编排 |
| `data-service-interfaces` | 依赖 `application/common` | 接口层并未独立到足以单独发布 |
| `data-service-federation` | 依赖 `domain/infrastructure/common` | 联邦能力与基础设施已强耦合 |

### 2.3 当前文档不一致点

| 文档位置 | 当前表述 | 与目标结构的冲突 |
| --- | --- | --- |
| `docs/research/common/工程架构说明.md` 第 5 章、第 12 章 | 明确要求 `interfaces/application/domain/infrastructure/federation` 为独立模块 | 需改为“单业务模块 + 业务域包结构” |
| `docs/research/common/工程架构说明.md` 多处目录树 | 分别展示 5 个 Maven 模块目录 | 需改为 `data-service-core` 下的业务域目录树 |
| `docs/research/common/过程文档/数据服务-后端集成测试报告-2026-04-04.md` | 测试命令依赖旧模块名 | 需追加说明该报告基于旧结构，或补新报告 |
| `docs/research/common/过程文档/数据服务-性能与资源保护验证记录-2026-04-04.md` | 覆盖模块包含 `data-service-federation` 等旧模块 | 需在重构后补一版新的回归记录 |

## 3. 目标工程方案

### 3.1 目标模块结构

| 模块名 | 是否保留 | 目标职责 |
| --- | --- | --- |
| `data-service-app` | 保留 | 启动、自动装配、运行配置 |
| `data-service-common` | 保留 | 通用基础能力 |
| `data-service-core` | 新增 | 承载 Web 接口、数据源管理、服务定义、查询执行、联邦、审计、安全等核心能力 |
| `data-service-interfaces` | 删除 | 并入 `data-service-core` |
| `data-service-application` | 删除 | 并入 `data-service-core` |
| `data-service-domain` | 删除 | 并入 `data-service-core` |
| `data-service-infrastructure` | 删除 | 并入 `data-service-core` |
| `data-service-federation` | 删除 | 并入 `data-service-core` |

### 3.2 目标包结构

合并后不再保留完整的历史分层包骨架，改为“业务域优先 + 少量技术基础包”：

| 包路径 | 说明 |
| --- | --- |
| `cn.dtkeys.dataservice.config` | Spring 配置、属性绑定、装配 |
| `cn.dtkeys.dataservice.web` | Controller、DTO、请求响应对象、全局异常处理 |
| `cn.dtkeys.dataservice.datasource` | 数据源连接管理、catalog、连接校验 |
| `cn.dtkeys.dataservice.service` | 服务定义、发布、版本、参数、字段、缓存策略 |
| `cn.dtkeys.dataservice.query` | 统一查询入口、执行编排、只读校验、结果映射 |
| `cn.dtkeys.dataservice.federation` | 联邦 SQL 解析、校验、优化、执行、诊断 |
| `cn.dtkeys.dataservice.audit` | 审计日志、操作记录、查询审计 |
| `cn.dtkeys.dataservice.security` | 权限、拦截器、角色、访问控制 |
| `cn.dtkeys.dataservice.repository` | MyBatis Repository |
| `cn.dtkeys.dataservice.common` | 公共异常、上下文、常量、工具、公共模型 |

说明：

| 结论 | 说明 |
| --- | --- |
| 不保留 `application/domain/interfaces/infrastructure` 包壳 | 这些名称更像历史分层术语，不利于继续降复杂度 |
| 保留 `federation` | 它是明确独立的业务能力域，不是单纯技术分层 |
| 保留 `repository` / `web` / `config` / `common` | 这些属于必要的技术边界，且语义直接 |

### 3.3 目标依赖关系

| 模块 | 目标依赖 |
| --- | --- |
| `data-service-app` | `data-service-core`、`data-service-common` |
| `data-service-core` | `data-service-common` |

这样可以把跨模块依赖收敛为单模块内的业务域协作，避免把旧的复杂分层从 Maven 层平移到包层。

## 5. 代码重构方案

### 5.1 总体策略

| 阶段 | 目标 | 输出 |
| --- | --- | --- |
| 阶段一 | 建立新模块骨架并接管依赖 | `data-service-core` 新模块、根 `pom` 更新、`app` 依赖更新 |
| 阶段二 | 迁移源码与资源 | 5 个旧模块源码、测试、资源迁入 `core` |
| 阶段三 | 清理旧模块与引用 | 删除旧模块目录、修正文档与脚本、清理 CI/命令 |
| 阶段四 | 完整回归 | 编译、单测、集成测试、容器测试、API 回归 |

### 5.2 具体改造步骤

#### 步骤 1：新增统一业务模块

| 动作 | 说明 |
| --- | --- |
| 新建 `data-service-core/pom.xml` | 以 jar 模块承载原 5 个模块全部依赖 |
| 收敛依赖 | 合并 `spring-boot-starter-web`、`spring-boot-starter`、`starter-jdbc`、MyBatis、Flyway、validation、testcontainers 等依赖 |
| 保持资源目录 | `src/main/resources/db/migration/` 迁入 `core` |

#### 步骤 2：迁移主代码

| 来源模块 | 迁移内容 | 目标位置 |
| --- | --- | --- |
| `data-service-interfaces` | `src/main/java` | `data-service-core/src/main/java`，并重组到 `web` |
| `data-service-application` | `src/main/java` | `data-service-core/src/main/java`，并重组到 `service` / `query` |
| `data-service-domain` | `src/main/java` | `data-service-core/src/main/java`，并重组到 `service` / `query` / `datasource` 等业务域 |
| `data-service-infrastructure` | `src/main/java` + `src/main/resources` | `data-service-core/src/main/java` + `src/main/resources`，其中 Repository 收敛到 `repository` |
| `data-service-federation` | `src/main/java` | `data-service-core/src/main/java/federation` |

> 这一步不建议简单原样搬目录。应在迁移时同步把旧的 `interfaces/application/domain/infrastructure` 包重组为更直接的业务域包，否则只是把旧复杂度平移到单模块内。

#### 步骤 3：迁移测试代码

| 来源模块 | 迁移内容 | 风险点 |
| --- | --- | --- |
| `data-service-application/src/test` | 应用层单测 | 依赖路径变化后需确认 surefire 扫描正常 |
| `data-service-infrastructure/src/test` | Repository 集成测试、容器测试、缓存测试 | 真实数据库与 Testcontainers 依赖需在 `core` 保留 |
| `data-service-federation/src/test` | 联邦链路单测 | 与 `infrastructure` 合并后要避免重复测试资源冲突 |
| `data-service-app/src/test` | Spring Boot 集成测试保留在 app | 需要把依赖改成 `data-service-core` |

#### 步骤 4：更新启动模块

| 文件/位置 | 目标修改 |
| --- | --- |
| `data-service-app/pom.xml` | 删除对 `application/interfaces/infrastructure/federation` 的依赖，改为仅依赖 `data-service-core` 与 `data-service-common` |
| `data-service-app` 下扫描与自动装配配置 | 结合新包结构，把 `@MapperScan`、组件扫描、配置类落位统一对齐到 `repository`、`config`、`web` 等新包 |
| `DataServiceApplication.java` | `scanBasePackages = "cn.dtkeys.dataservice"` 可保持不变 |

#### 步骤 5：更新聚合构建

| 文件 | 目标修改 |
| --- | --- |
| 根 `pom.xml` | 删除 5 个旧模块，加入 `data-service-core` |
| 可能存在的脚本 / CI 配置 | 把 `-pl data-service-application,data-service-federation,...` 改为 `-pl data-service-core,data-service-app` 或更精确的新命令 |

#### 步骤 6：删除旧模块目录

| 条件 | 要求 |
| --- | --- |
| 新模块编译通过 | 才能删除旧目录 |
| 所有测试迁移完成 | 不允许边删边漏测试 |
| 文档已切换到新结构 | 避免仓库内主文档继续引用旧目录 |

### 5.3 推荐的实际落地顺序

| 顺序 | 操作 | 目的 |
| --- | --- | --- |
| 1 | 新建 `data-service-core` 并写好 `pom.xml` | 先给迁移落点 |
| 2 | 先定义目标业务域包结构与迁移映射表 | 避免搬完代码后仍是一套旧分层壳 |
| 3 | 迁移 `datasource`、`repository`、`config` 相关代码 | 先稳定底层支撑能力 |
| 4 | 迁移 `query`、`service`、`audit`、`security` | 收敛主业务链路 |
| 5 | 迁移 `federation` | 独立能力域单独收口 |
| 6 | 迁移 `web` | 最上层最后调整，便于一次性改 DTO 与控制器引用 |
| 7 | 调整 `data-service-app` 依赖与扫描配置 | 接到新模块 |
| 8 | 跑编译与测试 | 验证中间态 |
| 9 | 删除旧模块与更新文档 | 收尾清理 |

### 5.4 重点风险与处理

| 风险 | 说明 | 处理方案 |
| --- | --- | --- |
| 依赖遗漏 | 原 5 个模块测试依赖和运行依赖分散在不同 `pom.xml` | 合并 `pom` 时逐项核对，先保守全量带上，再二次精简 |
| 测试资源冲突 | 多模块合并后 `src/test/resources` 可能重名 | 先扫描测试资源文件名，必要时合并或重命名 |
| 构建脚本失效 | 旧 `mvn -pl xxx` 命令全部失效 | 同步更新测试报告、README、CI 配置 |
| 文档失真 | 架构文档仍写旧模块 | 文档修改必须纳入同一次重构范围 |
| 第二阶段能力误删 | 误以为 `federation` 只是预留 | 合并的是模块，不是删除联邦能力，相关代码与测试必须完整迁入 |
| 历史分层被原样保留 | 只是把 `interfaces/application/domain/infrastructure` 从模块变成包，复杂度并未真正下降 | 先产出包迁移映射表，再按业务域重组代码 |

## 6. 回归测试方案

### 6.1 最低回归范围

| 层级 | 必测内容 | 说明 |
| --- | --- | --- |
| 编译验证 | 全量 `mvn test` 或至少受影响模块测试 | 先保证构建链可用 |
| Repository 集成测试 | 元数据 Repository、真实 Schema 映射、动态 SQL | 符合测试规范中“Repository 必须真实数据库验证” |
| 数据源连接测试 | PostgreSQL / MySQL / Oracle 容器连接验证 | 合并模块后必须确认驱动与容器依赖未丢失 |
| 应用层测试 | 连接管理、服务定义管理、联邦元数据管理 | 验证编排层未被模块合并破坏 |
| 联邦能力测试 | Parser / Validator / Planner / Optimizer / Executor | 确认 `federation` 并入后仍能独立回归 |
| Spring Boot 集成测试 | QueryController、管理接口、审计与权限链路 | 验证 `app -> core` 装配无问题 |

### 6.2 建议执行命令

> 以下是重构完成后的建议口径，实际以最终模块名为准。假设新模块名为 `data-service-core`。

| 目的 | 建议命令 | 说明 |
| --- | --- | --- |
| 核心模块单测/集成测试 | `mvn -pl data-service-core -am test` | 覆盖原 `interfaces/application/domain/infrastructure/federation` 测试 |

## 8. 结论

| 结论 | 说明 |
| --- | --- |
| 可以合并 | 从现有代码组织看，5 个业务模块本质上已是强协作关系，合并成单业务模块可显著降低构建与维护成本 |
| 不保留历史分层包壳 | 不建议继续保留 `interfaces/application/domain/infrastructure` 作为主包结构，否则只是把 Maven 模块复杂度平移到包层 |
| 按业务域组织更合适 | 建议以 `datasource/service/query/federation/audit/security/repository/web/config` 为主包结构，代码位置更直观 |
| 文档必须同步改 | 尤其是 `工程架构说明.md`，它现在是旧结构的主依据，不同步修改会直接误导后续开发 |
| 测试不能只跑编译 | 本次重构触及 Maven 依赖、资源路径、测试入口、Spring 装配，必须做真实回归 |
