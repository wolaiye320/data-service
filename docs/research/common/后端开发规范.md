# 后端开发规范

**版本**：1.0
**定位**：项目后端编码、配置、注释与 Java 21 特性使用的主规范文档
**适用范围**：各后端业务模块及其测试代码

---

## 1. 文档定位与使用方式

### 1.1 文档定位

本文档用于回答以下问题：

- Spring Boot 配置类应该如何组织与绑定
- Bean 应如何注入，哪些注入方式不推荐
- Controller / Service / Repository 的公共方法应满足什么最小可维护性要求
- Java 21 特性在本项目中何时使用、何时不应滥用
- 后端代码变更前后应完成哪些最低自检

### 1.2 使用原则

- 技术栈是否允许，优先看《技术选型说明书》
- 模块边界、目录落位、分层职责，优先看《工程架构说明》
- 数据库命名、MyBatis、迁移、Repository 映射，优先看《数据库设计规约》
- 测试类型与最低覆盖要求，优先看《测试规范》
- 本文档只承接“后端如何写”的编码约束，不重复展开架构、数据库与测试主规范

## 2. 配置与装配规范

### 2.1 配置文件组织

- 通用配置放在 `application.yml` 或 `application.yaml`
- 环境差异放在 `application-{profile}.yml`
- 敏感信息通过环境变量或外部配置注入，禁止硬编码到代码或仓库配置文件

### 2.2 配置绑定

- 配置绑定优先使用 `@ConfigurationProperties`，避免在业务代码中散落 `@Value`
- 配置类按模块或子域组织到对应 `config/` 目录，不放入无关包路径
- 配置类应体现清晰语义，命名与配置前缀保持一致
- 复杂配置优先使用嵌套结构表达，不把多个无关配置揉成平铺字段

### 2.3 配置校验

- 配置类应配合 `@Validated` 做启动期参数校验
- 布尔开关、时间、阈值、容量等配置必须具备明确语义，避免难以理解的魔法值
- 需要默认值时，应显式声明默认行为，避免依赖隐式空值

## 3. 依赖注入规范

### 3.1 默认注入方式

- 默认使用构造器注入，保证依赖显式、对象状态完整、字段可保持 `final`
- 字段注入不作为正式业务代码默认写法
- 字段注入仅允许在测试代码或确有框架限制的场景谨慎使用

### 3.2 Bean 装配原则

- 复杂装配逻辑放在 `@Configuration` + `@Bean` 中，不把装配细节散落到业务类
- 多实现 Bean 需要显式区分时，使用清晰命名、`@Qualifier` 或等价方式
- 如出现循环依赖，应优先重构职责边界，而不是使用技巧性绕过

## 4. 后端公共代码规范

### 4.1 分层实现边界

- `api` 层负责协议、参数校验、响应组装，不直接承载复杂业务逻辑
- `service` 层负责业务编排、事务边界、跨仓储协同
- `repository` 层负责数据访问与映射，不承载页面流程逻辑
- 具体分层与目录落位以《工程架构说明》为准

### 4.2 命名与代码风格

- 类名使用 PascalCase，方法名与变量名使用 camelCase，常量使用全大写下划线分隔
- 包名、模块命名与代码落位继续以《工程架构说明》的包命名与目录组织规则为准
- 统一使用 4 个空格缩进，禁止使用 Tab
- 单行长度一般不超过 120 个字符；若因 URL、固定协议文本等确需超出，应保持可读性并避免无意义拆行
- 大括号默认使用同行起括号风格，避免额外换行制造视觉噪音
- 方法之间空一行；较长方法中的逻辑块之间按需空一行，帮助阅读边界清晰

### 4.3 JavaDoc 与注释

- Controller、Service、Repository 的公共方法应补齐最小必要 JavaDoc
- JavaDoc 至少说明方法职责；按需补充 `@param`、`@return`、`@throws`
- 编排型 Service、校验器、守卫、组装器、解析器等语义不直观的类，应补 1 段类级注释，说明职责边界与不负责的内容
- 超过 40 行且承担多个阶段职责的方法，应按“校验 / 编排 / 执行 / 组装 / 审计”等逻辑阶段补 2 到 5 处短注释，帮助读者快速定位流程边界
- 注释优先解释“为什么这样做”“保护了什么约束”“失败边界是什么”，不要逐行翻译代码表面动作
- 涉及权限、租户、缓存、资源保护、只读限制、联邦补算等高风险分支时，应明确写出该分支防止什么错误或绕过
- DTO、Entity、简单 CRUD、字段映射、自解释条件分支默认不写注释；若靠改进命名即可消除歧义，应先改命名而不是加注释
- 复杂私有方法或不直观的业务规则应补简洁注释
- `TODO` 仅用于明确、可执行、可追踪的待办事项；禁止把未完成设计、临时绕过或模糊提醒大量堆积在代码中
- 禁止用注释替代糟糕命名，也避免对自解释代码做重复注释

### 4.4 异常与边界处理

- 谨慎使用检查异常；业务代码默认优先使用语义清晰的运行时异常，避免把异常处理责任机械上抛
- 不得吞掉异常或丢失原始异常上下文
- 包装异常时必须保留异常链，便于定位根因
- 外部调用、参数边界、空结果、非法状态必须有明确处理逻辑
- 可预期业务异常与系统异常应在语义上区分清楚
- 涉及文件、流、连接等资源管理时，优先使用 try-with-resources，确保资源按作用域自动释放

### 4.5 集合、Stream 与并发

- 集合类型选择应服务于真实访问模式，不为“习惯”或“默认印象”盲选实现
- 随机访问频繁时优先 `ArrayList`；插入删除频繁时再评估 `LinkedList` 是否真的更合适
- 键值对存储优先 `HashMap`；明确需要按键排序时使用 `TreeMap`
- 在不损害可读性与可调试性的前提下，可优先使用 Stream API 表达集合变换逻辑；过长链式调用应拆分
- 并发场景优先考虑不可变对象、清晰的状态边界与线程安全集合，而不是先引入锁
- 需要共享可变状态时，再按需使用 `synchronized`、`ReentrantLock` 等同步机制，并说明临界区边界
- 并发集合优先评估 `ConcurrentHashMap`、`CopyOnWriteArrayList` 等现成实现是否满足场景
- 异步流程优先使用 `CompletableFuture` 组织编排；若引入异步后会削弱可观测性、事务一致性或错误处理，应先评估是否值得

## 5. Java 21 特性使用边界

### 5.1 Record

- 适用于不可变 DTO、配置快照、简单值对象
- 不应为了“新特性”而把需要复杂生命周期或框架代理的对象强行改成 Record

### 5.2 Text Blocks

- 多行 SQL、JSON、模板文本优先使用 Text Blocks 提高可读性
- Repository 或持久化相关复杂 SQL 可优先采用该写法

### 5.3 Virtual Threads

- 仅在明确高并发、阻塞型调用场景下按需使用
- 未经验证前，不作为普通业务代码的默认并发模型

### 5.4 Sealed Class

- 仅在类型层次需要明确受限、分支语义稳定时使用
- 若只是简单 DTO 承载，不应为追求“高级感”引入不必要层次结构

### 5.5 兼容性原则

- Java 21 特性应服务于可读性、可维护性与正确性
- 不引入与现有项目风格明显冲突的新范式

## 6. 后端改动自检清单

- 是否已确认技术栈与实现方式符合《技术选型说明书》
- 是否已确认类落位、模块边界、分层职责符合《工程架构说明》
- 是否涉及数据库映射、SQL、迁移，且已核对《数据库设计规约》
- 是否核对了自定义 SQL / MyBatis Mapper 中引用的所有字段在当前 Flyway schema 中真实存在
- 是否检查了本次变更影响的菜单页 / 聚合页是否依赖新增或修改的 Repository 查询
- 是否遵循当前文档中的命名、缩进、异常处理与集合并发使用约束
- 是否使用了 `@ConfigurationProperties` / `@Validated` 替代散落配置绑定
- 是否优先使用构造器注入
- 是否为新增公共方法补齐必要 JavaDoc
- 是否在复杂 SQL / JSON / 多行文本场景优先使用 Text Blocks
- 是否补齐与改动类型匹配的测试，并按《测试规范》完成验证
- 是否避免通过默认值、静默 catch、页面假数据等方式掩盖后端真实错误
