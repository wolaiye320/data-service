# 数据服务技术选型说明书

## 1. 文档目的

本文档基于《[数据服务需求规格书](/Volumes/osdisk/java_code/data-service/docs/research/common/数据服务需求规格书.md)》和《[数据服务架构与详细设计](/Volumes/osdisk/java_code/data-service/docs/research/common/数据服务架构与详细设计.md)》编写，用于明确数据服务系统的技术选型、适用范围、选型理由与不选项，作为后续开发、部署、测试和演进的统一依据。

## 2. 选型原则

- 优先使用当前项目规则已明确支持的技术栈
- 优先使用成熟、稳定、社区验证充分的主流方案
- 非必要不引入额外中间件和复杂基础设施
- 满足“配置驱动查询、异构数据库接入、前端可配置管理、本地缓存”的核心需求
- 采用分阶段、瀑布式实施方法
- 第一阶段优先交付基础能力，第二阶段再引入联邦 SQL 平台能力
- 第二阶段选型必须与第一阶段架构连续演进，避免推翻式重构

## 4. 分阶段技术选型策略

### 4.1 第一阶段：基础数据服务技术栈

目标：

- 快速交付可用的数据服务基础系统
- 打通异构数据库接入、配置管理、统一查询 API、缓存与前端配置界面

技术重点：

- Spring Boot 3.x
- MyBatis 注解式 Mapper
- `NamedParameterJdbcTemplate`
- HikariCP
- Flyway
- Spring Cache + Caffeine

### 4.2 第二阶段：联邦 SQL 平台技术栈

目标：

- 支持一个服务直接维护一条联邦 SQL
- 支持联邦 SQL 解析、校验、优化、执行
- 支持 Join Reorder、Filter Pushdown、Project Pushdown
- 支持 SQL 方言兼容和自助式平台能力

技术重点：

- Apache Calcite 负责联邦 SQL 解析、校验、逻辑计划和优化
- Spring Boot 继续作为应用承载框架
- JDBC / HikariCP 继续作为底层数据源访问能力
- 方言适配与执行计划落地由平台侧扩展实现

## 5. 后端技术选型

### 5.1 Java 21

选型结论：

- 后端统一使用 Java 21

选型理由：

- 与项目规范一致
- 语言特性现代，适合构建长期维护的企业级服务
- 支持 Record、Text Blocks、Pattern Matching 等能力，适合 DTO、SQL、配置类场景

适用范围：

- Controller
- Service
- Domain
- Repository
- Infrastructure

### 5.2 Spring Boot 3.x

选型结论：

- 后端基础框架采用 Spring Boot 3.x

选型理由：

- 适合快速构建标准 REST API
- 与 Java 21 兼容
- 对配置管理、依赖注入、事务、测试、监控支持成熟
- 与 Spring JDBC、MyBatis、Flyway、Testcontainers 集成成熟

适用范围：

- 应用启动
- 配置装配
- 事务管理
- API 暴露
- 测试支持

### 5.3 Spring Web MVC

选型结论：

- API 层采用 Spring MVC，而非 WebFlux

选型理由：

- 当前系统以数据库访问和配置管理为主，属于典型同步 I/O 场景
- 与 JDBC/MyBatis 技术栈天然匹配
- 开发和排障成本低

不选项：

- 不选 Spring WebFlux
  - 当前没有高并发流式响应或 Reactor 体系需求
  - 与 JDBC 阻塞模型不匹配

## 6. 数据存储与访问选型

### 6.1 系统元数据库采用 PostgreSQL

选型结论：

- 系统元数据默认落 PostgreSQL

选型理由：

- 事务能力稳定
- DDL/DML 能力完整，适合配置中心类表结构
- 与 Spring、Flyway、Testcontainers 集成成熟
- 当前测试规范也以 PostgreSQL 为主要验证基线

适用范围：

- `DS_CONNECTION`
- `DS_CATALOG`
- `DS`
- `DS_SOURCE`
- `DS_PARAM`
- `DS_FIELD`
- `DS_CACHE_POLICY`
- `DS_SQL_PLAN`
- `DS_SQL_VALIDATE_LOG`

### 6.2 元数据访问采用 MyBatis 注解式 Mapper

选型结论：

- 系统元数据表访问采用 MyBatis 注解方式

选型理由：

- 项目规则已明确禁止 XML Mapper
- 对配置表 CRUD、列表查询、简单关联查询足够直接
- SQL 显式，便于控制字段映射
- 适合元数据表这种结构清晰、语句相对稳定的场景

适用范围：

- 元数据 Repository
- 配置管理查询
- 发布校验读取

不选项：

- 不选 MyBatis XML Mapper
  - 项目规则明确禁止
- 不选 JPA / Hibernate
  - 当前表结构和 SQL 需要较强可控性
  - 元数据表访问更适合显式 SQL

### 6.3 第一阶段动态 SQL 执行采用 Spring JDBC `NamedParameterJdbcTemplate`

选型结论：

- 运行时配置化 SQL 不通过 MyBatis Mapper 承载，改用 Spring JDBC 的 `NamedParameterJdbcTemplate`

选型理由：

- 数据服务 SQL 来自配置表，属于运行时动态装载 SQL
- 需要命名参数绑定，避免字符串拼接风险
- 相比 MyBatis 注解式 Mapper，更适合执行数据库中存储的动态查询语句
- 相比直接使用 `JdbcTemplate`，命名参数可读性和安全性更好

适用范围：

- 第一阶段数据服务查询执行器
- 单次查询
- 批量查询
- 关联查询中的数据库侧执行部分

不选项：

- 不选把动态 SQL 硬塞进 MyBatis 注解
  - 不适合运行时配置 SQL
- 不选直接拼接字符串执行 SQL
  - 存在明显 SQL 注入风险

### 6.4 第二阶段联邦 SQL 规划与优化采用 Apache Calcite

选型结论：

- 第二阶段联邦 SQL 的解析、校验、逻辑计划生成与优化统一采用 Apache Calcite

选型理由：

- Calcite 适合做 SQL Parser、Validator、Relational Algebra Planner 和 Rule-based Optimizer
- 能支撑 Join Reorder、Filter Pushdown、Project Pushdown 等联邦查询优化需求
- 能作为统一 SQL 表达层，降低不同数据库方言差异带来的平台复杂度
- 更适合承接“一个服务直接维护一条联邦 SQL”和“自助式 SQL 数据服务平台”的目标

适用范围：

- 联邦 SQL 解析
- 联邦 SQL 语义校验
- 逻辑计划生成
- 联邦优化规则执行
- 数据源能力感知下的下推决策

平台落地方式：

- Calcite 作为规划层与优化层
- 平台基于 Calcite 产出逻辑计划、优化结果和下推决策
- JDBC 作为底层实际执行层，负责按拆分后的子计划访问各数据源
- HikariCP 负责各数据源连接池复用
- 平台自身负责方言适配、执行计划拆分、结果整合和诊断输出

不选项：

- 不选直接引入 Flink 作为执行引擎
  - 当前系统是 API 查询服务，不是流批计算平台
  - 引入 Flink 运行时会显著增加系统复杂度
- 不选仅靠手写联邦 SQL 解析器
  - 难以支撑复杂表达式、优化和平台化演进

### 6.5 数据库连接池采用 HikariCP

选型结论：

- 统一使用 HikariCP 管理业务数据库连接池

选型理由：

- Spring Boot 默认集成
- 性能稳定
- 配置简单
- 适合多数据源连接池复用场景

适用范围：

- 业务数据库连接
- 系统元数据库连接

## 7. 数据库迁移选型

### 7.1 Flyway

选型结论：

- 数据库迁移统一使用 Flyway

选型理由：

- 项目规则已明确采用 Flyway
- 版本化迁移清晰
- 与 Spring Boot 集成成熟
- 适合管理 `DS_*` 配置表持续演进

适用范围：

- 建表
- 加字段
- 加索引
- 初始化数据

不选项：

- 不选手工维护 DDL
  - 难以追踪和回放

## 8. 缓存选型

### 8.1 Spring Cache + Caffeine

选型结论：

- 本地缓存采用 Spring Cache 抽象层 + Caffeine 实现

选型理由：

- 需求与详细设计都明确当前阶段只做本地缓存
- Caffeine 轻量、成熟、性能好
- 支持 TTL、容量限制、命中统计
- 与 Spring Cache 集成简单，便于后续按服务维度管理缓存

适用范围：

- 数据服务查询结果缓存
- `serviceCode + version + paramHash` 维度缓存

不选项：

- 不选 Redis
  - 当前需求明确不做分布式缓存
  - 引入额外运维复杂度

## 9. 前端技术选型

### 9.1 TypeScript + React 19

选型结论：

- 前端采用 TypeScript + React 19

选型理由：

- 项目前端规范已明确 React 技术栈
- TypeScript 适合管理复杂配置表单和 DTO 类型
- React 适合构建数据源、服务配置、发布管理类后台界面

适用范围：

- 数据源配置界面
- 目标库配置界面
- 数据服务配置界面
- SQL 配置界面
- 联邦 SQL 编辑界面
- 联邦 SQL 校验结果界面
- 联邦查询计划展示界面
- 参数配置界面
- 返回字段配置界面
- 缓存策略配置界面

### 9.2 Ant Design 5

选型结论：

- UI 组件库采用 Ant Design 5

选型理由：

- 现有前端规范、UI 设计规范都围绕 Ant Design 展开
- 适合企业级后台管理系统
- Form、Table、Drawer、Modal、Tabs 等能力完整
- 能快速支撑配置型页面开发

适用范围：

- 表单
- 表格
- 抽屉
- 弹窗
- 消息反馈
- 页面布局

### 9.3 React Router 7 兼容模式

选型结论：

- 前端路由采用 React Router，并按现有前端规范开启 v7 兼容配置

选型理由：

- 现有前端规范已给出 React Router 使用方式
- 适合后台管理端多页面路由切换

### 9.4 Vite

选型结论：

- 前端构建工具采用 Vite

选型理由：

- React + TypeScript 项目构建简单
- 本地启动快
- 工程化配置成本低

不选项：

- 不选 Next.js
  - 当前是后台管理系统，不需要 SSR/SSG

## 10. 安全与日志选型

### 10.1 日志：SLF4J + Logback

选型结论：

- 日志框架采用 SLF4J + Logback

选型理由：

- Spring Boot 默认成熟方案
- 便于输出调用日志、配置变更日志、异常日志

### 10.2 安全实现

选型结论：

- 数据库连接凭据加密存储
- SQL 执行统一使用参数绑定
- 联邦 SQL 必须通过平台解析、校验和优化链路后执行

实现建议：

- 密码字段采用应用层加密后存储
- 敏感字段在接口返回与页面展示时脱敏

说明：

- 当前阶段不单独引入复杂权限引擎
- 若后续增加管理端登录鉴权，可在 Spring Security 基础上补充

## 11. 测试技术选型

### 11.1 后端测试

选型结论：

- JUnit 5
- AssertJ
- Mockito
- Spring Boot Test
- Testcontainers

选型理由：

- 与项目测试规范一致
- 适合单元、集成、API E2E 分层测试
- Testcontainers 适合真实数据库测试
- 第二阶段需补充联邦 SQL Parser、Planner、Optimizer、Dialect 相关测试

### 11.2 前端测试

选型结论：

- Playwright 用于页面级 E2E

选型理由：

- 适合覆盖后台配置页面的真实交互链路
- 可验证表单、列表、发布、反馈消息等真实操作

## 12. 选型与需求映射

| 需求 | 技术选型 |
| --- | --- |
| 支持不同类型数据库 | JDBC + 多驱动适配 |
| SQL 配置化 | 第一阶段 `NamedParameterJdbcTemplate` + 元数据配置表 |
| 数据库连接可配置 | Spring Boot + HikariCP + MyBatis |
| 一个连接访问多个目标库 | 多数据源连接管理组件 |
| 统一查询 API | Spring Web MVC |
| 联邦 SQL | Apache Calcite + 平台执行层 |
| 联邦查询优化 | Apache Calcite Rule Planner |
| SQL 方言兼容 | Calcite + 平台方言适配层 |
| 关联查询 | 第一阶段动态 SQL 执行器 + 服务端结果整合 |
| 批量查询 | Spring Boot 应用服务编排 |
| 查询缓存 | Spring Cache + Caffeine |
| 前端配置界面 | React + TypeScript + Ant Design |
| 测试规范落地 | JUnit 5 + Testcontainers + Playwright |

## 13. 当前阶段明确不选

- 不选 JPA / Hibernate 作为元数据主访问方案
- 不选 MyBatis XML Mapper
- 不选 Redis 作为当前阶段缓存
- 不选 WebFlux 作为 API 框架
- 不选 Next.js 作为前端框架
- 不选 Flink 作为当前阶段联邦查询执行引擎
- 不选 Elasticsearch、Kafka、工作流引擎等额外基础设施

## 14. 后续演进建议

- 第一阶段完成后，引入 Calcite 作为联邦 SQL 规划与优化核心
- 第二阶段优先落地联邦 SQL 解析、校验、计划生成与优化，不先引入分布式执行引擎
- 若异构数据库关联复杂度继续上升，可进一步增强数据源能力模型、规则优化和执行计划缓存
- 若缓存从本地扩展到分布式，再评估 Redis
- 若前端界面规模明显扩大，可补充 Zustand 或 React Query 一类状态管理/服务请求方案
- 若权限、审计、登录要求上升，可补充 Spring Security 与更完整的审计链路
