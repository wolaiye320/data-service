## 0. 文档适用边界

### 0.1 通用规范优先

- 本文档正文优先沉淀可跨项目复用的测试原则、分层策略、E2E 设计、契约验证、门禁要求与审查清单。
- 正文避免直接绑定某个项目的脚本入口、目录路径、账号命名、前端工程名。
- 项目特有测试命令、固定执行入口、仓库内路径等信息，统一集中在文末“项目特有落地约定”。

### 0.2 项目特有约定集中收口

- 当某条要求仅适用于当前项目时，应集中写入项目特有附录，不得在正文多个章节散落重复。
- 其他项目复用本文档时，应优先沿用正文，仅替换项目特有附录。

## 1. 文档定位与使用方式

### 1.1 文档定位

本文档回答以下问题：

- 这个改动至少需要补什么类型的测试
- 哪些场景必须使用真实数据库
- 哪些场景可以使用 Mock，哪些绝对不行
- API、前后端契约、E2E 文档应该怎么维护
- PR 提交前的最低测试门槛是什么

### 1.2 三层文档结构

测试文档拆分为三份：

- **核心规范**：`测试规范.md`
- **代码示例**：`测试规范-代码示例.md`
- **高级主题**：`测试规范-高级主题.md`

分工如下：

| 文档 | 作用 |
| --- | --- |
| `测试规范.md` | 定义“必须怎么做” |
| `测试规范-代码示例.md` | 提供“推荐怎么写” |
| `测试规范-高级主题.md` | 处理隔离、清理、复杂环境、数据生命周期等进阶问题 |

### 1.3 使用原则

- 日常开发、补测试、代码审查、提测、验收时，默认先读本文件
- 当需要落地写法时，再读 `测试规范-代码示例.md`
- 当涉及事务隔离、异步、复杂数据清理、容器复用等问题时，再读 `测试规范-高级主题.md`

## 2. 核心测试原则

1. **真实环境优先**：Repository / Connector 层必须使用真实数据库
2. **端到端覆盖**：关键业务流程必须有完整 E2E 测试
3. **契约验证**：前后端交互必须验证契约一致性
4. **Schema 验证**：数据库字段使用前必须验证真实存在
5. **Mock 谨慎使用**：Mock 只能隔离不可控外部依赖，不能掩盖真实问题
6. **重启验证**：关键改动测试通过后，必须验证系统重启后仍正常
7. **首屏接口成功约束**：菜单页 / 首屏页面的 E2E 不得只验证页面可见，必须同时验证关键接口成功返回
8. **禁止假绿**：前端静默吞掉核心接口失败、E2E 未检查接口状态码、文档遗漏 skip/fixme，均不得视为“测试通过”

> 记住：过度依赖 Mock 的测试很容易制造“测试通过、上线失败”的幻觉。

## 3. 测试分层策略

### 3.1 单元测试（Unit Tests）

**目标**：验证单个类、方法或纯业务逻辑的正确性。

**适用场景**：

- 算法、计算、规则判断
- 工具类、转换类、校验类
- 不依赖外部资源的业务逻辑

**要求**：

- 可以使用 Mock 隔离依赖
- 应快速执行
- 不得用 Mock 掩盖本该由集成测试发现的问题

### 3.2 Repository 集成测试（Repository Integration Tests）

**目标**：验证 Repository 与真实数据库交互是否正确。

**强制要求**：

- 必须连接真实数据库（优先 Testcontainers）
- 必须验证 SQL 正确性
- 必须验证字段映射正确性
- 必须验证方法参数与 SQL 参数一致性
- 禁止使用 Mock 或 H2 之类替代生产特性的内存数据库来代替真实验证

### 3.3 Service 集成测试（Service Integration Tests）

**目标**：验证 Service 层与 Repository、事务边界、部分外部依赖之间的协作是否正确。

**要求**：

- 使用真实 Repository
- 使用真实测试数据库
- 可以 Mock 外部 API / 第三方服务
- 必须覆盖完整业务流程，而不是只测单个语句

### 3.4 API 端到端测试（API E2E Tests）

**目标**：验证完整 HTTP 请求—应用处理—数据库交互—响应返回链路。

**强制要求**：

- 必须启动完整 Spring Boot 应用
- 必须使用真实 HTTP 请求
- 必须验证状态码、响应格式、关键字段与错误路径
- 必须验证前后端契约一致性

### 3.5 前后端契约测试（Contract Tests）

**目标**：验证前端接口定义与后端真实 API 契约一致。

**要求**：

- 验证路径、参数、状态值、错误码、响应结构一致性
- 新增或修改 API 时必须考虑契约验证
- 可结合 Spring Cloud Contract、Pact 或等价机制；若暂未引入正式框架，至少要通过自动化校验与集成测试显式覆盖

## 4. 不同改动对应的最低测试要求

| 改动类型 | 最低要求 |
| --- | --- |
| 纯算法 / 工具类 / 无外部依赖逻辑 | 单元测试 |
| 新增 / 修改 Repository 方法 | Repository 集成测试 |
| 新增 / 修改 Service 流程 | 单元测试或 Service 集成测试；涉及数据库时优先集成测试 |
| 新增 / 修改 API 端点 | API E2E 测试 + 契约验证 |
| 数据库 Schema 变更 | 迁移脚本 + Repository/集成测试 |
| 新增 / 修改自定义 SQL / MyBatis Mapper | Repository 集成测试 + 真实 Schema 字段校验 |
| 数据库连接器变更 | 真实数据库集成测试 |
| 用户可见完整业务流程变更 | 前端 E2E / 页面验证 + 后端链路验证 |
| 菜单页 / 仪表盘 / 目录页首屏数据加载变更 | 页面 E2E + 首屏关键 API 成功断言 + 浏览器 console 无 error |
| 状态机、权限、租户隔离逻辑变更 | 必须补关键路径测试和异常路径测试 |

## 5. Mock 使用规范

### 5.1 可以使用 Mock 的场景

- 外部 API 或第三方服务
- 不可控、昂贵、慢速依赖
- 异常路径模拟（超时、限流、远端失败）
- 只想隔离当前类逻辑时的复杂依赖链

### 5.2 禁止使用 Mock 的场景

- Repository 层
- Connector 层
- 数据库 Schema 相关验证
- SQL 参数与字段映射验证
- 任何需要发现真实数据库行为差异的问题

### 5.3 Mock 数据要求

- Mock 数据必须尽量接近真实结构与真实值域
- 不得使用“看起来能跑”的虚假结构掩盖契约问题
- 不得通过 Mock 绕过权限、租户、状态、Schema、事务问题

## 6. 数据库测试要求

### 6.1 真实数据库要求

所有涉及数据库的测试必须优先使用真实数据库，推荐使用 Testcontainers 启动 PostgreSQL 15+ 测试环境。

### 6.2 Schema 一致性要求

- 测试环境必须执行数据库迁移
- Repository 测试必须验证使用的字段真实存在
- 不得出现“测试使用旧 Schema、代码依赖新字段”的情况

### 6.3 Repository 层必测项

至少应覆盖：

- 创建 / 查询 / 更新 / 删除
- 空结果与边界结果
- 分页、排序、过滤
- 批量查询 / 聚合查询（如有）
- NULL 值与特殊字符处理
- 关键约束与唯一性行为

### 6.4 数据库变更闭环要求

每次 Schema 变更至少要同步检查：

- 迁移脚本是否存在
- Repository 映射是否更新
- Domain / DTO 是否更新
- 测试是否覆盖新字段或新逻辑

### 6.5 自定义 SQL / Mapper 闭环要求

- 任何 Repository 中新增或修改的 join / count / 聚合 / 统计 SQL，必须补真实数据库集成测试
- 测试必须覆盖：
  - 正常命中
  - 空结果
  - 至少一个关联条件过滤场景
- 禁止在 SQL 中引用当前迁移后 schema 不存在的字段
- 代码评审时必须显式核对：SQL 字段名、表名、别名、关联条件是否与当前 Flyway schema 一致

## 7. E2E 测试与用例文档规范

### 7.1 E2E 的定位

E2E 用例文档不是“测试摘要”，而是“验收执行脚本”。

要求达到：即使不是研发，也能按文档逐步执行并判断结果。

### 7.2 E2E 文档强制要求

1. **前置条件必须具体**
   - 写明账号、角色、页面路由、依赖环境、依赖数据
   - 禁止只写“已登录”“有测试数据”

2. **测试步骤必须逐步、可操作**
   - 写明按钮、输入框、Tab、选择项、实际点击动作
   - 禁止“填写有效配置”“执行查询”这类空泛表述

3. **必须给出明确样例数据**
   - 表单值、筛选值、规则阈值、关键字等都应写清楚

4. **预期结果必须是可观察结果**
   - 优先写页面提示、表格变化、状态标签、可见字段变化
   - 如有必要再补充后端副作用

5. **一条用例只验证一个清晰目标**
   - 避免多个目标混在同一条中

6. **允许通过测试数据字典减少重复**
   - 但必须使用固定别名，不能写成“某数据源”“某表”

### 7.3 E2E 文档最低质量门槛

- 禁止“填写有效数据”“显示正确结果”这类模糊描述
- 禁止只写页面路由，不写进入方式与实际控件
- 禁止依赖读者自行猜测输入值、按钮位置、筛选条件
- 默认按“业务 / 产品 / UAT 人员可直接照做”的标准编写

### 7.4 结果维护规则（集成测试 / E2E 通用）

测试用例文档维护的是**稳定测试基线**，而不是每次执行日志。

原则：

- 用例文档维护目标、前置条件、步骤、预期结果、测试数据字典和最新跟踪字段
- “实际结果”仅记录最新一次跟踪结论，如“未执行 / 通过 / 失败 / 阻塞 + 简短说明”，不替代完整执行日志
- 用例表中应同时维护自动化映射、执行日期、执行人、证据链接和阻塞说明
- 执行明细写入独立测试报告，而不是堆到每条用例下面

### 7.5 自动化映射要求

用例文档中应维护至少以下字段：

- 用例编号
- 自动化状态（未自动化 / 部分自动化 / 已自动化）
- 自动化用例（测试类#方法 或 Playwright 用例名）
- 最近执行时间
- 执行人
- 证据 / 报告
- 备注 / 阻塞原因

### 7.6 独立测试报告要求

每次执行应在对应领域的 `过程文档/` 中维护独立测试报告，记录：

- 执行范围
- 执行命令
- 执行环境

### 7.7 首屏页面 E2E 强制要求

- 菜单点击进入页面后，必须验证首屏关键 API 返回 `2xx`
- 若后端使用统一响应包装，必须同时验证业务响应码成功
- 不得仅以“标题可见”“表格出现”“搜索框存在”判定页面通过
- 若页面首屏存在多个并行接口，至少覆盖主数据接口、统计接口、评分接口等核心调用
- 对资产目录、看板、仪表盘、详情页等聚合页面，必须校验至少 1 条真实后端聚合接口成功

### 7.8 E2E 假绿防护要求

- 测试执行期间若出现前端 console error、关键接口 `4xx/5xx`、全局错误提示，默认判失败
- 前端不得对核心接口使用静默降级掩盖错误后再让 E2E 通过
- 若存在 `skip`、`fixme`、临时放宽断言、前端 catch 降级等情况，测试报告必须显式列出“未覆盖项 / 风险项”
- 宣称“E2E 已完成”时，必须同时给出：
  - 覆盖的页面 / 菜单
  - 覆盖的关键接口
  - 未覆盖或被跳过的场景
- 汇总结果
- 用例编号与自动化脚本映射
- 已知问题与限制说明

### 7.9 E2E 选择器与 UI 规范一致性要求

- E2E 选择器优先使用稳定语义定位，如 `getByRole`、`aria-label`、`data-testid`，禁止依赖脆弱 DOM 结构或样式类名。
- 对表格操作列、工具栏图标按钮等可见文案不稳定的控件，优先使用 `aria-label` 或 `data-testid`，禁止以临时可见文案作为长期定位依据。
- 若 UI 规范要求某控件为纯图标按钮，E2E 不得通过依赖文字按钮名称的方式固化错误实现。
- 对关键共享 UI 规范，除 E2E 外，还应补充更靠近实现层的契约测试、组件测试或页面测试，避免“功能通过但样式规范失守”。

## 8. 覆盖率与关键路径要求

### 8.1 最低覆盖率

- Repository 层：100%
- Service 层：90%
- Controller 层：90%
- Connector 层：100%

### 8.2 关键路径必须覆盖的场景

以下场景必须有自动化测试覆盖：

1. 完整业务流程
2. 数据库 Schema 变更
3. 前后端交互契约
4. 关键异常场景
5. 多租户、权限、状态机等高风险逻辑

### 8.3 覆盖率工具

使用 JaCoCo 作为覆盖率统计基础工具，覆盖率不达标时不得视为完成。

## 9. 测试执行策略

### 9.1 本地开发阶段

要求：

- 修改前明确影响范围
- 修改后执行覆盖本次改动的最小必要测试
- 涉及数据库、API、前端联动、关键业务流程时，不得只跑单个单元测试草草收尾

### 9.2 提交前阶段

要求：

- 功能性代码变更必须同步补测试
- 提交前至少跑受影响模块的测试
- 前端改动至少验证构建或页面行为
- 数据库变更至少验证迁移与映射

### 9.3 PR / 合并前阶段

强制要求：

- 所有相关测试通过
- 覆盖率达到阈值
- 关键路径回归通过
- 必要时进行重启验证

### 9.4 E2E 执行前置条件

执行 E2E 前，应确认：

- 后端应用已启动
- 前端应用已启动
- 测试账号、测试数据、依赖数据源已准备
- 当前使用的测试文档和自动化映射是最新版本

## 10. 测试命名规范

### 10.1 单元测试

```java
methodName_withCondition_shouldExpectedBehavior()
```

### 10.2 集成测试

```java
businessScenario_shouldProduceExpectedResult()
```

### 10.3 E2E 测试

```java
userJourney_shouldCompleteSuccessfully()
```

### 10.4 命名要求

- 名称必须体现触发条件与预期结果
- 禁止使用 `test1`、`shouldWork`、`demoTest` 之类无语义命名
- 优先按“场景 → 条件 → 结果”表达

## 11. 用例文档组织与编号规范

### 11.1 拆分原则

按 WBS 一级功能模块拆分集成测试文档与 E2E 测试文档，便于分批测试和验收。

### 11.2 编号规范

- 集成测试：`IT-{领域}-{序号}`
- E2E 测试：`E2E-{领域}-{序号}`

### 11.3 对应关系维护

- 测试类或方法注释中可标注用例编号，便于追溯
- 文档中维护自动化映射总表
- 过程文档维护执行报告，不在用例文档中堆叠历史流水账

## 12. PR 前测试审查清单

### 12.1 作者自查

- [ ] 所有新增 Repository 方法都有集成测试
- [ ] 所有新增 Service 方法都有单元测试或集成测试
- [ ] 所有新增 API 端点都有 E2E 测试或等价端到端验证
- [ ] 所有数据库 Schema 变更都有迁移脚本和测试
- [ ] 所有前后端交互都验证了契约一致性
- [ ] 覆盖率达到要求
- [ ] 受影响测试已在本地通过
- [ ] 关键改动已验证重启后行为正常

### 12.2 Review 检查项

- [ ] Repository / Connector 层是否使用真实数据库测试
- [ ] Mock 是否使用得当，没有掩盖真实问题
- [ ] 是否覆盖了关键业务链路
- [ ] 是否验证了 API 契约一致性
- [ ] 是否验证了 Schema 与映射一致性
- [ ] 测试命名是否清晰表达场景
- [ ] UI 规范相关改动是否补充了组件测试、页面测试或等价自动化验证
- [ ] 操作列 / 图标按钮的自动化定位是否使用稳定语义标识，而非临时可见文案

## 13. AI / 开发者测试决策速查

遇到以下情况时，优先这样判断：

- **只改了纯逻辑** → 先补单元测试
- **改了 SQL / Repository** → 必补真实数据库集成测试
- **改了 Service 流程** → 补业务流程测试，涉及数据库时优先集成测试
- **改了 API** → 补 API E2E + 契约验证
- **改了用户可见流程** → 补前端 E2E 或页面验证
- **改了迁移 / 字段 / 约束** → 补迁移验证 + Repository 映射测试

## 14. 维护原则

维护本文档时遵循以下原则：

1. 本文档只保留“测试总规范”
2. 大段代码示例放入 `测试规范-代码示例.md`
3. 高级隔离、事务、容器复用、清理策略放入 `测试规范-高级主题.md`
4. 若新增门禁、分层要求、覆盖率要求，应优先更新本文件

这样可以保证：

- 本文档保持“主规范”角色
- 示例文档负责“怎么写”
- 高级主题文档负责“复杂情况怎么处理”

## 15. 项目特有落地约定（data-service）

### 15.1 本地 Playwright E2E 执行入口

针对 `data-service-web` 的本地 Playwright E2E，默认使用固定入口执行：

- 标准入口：`pnpm test:e2e:local`
- Playwright 配置文件：`data-service-web/playwright.config.ts`
- 默认运行目录：`data-service-web`
- 当前 reporter：`list`

强制要求：

- 需要执行本地 Playwright E2E 时，优先在 `data-service-web` 目录下通过 `pnpm test:e2e:local` 及其参数透传形式执行
- 如需按文件、按 `--grep` 或其他 Playwright 参数执行，应在 `pnpm test:e2e:local -- ...` 后追加参数
- 如需 CI 风格全量执行，可使用 `pnpm test:e2e`

### 15.2 当前项目执行入口的目的

- 固化团队与 Agent 的统一执行方式
- 保持 `http://127.0.0.1:3001` 前端入口、Chrome 渠道、上海时区等本地执行参数一致
- 保持本地 E2E 输出格式与失败工件收集方式一致
