# 测试规范（核心）

> 代码示例见：[测试规范-代码示例.md](./测试规范-代码示例.md)
> 高级主题见：[测试规范-高级主题.md](./测试规范-高级主题.md)

## 1. 适用范围

本文档适用于当前数据服务项目的后端、前端和前后端协作测试，覆盖以下能力：

- 数据源连接管理
- 目标库管理
- 数据服务配置与发布
- 单次查询
- 关联查询
- 批量查询
- 查询缓存
- 前端配置界面

## 2. 核心原则

- 必须优先验证真实行为，不允许用 Mock 掩盖数据库、SQL、映射、契约问题
- Repository 层和数据库连接相关能力必须连接真实数据库测试
- 用户可见业务流程必须具备前端页面级 E2E 测试
- 后端 API 必须具备真实 HTTP 请求级测试
- 测试数据必须可重复构造、可独立清理、可单独运行
- 所有新增功能必须同时补齐对应层级测试

## 3. 测试分层

### 3.1 单元测试

目标：

- 验证纯业务逻辑、校验逻辑、工具类逻辑

适用范围：

- 参数校验
- 缓存键生成
- 状态流转
- 字段映射规则
- 错误码转换

要求：

- 可以使用 Mock 隔离外部依赖
- 单测应快速、稳定、可并行执行
- 禁止把需要真实数据库验证的逻辑塞入单元测试

### 3.2 Repository 集成测试

目标：

- 验证 Repository、SQL、字段映射、参数绑定与真实数据库的一致性

强制要求：

- 必须使用 Testcontainers 或独立测试数据库
- 必须验证 SQL 可执行
- 必须验证字段映射正确
- 必须验证方法签名、`@Param` 名称与 SQL 参数一致
- 禁止使用 H2 等内存数据库替代真实数据库行为
- 禁止用 Mock 替代 Repository 或数据库连接层

必须覆盖：

- `DS_CONNECTION`
- `DS_CATALOG`
- `DS`
- `DS_SOURCE`
- `DS_PARAM`
- `DS_FIELD`
- `DS_CACHE_POLICY`

### 3.3 Service 集成测试

目标：

- 验证 Service 层编排逻辑与真实 Repository 的集成结果

要求：

- 使用真实 Repository
- 数据库相关依赖必须连接真实数据库
- 可以 Mock 外部第三方服务，但必须说明原因
- 必须覆盖完整业务链路，而不是只断言单个方法调用

必须覆盖：

- 数据源连接测试
- 数据服务发布校验
- 查询执行主流程
- 缓存命中与失效流程
- 关联查询结果整合
- 批量查询结果汇总

### 3.4 API 集成 / E2E 测试

目标：

- 验证完整的 HTTP 请求到响应流程

强制要求：

- 必须启动完整 Spring Boot 应用
- 必须使用真实 HTTP 请求
- 必须验证状态码、响应结构、核心字段和错误码
- 必须覆盖管理接口与查询接口

必须覆盖：

- 数据源连接新增、编辑、测试连接
- 数据服务创建、编辑、发布、停用
- 单次查询成功
- 关联查询成功
- 批量查询成功
- 参数非法
- 服务未发布
- 数据源不可用

### 3.5 前端页面级 E2E 测试

目标：

- 验证用户从前端页面完成业务流程的真实结果

强制要求：

- 对已交付的用户可见配置功能，必须有前端页面级 E2E
- 用例必须覆盖页面操作、提交结果和页面反馈
- 测试步骤必须可直接执行，非研发角色也能照文档复现

必须覆盖：

- 新增数据源连接
- 配置目标库
- 创建数据服务
- 配置 SQL、参数、返回字段、缓存策略
- 发布数据服务
- 前端触发查询并查看结果

### 3.6 前后端契约测试

目标：

- 验证前后端 API 契约一致

要求：

- 验证路径一致
- 验证请求字段一致
- 验证响应字段一致
- 验证状态值、错误码一致
- 前端类型定义变更时必须同步验证后端返回结构

## 4. Mock 使用规则

### 4.1 可以使用 Mock 的场景

- 第三方短信、邮件、消息推送
- 外部收费或不可控服务
- 极难稳定构造的异常场景

### 4.2 禁止使用 Mock 的场景

- Repository 层
- 数据库连接管理层
- 动态 SQL 执行层
- 数据库 Schema 验证
- 字段映射验证

### 4.3 Mock 数据要求

- Mock 数据必须接近真实业务结构
- 禁止只为“让测试通过”而构造不可能出现的数据

## 5. 数据库测试规则

### 5.1 真实数据库原则

- 所有数据库相关测试必须连接真实数据库
- 默认使用 PostgreSQL Testcontainers
- 如涉及异构数据库能力，必须增加对应数据库类型的测试场景

### 5.2 Schema 一致性验证

- Repository 测试必须验证 SQL 中使用的字段真实存在
- 迁移脚本变更后必须补充对应测试

### 5.3 SQL 与参数验证

- 必须覆盖正常参数
- 必须覆盖缺失参数
- 必须覆盖空值、特殊字符、边界值
- 必须覆盖动态 SQL 条件分支

## 6. 测试数据管理

要求：

- 每个测试独立构造测试数据
- 测试数据必须可重复执行
- 不依赖共享脏数据
- 测试后必须自动回滚或清理

推荐方式：

- Repository / Service 集成测试优先使用 `@Transactional`
- API E2E 测试使用显式清理
- 复杂对象使用 Fixture 或 Builder 构造

## 7. 覆盖率要求

- Repository 层：100%
- Service 层：90%
- Controller 层：90%
- 数据库连接相关层：100%

除覆盖率外，还必须满足：

- 所有新增 Repository 方法必须有集成测试
- 所有新增 Service 方法必须有单元测试或集成测试
- 所有新增 API 端点必须有 API E2E 测试
- 所有已交付的用户可见业务能力必须有前端 E2E 测试

## 8. 测试执行要求

### 8.1 本地执行

最小执行要求：

- 提交前至少执行本次改动涉及的单元测试
- 涉及数据库的改动必须执行对应集成测试
- 涉及接口的改动必须执行 API E2E 或至少完整的接口集成测试
- 涉及前端配置界面的改动必须执行前端页面级 E2E

### 8.2 合并前执行

合并前必须完成：

- 后端测试通过
- 如本次包含前端界面改动，则前端测试通过
- 契约测试通过
- 关键业务链路 E2E 通过

## 9. 测试文档维护规则

- 核心规范文档维护规则、分层、门槛
- 代码示例文档维护可直接复用的示例代码
- 高级主题文档维护隔离、性能、异构数据库、失败分析等内容
- 文档中不得出现其他项目模块名、脚本名、业务域名
- 测试命名、测试对象、示例 SQL 必须围绕当前数据服务项目

## 10. 推荐命名规范

- 单元测试：`methodName_withCondition_shouldExpectedBehavior()`
- 集成测试：`businessScenario_shouldProduceExpectedResult()`
- E2E 测试：`userJourney_shouldCompleteSuccessfully()`

示例：

- `publish_withMissingSql_shouldRejectService()`
- `query_withValidServiceCode_shouldReturnConfiguredResult()`
- `createDatasourceFromPage_shouldSaveSuccessfully()`

## 11. 退出条件

功能进入提测或合并前，至少满足以下条件：

- 相关测试全部通过
- 无新增未解释的失败测试
- 文档、代码、测试口径一致
- 关键需求具备可追踪测试覆盖
