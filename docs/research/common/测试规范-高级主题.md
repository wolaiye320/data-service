# 测试规范 - 高级主题

> 返回核心规范：[测试规范.md](./测试规范.md)

本文档聚焦当前数据服务项目测试中的高级话题，包括测试隔离、异构数据库覆盖、动态 SQL 风险控制、缓存验证、前端 E2E 稳定性与测试报告维护。

## 1. 测试隔离与清理

### 1.1 基本原则

- 每个测试必须可独立运行
- 测试顺序不得影响结果
- 测试之间不得共享可变状态
- 测试数据必须能自动回滚或显式清理

### 1.2 `@Transactional` 回滚

适用：

- Repository 集成测试
- Service 集成测试
- 不涉及异步提交的场景

优点：

- 自动回滚
- 执行快
- 隔离稳定

### 1.3 `@DirtiesContext`

适用：

- 修改了 Spring 上下文
- 测试了异步流程
- 必须提交事务后再验证的场景

限制：

- 很慢
- 只在确实无法用事务隔离时使用

### 1.4 API / 前端 E2E 清理

适用：

- API E2E
- 前端页面级 E2E

要求：

- 每次执行前准备固定测试数据
- 每次执行后清理新增数据
- 清理逻辑必须可重复执行

## 2. Testcontainers 使用建议

### 2.1 共享容器

推荐：

- 一个测试类共享一个静态容器
- 配合事务回滚隔离测试数据

适用：

- 大多数 Repository / Service 集成测试

### 2.2 多容器场景

适用：

- 异构数据库关联查询验证
- 同时验证 PostgreSQL / MySQL / Oracle 适配逻辑

建议：

- 一个测试类只验证一个清晰场景
- 避免在同一类里堆叠过多容器
- 只为“需求中明确要求的异构能力”构建多容器测试

## 3. 异构数据库测试策略

当前项目支持不同类型数据库，因此测试不能只覆盖单一数据库。

最低覆盖建议：

- PostgreSQL：基础能力基线
- MySQL：参数绑定、字段类型差异
- Oracle：关键接入流程与查询能力

必须验证：

- 连接建立
- 查询执行
- 参数绑定
- 字段映射
- 关联查询

如果无法在日常开发环境覆盖全部数据库类型：

- 本地至少保证一种数据库类型完整跑通
- CI 或阶段性验证中补齐其余数据库类型

## 4. 动态 SQL 测试重点

动态 SQL 是本项目的高风险区域，必须重点测试。

必须覆盖：

- 占位符与参数名一致
- 缺失参数
- 空字符串参数
- `null` 参数
- 特殊字符参数
- 多条件分支
- SQL 注入尝试

建议断言：

- 查询结果正确
- 生成 SQL 行为符合预期
- 非法参数不会变成字符串拼接 SQL

## 5. 关联查询测试策略

需求规格要求支持同类型和不同类型数据库之间的关联查询，测试必须覆盖这两类场景。

### 5.1 同类型数据库关联

验证点：

- 同库或同类型跨库关联
- 关联字段映射
- 输出字段统一

### 5.2 异构数据库关联

验证点：

- PostgreSQL 到 MySQL
- Oracle 到 PostgreSQL
- 服务端结果整合逻辑

### 5.3 断言重点

- 调用方不感知底层来源差异
- 返回字段结构稳定
- 关联失败时错误信息明确

## 6. 批量查询测试策略

必须验证：

- 多组输入批量提交
- 单条结果与输入条件的对应关系
- 单条失败不影响其他结果
- 批量数量上限控制

建议断言：

- 返回结果中包含业务可识别的输入回显或 `batchKey`
- 整体结果结构稳定

## 7. 缓存测试策略

必须覆盖：

- 首次查询未命中缓存
- 相同参数重复查询命中缓存
- 参数变化时缓存隔离
- 服务变更后缓存失效
- 失效后重新命中数据库

避免只测试“有缓存对象返回”，必须测试：

- 缓存命中条件
- 缓存失效条件
- 缓存不影响正确性

## 8. 前端 E2E 稳定性

### 8.1 选择器规范

- 优先使用语义化选择器
- 优先通过按钮名、输入框标签、表格列标题定位
- 尽量避免基于样式类名定位

### 8.2 固定测试数据

- 页面 E2E 统一使用固定数据源编码和服务编码
- 每个测试运行前确保环境可清理、可重建

### 8.3 失败排查

前端 E2E 失败后至少检查：

- 页面是否真正提交成功
- 后端接口是否报错
- 测试数据是否已存在
- 异步渲染是否等待充分

## 9. 测试数据构建

推荐使用 Fixture / Builder 模式构建对象，避免重复硬编码。

示例思路：

- `DSConnectionFixtures.enabledPostgresConnection()`
- `DSFixtures.queryServiceDraft()`
- `DSParamFixtures.requiredCustomerIdParam()`
- `DSFieldFixtures.orderAmountField()`

要求：

- 默认对象应可直接用于成功场景
- 失败场景通过覆盖个别字段生成

## 10. 失败测试的处理规则

- 先判断是代码问题、测试问题还是环境问题
- 不允许因为环境波动直接删除测试
- 不允许因为修复成本高而降级真实数据库测试为 Mock
- 对已知环境噪音应在测试报告中说明，而不是写死在核心规范中

## 11. 测试报告维护

核心规范文档不维护执行流水账。

执行结果应单独沉淀到测试报告中，建议至少包含：

- 执行范围
- 执行环境
- 执行命令
- 结果汇总
- 失败用例
- 问题归因

推荐命名：

- `数据服务-后端集成测试报告-YYYY-MM-DD.md`
- `数据服务-前端E2E测试报告-YYYY-MM-DD.md`

## 12. 常见反模式

- 用 H2 替代真实 PostgreSQL / MySQL / Oracle
- 用 Mock 代替 Repository
- 只验证方法被调用，不验证数据库结果
- 只验证 HTTP 200，不验证响应结构
- 前端 E2E 不写具体操作步骤
- 文档中残留其他项目模块名、命令、页面路由

## 13. 文档维护要求

- 示例代码应优先使用当前项目对象命名
- 若未来项目真实类名调整，应同步修本文档示例
- 发现跨项目残留内容时，直接删除，不做兼容保留
