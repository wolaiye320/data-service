# 测试规范 - 高级主题

> 返回核心规范：[测试规范.md](./测试规范.md)

本文档涵盖测试的高级主题，包括测试隔离、数据管理、失败处理、性能测试、环境配置等。

## 测试隔离与数据清理

### 1. 测试隔离原则

**核心原则**：每个测试必须独立运行，不依赖其他测试的执行顺序或结果

**隔离策略**：
- ✅ 每个测试使用独立的测试数据
- ✅ 测试之间不共享可变状态
- ✅ 测试执行顺序不影响结果
- ✅ 可以单独运行任何一个测试

### 2. 数据清理策略

#### 策略 A：@Transactional（推荐用于大多数测试）

**适用场景**：
- Repository 集成测试
- Service 集成测试
- 不涉及多线程或异步操作的测试

**优点**：
- 自动回滚，无需手动清理
- 性能好，不需要重启容器
- 测试之间完全隔离

**示例**：
```java
@SpringBootTest
@Testcontainers
@Transactional  // ← 测试结束后自动回滚
class UserRepositoryIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15");

    @Autowired
    private UserRepository repository;

    @Test
    void save_withValidData_shouldPersistCorrectly() {
        User user = new User("John", "john@example.com");
        repository.save(user);

        User result = repository.findById(user.getId()).orElse(null);
        assertNotNull(result);
        // 测试结束后自动回滚，数据不会保留
    }
}
```

#### 策略 B：@DirtiesContext（用于特殊场景）

**适用场景**：
- 测试修改了 Spring 上下文（如修改配置、Bean 状态）
- 测试涉及多线程或异步操作（@Transactional 无法回滚）
- 测试需要提交事务（如测试事务传播行为）

**缺点**：
- 性能差，每次测试后重启 Spring 上下文
- 仅在必要时使用

**示例**：
```java
@SpringBootTest
@Testcontainers
@DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_EACH_TEST_METHOD)
class AsyncServiceIntegrationTest {

    @Test
    void processAsync_shouldCompleteSuccessfully() {
        // 测试异步操作，无法使用 @Transactional
        service.processAsync();
        // 等待异步完成
        await().atMost(5, SECONDS).until(() -> service.isCompleted());
        // 测试结束后重启上下文，清理所有状态
    }
}
```

#### 策略 C：手动清理（用于 E2E 测试）

**适用场景**：
- API E2E 测试
- 需要验证完整事务提交的测试

**示例**：
```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers
class UserApiTest {

    @Autowired
    private UserRepository userRepository;

    @AfterEach
    void cleanup() {
        // 手动清理测试数据
        userRepository.deleteAll();
    }

    @Test
    void createUser_shouldReturnCreatedUser() {
        // 测试逻辑
    }
}
```

### 3. Testcontainers 隔离机制

**容器级别隔离**：
- 每个测试类使用独立的数据库容器（如果使用非 static @Container）
- 或所有测试共享一个容器，但使用事务隔离数据

**推荐配置**（共享容器 + 事务隔离）：
```java
@SpringBootTest
@Testcontainers
@Transactional
class MyIntegrationTest {

    // static 容器：所有测试共享，启动一次
    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15")
        .withDatabaseName("testdb")
        .withUsername("test")
        .withPassword("test");

    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    // 每个测试使用 @Transactional 隔离数据
}
```

### 4. 测试数据生命周期

**原则**：
- ✅ 测试开始前：准备测试数据（Arrange）
- ✅ 测试执行中：执行测试逻辑（Act）
- ✅ 测试结束后：验证结果（Assert）+ 清理数据（Cleanup）

**反模式**：
- ❌ 在 @BeforeAll 中准备共享数据（测试之间会互相影响）
- ❌ 依赖数据库中已存在的数据（测试不可重复）
- ❌ 不清理测试数据（影响后续测试）

## 测试数据构建策略

### 1. 问题：测试数据重复和硬编码

**反模式示例**：
```java
@Test
void test1() {
    User user = new User(1L, "John", "john@example.com", "ACTIVE", LocalDateTime.now());
    // ...
}

@Test
void test2() {
    User user = new User(2L, "John", "john@example.com", "ACTIVE", LocalDateTime.now());
    // 重复的测试数据构建代码
}
```

### 2. 解决方案：Test Fixtures + Builder 模式

#### 方案 A：Test Fixtures（推荐）

创建专门的测试数据工厂类：

```java
public class UserFixtures {

    public static User createDefaultUser() {
        return User.builder()
            .name("John Doe")
            .email("john@example.com")
            .status("ACTIVE")
            .createdAt(LocalDateTime.now())
            .build();
    }

    public static User createUserWithEmail(String email) {
        return User.builder()
            .name("Test User")
            .email(email)
            .status("ACTIVE")
            .createdAt(LocalDateTime.now())
            .build();
    }

    public static User createInactiveUser() {
        return User.builder()
            .name("Inactive User")
            .email("inactive@example.com")
            .status("INACTIVE")
            .createdAt(LocalDateTime.now())
            .build();
    }
}
```

**使用示例**：
```java
@Test
void save_withValidData_shouldPersistCorrectly() {
    User user = UserFixtures.createDefaultUser();
    repository.save(user);

    User result = repository.findById(user.getId()).orElse(null);
    assertNotNull(result);
}

@Test
void findByEmail_withExistingEmail_shouldReturnUser() {
    User user = UserFixtures.createUserWithEmail("test@example.com");
    repository.save(user);

    Optional<User> result = repository.findByEmail("test@example.com");
    assertTrue(result.isPresent());
}
```

#### 方案 B：Builder 模式（灵活定制）

为测试对象添加 Builder：

```java
@Builder
public class User {
    private Long id;
    private String name;
    private String email;
    private String status;
    private LocalDateTime createdAt;
}
```

**使用示例**：
```java
@Test
void save_withCustomData_shouldPersistCorrectly() {
    User user = User.builder()
        .name("Custom Name")
        .email("custom@example.com")
        .status("PENDING")
        .build();

    repository.save(user);
    // ...
}
```

### 3. 测试数据最佳实践

**原则**：
- ✅ 使用 Fixtures 提供默认测试数据
- ✅ 使用 Builder 定制特定场景的数据
- ✅ 测试数据应该语义化（如 `createInactiveUser()` 而非 `createUser2()`）
- ✅ 避免魔法数字和硬编码字符串
- ✅ 测试数据应该最小化（只包含测试所需的字段）

**反模式**：
- ❌ 在每个测试中重复构建相同的测试数据
- ❌ 使用生产数据作为测试数据
- ❌ 测试数据过于复杂（包含不必要的字段）

## 测试失败处理

### 1. Flaky Tests 识别

**Flaky Test 定义**：在相同代码和环境下，有时通过、有时失败的测试

**常见原因**：
- 时间依赖（setTimeout、Date.now()）
- 异步操作未正确等待
- 测试之间的数据污染
- 并发竞争条件
- 外部依赖不稳定

**识别方法**：
```bash
# 重复运行测试 10 次
for i in {1..10}; do mvn test; done

# 使用 Maven Surefire 插件重复运行
mvn test -Dsurefire.rerunFailingTestsCount=3
```

### 2. Flaky Tests 修复策略

#### 问题：时间依赖

**反模式**：
```java
@Test
void testTimeout() {
    service.startAsync();
    Thread.sleep(1000); // ❌ 不可靠
    assertTrue(service.isCompleted());
}
```

**正确做法**：
```java
@Test
void testTimeout() {
    service.startAsync();
    await().atMost(5, SECONDS).until(() -> service.isCompleted()); // ✅ 使用 Awaitility
}
```

#### 问题：异步操作未等待

**反模式**：
```java
@Test
void testAsyncOperation() {
    CompletableFuture<String> future = service.processAsync();
    assertEquals("result", future.get()); // ❌ 可能超时
}
```

**正确做法**：
```java
@Test
void testAsyncOperation() {
    CompletableFuture<String> future = service.processAsync();
    String result = future.get(10, TimeUnit.SECONDS); // ✅ 设置超时
    assertEquals("result", result);
}
```

#### 问题：测试数据污染

**反模式**：
```java
@Test
void test1() {
    User user = new User("John");
    repository.save(user); // ❌ 数据未清理
}

@Test
void test2() {
    List<User> users = repository.findAll();
    assertEquals(0, users.size()); // ❌ 可能失败，因为 test1 的数据还在
}
```

**正确做法**：
```java
@SpringBootTest
@Transactional // ✅ 自动回滚
class MyTest {
    @Test
    void test1() {
        User user = new User("John");
        repository.save(user);
    }

    @Test
    void test2() {
        List<User> users = repository.findAll();
        assertEquals(0, users.size()); // ✅ 每个测试独立
    }
}
```

### 3. 测试失败诊断流程

**步骤 1：重现失败**
```bash
# 本地重复运行
mvn test -Dtest=FailingTest

# 查看详细日志
mvn test -Dtest=FailingTest -X
```

**步骤 2：分析日志**
- 查看异常堆栈
- 查看测试输出
- 查看数据库状态

**步骤 3：隔离问题**
```java
@Test
void isolatedTest() {
    // 1. 添加日志
    System.out.println("Before operation: " + repository.count());

    // 2. 执行操作
    service.operation();

    // 3. 验证中间状态
    System.out.println("After operation: " + repository.count());

    // 4. 断言
    assertEquals(expected, actual);
}
```

**步骤 4：修复并验证**
```bash
# 重复运行 10 次验证修复
for i in {1..10}; do mvn test -Dtest=FixedTest || break; done
```

## 性能测试

### 1. 性能基准测试

**目标**：建立性能基线，检测性能回归

**测试场景**：
- [ ] 查询性能：1000+ 条记录查询 < 1s
- [ ] 批量操作性能：1000+ 条记录批量操作 < 5s
- [ ] 并发性能：100 并发请求无错误
- [ ] 内存使用：处理大数据集不 OOM

**示例**：
```java
@SpringBootTest
@Testcontainers
class PerformanceTest {

    @Autowired
    private UserRepository repository;

    @Test
    void queryPerformance_with1000Records_shouldCompleteIn1Second() {
        // 准备 1000 条数据
        List<User> users = IntStream.range(0, 1000)
            .mapToObj(i -> UserFixtures.createUserWithEmail("user" + i + "@example.com"))
            .collect(Collectors.toList());
        repository.saveAll(users);

        // 测试查询性能
        long startTime = System.currentTimeMillis();
        List<User> result = repository.findAll();
        long endTime = System.currentTimeMillis();

        // 验证性能
        assertEquals(1000, result.size());
        assertTrue(endTime - startTime < 1000, "Query should complete in less than 1 second");
    }

    @Test
    void batchInsertPerformance_with1000Records_shouldCompleteIn5Seconds() {
        List<User> users = IntStream.range(0, 1000)
            .mapToObj(i -> UserFixtures.createUserWithEmail("user" + i + "@example.com"))
            .collect(Collectors.toList());

        long startTime = System.currentTimeMillis();
        repository.saveAll(users);
        long endTime = System.currentTimeMillis();

        assertTrue(endTime - startTime < 5000, "Batch insert should complete in less than 5 seconds");
    }

    @Test
    void concurrentRequests_with100Threads_shouldCompleteWithoutErrors() throws InterruptedException {
        ExecutorService executor = Executors.newFixedThreadPool(100);
        CountDownLatch latch = new CountDownLatch(100);
        AtomicInteger successCount = new AtomicInteger(0);
        AtomicInteger errorCount = new AtomicInteger(0);

        for (int i = 0; i < 100; i++) {
            final int index = i;
            executor.submit(() -> {
                try {
                    User user = UserFixtures.createUserWithEmail("user" + index + "@example.com");
                    repository.save(user);
                    successCount.incrementAndGet();
                } catch (Exception e) {
                    errorCount.incrementAndGet();
                } finally {
                    latch.countDown();
                }
            });
        }

        latch.await(30, TimeUnit.SECONDS);
        executor.shutdown();

        assertEquals(100, successCount.get(), "All requests should succeed");
        assertEquals(0, errorCount.get(), "No errors should occur");
    }
}
```

### 2. 性能回归测试

**策略**：
- 在 CI/CD 中运行性能测试
- 记录性能基线
- 检测性能回归（> 10% 性能下降）

**示例**：
```java
@Test
void performanceRegression_shouldNotExceedBaseline() {
    // 性能基线：1000 条记录查询 < 1s
    final long BASELINE_MS = 1000;
    final double REGRESSION_THRESHOLD = 1.1; // 允许 10% 性能下降

    // 准备数据
    List<User> users = IntStream.range(0, 1000)
        .mapToObj(i -> UserFixtures.createUserWithEmail("user" + i + "@example.com"))
        .collect(Collectors.toList());
    repository.saveAll(users);

    // 测试性能
    long startTime = System.currentTimeMillis();
    repository.findAll();
    long endTime = System.currentTimeMillis();
    long duration = endTime - startTime;

    // 验证性能未回归
    assertTrue(duration < BASELINE_MS * REGRESSION_THRESHOLD,
        String.format("Performance regression detected: %dms (baseline: %dms)", duration, BASELINE_MS));
}
```

## 测试环境配置

### 1. application-test.yml 配置

**配置原则**：
- ✅ 测试环境独立配置
- ✅ 使用内存数据库或 Testcontainers
- ✅ 禁用不必要的功能（邮件、定时任务）
- ✅ 加快测试执行速度

**示例**：
```yaml
# src/test/resources/application-test.yml

    # 由 Testcontainers 动态配置

  jpa:
    hibernate:
      ddl-auto: validate
    show-sql: false
    properties:
      hibernate:
        format_sql: false
        use_sql_comments: false

  flyway:
    enabled: true
    locations: classpath:db/migration
    clean-disabled: false

  mail:
    # 禁用邮件发送
    host: localhost
    port: 3025
    username: test
    password: test

  task:

      # 禁用定时任务
      enabled: false

logging:
  level:
    root: WARN

### 2. 测试配置类

- Mock 外部依赖
- 提供测试数据源

        );
    }
}
```

## 测试最佳实践

### 1. 测试代码可维护性

**原则**：
- ✅ 测试代码应该像生产代码一样干净
- ✅ 避免重复代码，提取公共方法
- ✅ 使用描述性的变量名和方法名
- ✅ 保持测试简单，一个测试只验证一件事

**示例**：
```java
// ❌ 反模式：重复代码
@Test
void test1() {
    User user = new User("John", "john@example.com");
    user.setStatus("ACTIVE");
    user.setCreatedAt(LocalDateTime.now());
    repository.save(user);
    // ...
}

@Test
void test2() {
    User user = new User("Jane", "jane@example.com");
    user.setStatus("ACTIVE");
    user.setCreatedAt(LocalDateTime.now());
    repository.save(user);
    // ...
}

// ✅ 正确做法：提取公共方法
private User createAndSaveUser(String name, String email) {
    User user = User.builder()
        .name(name)
        .email(email)
        .status("ACTIVE")
        .createdAt(LocalDateTime.now())
        .build();
    return repository.save(user);
}

@Test
void test1() {
    User user = createAndSaveUser("John", "john@example.com");
    // ...
}

@Test
void test2() {
    User user = createAndSaveUser("Jane", "jane@example.com");
    // ...
}
```

### 2. 测试重构策略

**何时重构测试**：
- 测试代码重复
- 测试难以理解
- 测试运行缓慢
- 测试频繁失败（Flaky）

**重构技巧**：
- 提取测试数据工厂（Fixtures）
- 提取公共断言方法
- 使用参数化测试减少重复
- 拆分大型测试类

**示例：参数化测试**：
```java
@ParameterizedTest
@CsvSource({
    "john@example.com, true",
    "invalid-email, false",
    "'', false",
    "test@, false"
})
void validateEmail_withVariousInputs_shouldReturnExpectedResult(String email, boolean expected) {
    boolean result = validator.isValidEmail(email);
    assertEquals(expected, result);
}
```

### 3. 测试覆盖率陷阱

**警告**：高覆盖率 ≠ 高质量测试

**反模式**：
```java
// ❌ 为了覆盖率而写的无意义测试
@Test
void testGetter() {
    User user = new User("John", "john@example.com");
    assertEquals("John", user.getName()); // 测试 getter 没有意义
}
```

**正确做法**：
- 关注业务逻辑覆盖，而非代码行覆盖
- 测试边界条件和异常路径
- 测试集成点和关键路径
