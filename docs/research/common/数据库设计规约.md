# 数据库设计规约

**版本**：2.0
**定位**：数据库设计、命名、分层、迁移、约束、索引、审计与环境边界的主规约文档
**适用范围**：系统元数据库、业务治理表、配置表、流水表、审计表，以及与业务数据库、数据集市交互时的建模约束

---

## 0. 文档适用边界

### 0.1 通用规范优先

- 本文档正文优先沉淀可跨项目复用的数据库设计原则、命名规则、Schema 演进要求、完整性约束与测试闭环。
- 正文避免直接绑定具体项目名、数据库实例名、表名前缀、迁移目录路径。
- 项目特有数据库名、表名前缀、模块缩写、迁移目录等信息，统一集中在文末“项目特有落地约定”。

### 0.2 项目特有约定集中收口

- 若某条规则依赖当前项目数据库拓扑、命名历史、模块缩写或工具目录，应集中写入项目特有附录，不得在正文多个章节散落重复。
- 其他项目复用本文档时，应优先复用正文，仅替换项目特有附录。

## 2. 数据库边界与环境角色

### 2.1 数据库角色划分

| 数据库 | 角色 | 用途 |
| --- | --- | --- |
| 系统元数据库 | 系统内部数据库 | 存放系统配置、元数据、治理数据、权限、审计、任务状态等 |
| 业务数据库 | 外部业务源库或接入库 | 存放被接入、被分析、被治理的业务数据 |
| 数据集市 | 分析沉淀库 | 存放指标沉淀、主题宽表、汇总结果等 |

### 2.2 边界原则

- **系统治理数据** 放在系统元数据库
- **业务原始数据** 保持在业务数据库或被接入的数据源中
- **分析沉淀结果** 放在数据集市
- 不得把业务数据库误当作系统元数据库使用
- 不得把系统元数据库当作业务明细大表存储层使用

### 2.3 操作原则

- 对系统元数据库的读写，应显式确认目标对象为系统内部库
- 对业务数据库的探查、样例校验、质量分析，应显式确认目标对象为业务源库
- 对数据集市的核对、沉淀、汇总校验，应显式确认目标对象为分析沉淀库
- 跨环境任务必须先读取元数据定义，再访问业务数据
- 当前项目的具体数据库实例名见“项目特有落地约定”

## 3. 表命名规范

### 3.1 总体命名格式

项目应统一维护一套稳定表命名模式，例如：

```text
{SYSTEM}_{MODULE}_{ENTITY}
```

说明：

- `SYSTEM`：系统统一前缀
- `MODULE`：业务模块缩写
- `ENTITY`：实体名称，使用大写下划线风格

### 3.2 模块前缀建议

| 维度 | 约束 | 说明 |
| --- | --- | --- |
| 系统前缀 | 项目内必须固定且统一 | 避免不同模块各自发明表名前缀 |
| 模块缩写 | 项目内必须有唯一映射表 | 避免同一模块多套缩写并存 |
| 实体命名 | 必须表达真实业务语义 | 避免临时、模糊、不可追溯命名 |

项目内具体模块前缀映射见“项目特有落地约定”。

### 3.3 命名原则

- 表名统一使用大写下划线风格
- 名称应表达业务语义，不使用模糊缩写
- 关系表使用双方实体名组合，如 `{SYSTEM}_{MODULE}_{LEFT_ENTITY}_{RIGHT_ENTITY}`
- 配置表、主数据表、流水表命名需能看出其职责
- 禁止使用无业务语义的表名，如 `{SYSTEM}_TMP_1`、`{SYSTEM}_TEST_TABLE`

## 4. 表分层规范

### 4.1 三类表模型

数据库设计遵循“配置 / 主数据 / 交易流水”分层思想：

| 类型 | 特征 | 示例 |
| --- | --- | --- |
| Configuration（配置表） | 低频变更，高频读取，承载规则、策略、开关、模板 | 策略表、模型路由表、权限策略表 |
| Master（主数据表） | 稳定实体、被多方引用、生命周期较长 | 用户、角色、租户、指标、维度、资源 |
| Transaction（流水表） | 高频写入、状态演进、用于追踪过程或结果 | 查询流水、执行流水、审计日志、检查结果 |

### 4.2 设计要求

- 设计表时，应先判断其属于哪一类
- 不得把配置与流水混杂到同一张大表
- 不得让主数据表承担高频日志流水职责
- 高频交易表应单独设计索引、分区、归档策略

## 5. 主键、唯一键与通用字段规范

### 5.1 主键规范

- 默认主键字段统一使用 `id`
- 类型优先使用 `BIGINT`
- 由应用或数据库统一生成，保持同类表生成策略一致
- 不推荐将业务编码直接作为主键

### 5.2 业务唯一键

- 稳定可读的业务标识应使用独立字段，如 `code`、`key`、`name`
- 业务唯一键应配套唯一索引或唯一约束
- 用户可编辑字段若不稳定，不应承担唯一主标识职责

### 5.3 通用审计字段

除确有例外外，业务表建议统一具备以下字段：

- `id`
- `tenant_id`（适用时）
- `created_at`
- `created_by`
- `updated_at`
- `updated_by`

按场景补充：

- `status`
- `remark`
- `version`
- `deleted`
- `deleted_at`
- `deleted_by`

### 5.4 时间字段规范

- 时间字段统一使用 `_at` 后缀，如 `created_at`
- 日期字段统一使用 `_date` 后缀，如 `effective_date`
- 开始/结束时间使用成对命名，如 `start_at` / `end_at`
- 版本生效区间使用 `version_start_date` / `version_end_date` 等清晰命名

## 6. 隔离维度设计规范

### 6.1 核心原则

- 是否需要租户、环境、数据域等隔离字段，必须以当前项目真实架构为准，不能从其他项目照搬。
- 当前项目若未建设多租户模型，不得预埋 `tenant_id` 并要求所有表强制携带。
- 当后续确需引入隔离字段时，必须先在需求、架构、数据库规约中明确隔离语义，再统一落库。

### 6.2 当前项目约束

- `data-service` 当前元数据模型以单租户部署为前提，现有 `DS_*` 元数据表不要求 `tenant_id`。
- 隔离边界当前主要通过系统元数据库、业务数据库作用域、服务编码、连接配置和发布状态来表达。
- 若未来新增多租户能力，应新增独立设计，不得直接复用旧项目的租户字段规则。

### 6.3 命名与查询要求

- 只有在隔离字段已进入正式模型后，才允许在表结构、唯一约束、索引和查询中统一使用该字段。
- 隔离字段命名必须单义、稳定，并在所有相关表和查询中保持一致。
- 禁止出现“代码里假定存在隔离字段，但 schema、迁移和测试未同步”的情况。

## 7. 状态、删除与版本化规范

### 7.1 状态字段

- 涉及流程、审核、执行、生命周期演进的表应设计 `status`
- `status` 值必须有清晰枚举语义，不得使用不可解释数字魔法值
- 状态设计应支持明确状态机流转，而不是任意跳转

### 7.2 删除策略

- 默认优先使用逻辑删除而非物理删除，尤其是配置表、主数据表、审计相关表
- 若使用逻辑删除，建议统一字段：`deleted`、`deleted_at`、`deleted_by`
- 高频流水、临时缓存、可重建数据可按设计选择物理删除，但必须明确说明原因

### 7.3 版本化

以下场景优先考虑版本化：

- 指标口径
- 规则策略
- Prompt 模板
- 权限策略
- 语义映射

常用字段：

- `version`
- `version_start_date`
- `version_end_date`
- `is_latest`

原则：

- 不直接覆盖关键历史配置
- 需要追溯时，应保留历史版本
- 历史版本与当前版本应能明确区分

## 8. 外键、约束与数据完整性规范

### 8.1 基本原则

- 重要关系必须通过外键或等价约束保证一致性
- 不得完全依赖应用层“约定”替代数据库完整性约束
- 但高并发、大流水场景也需平衡写入性能与约束成本

### 8.2 建议使用外键的场景

- 主数据之间稳定的一对多关系
- 配置表指向租户、用户、角色、资源等核心主数据
- 中小规模关系表需要强一致性时

### 8.3 可谨慎弱化外键的场景

- 超高频日志流水
- 审计明细
- 大批量导入中间表
- 需要跨系统弱耦合存储时

即便弱化外键，也应满足：

- 字段命名规范

### 8.4 Schema 变更与查询一致性要求

- 任何表结构变更后，必须同步全仓检查相关 Repository / Mapper / 原生 SQL 中的字段引用
- 若某业务语义未在 schema 中建模，禁止在 SQL 中臆造字段并直接依赖
- 对统计、评分、聚合类查询，优先基于真实主键、外键或稳定业务键关联；禁止使用“代码里想当然存在”的字段
- 当查询依赖 `datasource_id + schema_name + table_name` 这类业务键时，应在 schema、Repository、测试中保持统一表达
- 迁移脚本完成后，必须通过真实数据库集成测试验证关键查询仍可执行
- 数据写入校验
- 后续清理/补偿机制明确

### 8.5 唯一性约束

- 业务唯一标识必须有唯一约束或唯一索引
- 若项目存在隔离字段，唯一性通常应设计为 `(isolation_key, business_key)` 或等价组合；当前项目未引入该规则时，不得机械套用。
- 禁止仅靠应用层先查后写来“模拟唯一性”

## 9. 索引设计规范

### 9.1 基本原则

- 索引服务于查询模式，而不是“字段越多越好”
- 建索引前先明确主查询条件、排序条件、关联条件
- 高频写入表谨慎增加过多索引

### 9.2 建议优先考虑索引的字段

- 隔离字段（适用时）
- 外键字段
- 业务唯一键
- 状态字段（与高频筛选组合时）
- 时间字段（按时间范围查询时）
- 排序字段

### 9.3 组合索引原则

- 组合索引字段顺序应贴近最常见查询谓词顺序
- 若项目存在隔离字段，通常应优先评估是否需要放入组合索引
- 不要为低频查询大量堆叠组合索引

### 9.4 审查要求

新增索引前，应思考：

- 该索引服务的查询是什么
- 是否已有可复用索引
- 写入代价是否可接受
- 是否会与已有索引重复

## 10. 字段设计规范

### 10.1 命名规范

- 字段名统一使用小写下划线风格
- 布尔字段使用明确语义，如 `enabled`、`deleted`、`is_latest`
- 计数字段使用 `_count`
- 金额/数值字段使用具象名称，如 `token_cost`、`retry_count`

### 10.2 数据类型选择

- 主键、外键优先使用 `BIGINT`
- 文本说明类字段使用 `TEXT` 或足够长度的 `VARCHAR`
- 状态、类型、类别字段长度应控制合理，不滥用超长字符串
- JSON 结构化扩展字段仅在确有必要时使用，不能代替正常建模

### 10.3 扩展字段原则

- 优先建模，谨慎使用 `extra_json`、`metadata_json` 一类大杂烩字段
- 若使用 JSON 字段，必须明确其边界和用途
- 不得把稳定结构长期放在 JSON 中逃避 Schema 设计

## 11. 审计与日志表规范

### 11.1 审计表特点

审计与日志类表通常属于高频流水表，应具备：

- 明确主体（who）
- 明确时间（when）
- 明确对象（what）
- 明确位置/来源（where）
- 明确结果（result）

### 11.2 建议字段

按场景选择：

- `trace_id`
- `request_id`
- `operator_id`
- 隔离字段（适用时）
- `action`
- `resource_type`
- `resource_id`
- `result_status`
- `error_message`
- `created_at`

### 11.3 设计原则

- 审计表以可追溯为优先
- 审计表通常不做逻辑删除
- 高频审计表应考虑时间维度索引、归档、冷热分离

## 12. Repository 映射与持久化实现约束

### 12.1 MyBatis 规范

- Repository 接口统一使用注解方式定义 SQL
- 禁止使用 XML Mapper 文件
- 禁止使用 XML 的原因是模块在 JAR 依赖链中复用时，XML Mapper 的扫描与绑定更容易出现运行时不确定性
- 简单查询使用 `@Select`
- 插入操作使用 `@Insert`；需要回填主键时，配合 `@Options(useGeneratedKeys = true, keyProperty = "id")`
- 更新操作使用 `@Update`
- 删除操作使用 `@Delete`
- 复杂 SQL 可使用 Java Text Blocks 提高可读性
- 参数必须使用 `@Param` 显式命名
- 字段映射应使用 `@Results` / `@Result` / `@ResultMap` 清晰定义

### 12.2 映射一致性要求

- 数据库字段名与 Java 字段名之间的映射必须显式、清楚、可测试
- 新增字段后必须同步更新：
  - DDL / 迁移脚本
  - Repository 映射
  - Domain / DTO
  - 测试用例

### 12.3 Schema 验证要求

- 使用数据库字段前必须确认其已在真实 Schema 中存在
- 不得出现“代码已引用、迁移未落地、测试未覆盖”的状态

## 13. 迁移规范（Flyway）

### 13.1 基本规则

- 所有 Schema 变更必须通过 Flyway 迁移脚本落地
- 禁止直接修改已提交的迁移文件
- 每次变更必须新增新的迁移版本

### 13.2 命名规则

```text
V{N}__{description}.sql
```

示例：

```text
V45__relation_candidate.sql
```

### 13.3 文件位置

- 迁移目录应在项目内统一约定，并保持所有模块一致
- 当前项目的具体迁移目录见“项目特有落地约定”

### 13.4 版本管理要求

- 版本号单调递增
- 不可重复
- 不可跳号后回填
- 一次迁移只做一组逻辑相关变更，避免混入无关修改

### 13.5 迁移配套要求

新增迁移时，必须同步考虑：

- Repository / Domain 映射是否同步更新
- 是否新增或调整了索引、约束、默认值
- 是否需要补充集成测试验证字段映射与行为
- 是否影响历史数据兼容性

---

## 14. 测试与验证要求

### 14.1 数据库变更最低门槛

涉及以下情况时，必须补充测试：

- 新建表
- 新增字段
- 新增索引
- 新增约束
- 新增 Repository 方法
- 修改 SQL 查询逻辑

### 14.2 测试原则

- Repository 层必须优先使用真实数据库集成测试
- 不得用 Mock 掩盖字段不存在、SQL 错误、映射错误等真实问题
- 迁移脚本与 Repository 映射应形成闭环验证

详细测试要求见：

- `docs/research/common/测试规范.md`

---

## 15. AI / 开发者数据库设计检查清单

在提交数据库相关改动前，至少自检：

- 是否明确当前操作的是系统元数据库、业务数据库还是数据集市
- 表名是否符合项目统一命名规范
- 是否正确区分了配置表、主数据表、流水表
- 是否确认当前变更不应引入仓库中不存在的隔离字段约束
- 是否考虑了主键、唯一键、索引、状态、审计字段
- 是否避免把稳定结构塞进 JSON 字段
- 是否同步新增了 Flyway 迁移脚本
- 是否同步更新了 Repository / Domain / DTO 映射
- 是否补充了真实数据库测试
- 是否说明了变更影响范围和验证方式

## 16. 维护原则

维护本文档时，遵循以下原则：

1. 只保留数据库设计层面的稳定规则
2. 具体某张表的详细 DDL 不放在本文档，而放在详细设计或迁移脚本中
3. 当命名规范、隔离约束、迁移规则、索引策略发生变化时，必须同步更新本文档
4. 若项目后续拆分更多数据库或引入新存储层，也应先更新本文档，再更新实现

这样可以保证：

- `AGENTS.md` 保持通用
- 本文档承载项目数据库设计总规约
- 迁移脚本、Repository、测试与详细设计可以据此保持一致

## 17. 项目特有落地约定（data-service）

### 17.1 当前数据库角色实例

| 实例 | 角色 | 用途 |
| --- | --- | --- |
| `data_service` | 系统元数据库 | 存放系统配置、元数据、服务定义、缓存策略、发布版本、审计与联邦 SQL 元数据等 |
| `bankdb.public` | 业务数据库默认作用域 | 存放被接入、被分析、被治理的业务数据 |
| `datamart` | 数据集市 | 作为后续分析沉淀与结果落地的默认目标域 |

### 17.2 当前表命名模式与模块前缀

当前项目表名统一使用：

```text
ds_{entity}
```

| 类型 | 示例 | 说明 |
| --- | --- | --- |
| 元数据主表 | `ds_connection`、`ds_catalog`、`ds_service` | 连接、目标库、服务定义 |
| 服务子表 | `ds_source`、`ds_param`、`ds_field`、`ds_cache_policy` | 来源、参数、字段、缓存策略 |
| 发布与审计 | `ds_service_version`、`ds_audit_log` | 版本快照、审计流水 |
| 联邦 SQL | `ds_sql_text`、`ds_sql_plan`、`ds_sql_validate_log`、`ds_source_capability` | SQL 文本、执行计划、校验日志、来源能力 |

### 17.3 当前隔离模型说明

- 当前项目尚未引入租户主表。
- 如后续引入多租户能力，应先更新需求、架构与本文档，再新增隔离字段和对应主数据表。
