# 数据服务架构与详细设计

## 1. 文档目的

本文档基于《[数据服务需求规格书](/Volumes/osdisk/java_code/data-service/docs/research/common/数据服务-需求规格书.md)》和《[数据服务工程架构说明](/Volumes/osdisk/java_code/data-service/docs/research/common/工程架构说明.md)》编写，用于说明数据服务系统的模块设计、核心流程、数据模型、接口设计、前后端协作方式和测试要求，作为开发实施与联调依据。

## 2. 设计范围

- 数据源连接与目标库管理
- 逻辑数据服务配置与发布
- 单次查询、关联查询、批量查询
- 本地缓存
- 前端配置管理界面
- 日志、审计、异常处理
- 联邦 SQL 管理、校验、优化与执行
- 自助式 SQL 数据服务平台能力

本文档不包含以下实现范围：

- 数据新增、修改、删除能力
- 数据同步、ETL、离线计算能力
- 报表分析和 BI 展示能力
- 分布式缓存实现

## 3. 详细设计原则

- 服务定义、数据源配置、执行逻辑解耦
- 所有查询能力由配置驱动，不写死业务 SQL
- 服务仅支持查询，不支持写操作
- 动态 SQL 只能使用参数绑定
- 服务发布前必须完成完整性校验
- 查询返回结构以字段配置为准，不直接暴露原始列结构
- 调用方不感知底层数据库类型和物理位置
- 采用分阶段、瀑布式实施方式，阶段边界必须明确
- 第一阶段与第二阶段架构必须连续演进，不允许推翻式重构
- 必须满足普通单机部署运行要求，设计基线按 4 核 CPU、16G 内存控制
- 资源保护优先于单次查询吞吐，禁止以无边界并发或无边界内存占用换取局部性能
- 详细设计必须与需求规格书中的功能范围、业务规则、约束和验收标准保持一致

## 4. 分阶段实施架构

### 4.1 第一阶段：基础数据服务架构

建设目标：

- 完成异构数据库接入
- 完成配置驱动的数据服务管理
- 完成统一查询 API、批量查询、缓存、前端配置界面
- 形成可发布、可调用、可测试、可验收的基础系统

核心实现方式：

- 基于配置表定义数据服务
- 基于 Spring JDBC 执行配置化 SQL
- 基于服务端结果整合实现基础跨库关联
- 默认采用本地缓存提升热点查询性能

### 4.2 第二阶段：联邦 SQL 平台架构

建设目标：

- 支持一个服务直接维护一条联邦 SQL
- 支持联邦 SQL 解析、校验、优化、执行
- 支持 Join Reorder、Filter Pushdown、Project Pushdown
- 支持更复杂表达式和 SQL 方言兼容
- 将系统升级为自助式 SQL 数据服务平台

核心实现方式：

- 引入联邦 SQL 规划器
- 引入联邦 SQL 优化器
- 引入统计信息与代价估算层
- 引入数据源能力注册层
- 引入方言适配与统一 SQL 表达层
- 引入子计划拆分与执行编排层
- 引入运行时动态过滤与阶段化执行摘要
- 引入中间结果缓冲、落盘与受控并发机制
- 引入联邦执行计划与诊断能力
- 保持统一 API 和统一配置管理界面不变

### 4.3 第二阶段平台分层

第二阶段联邦 SQL 平台采用以下分层：

- 接入层
  - 管理联邦 SQL 配置、校验、发布接口
  - 管理统一查询接口
- 服务编排层
  - 装载服务版本
  - 编排校验、规划、优化、执行、缓存与日志
- Calcite 规划层
  - 负责 Parser、Validator、`SqlNode -> RelNode`、规则优化
- 数据源能力层
  - 负责维护各类数据库的 join、filter、project、aggregate、sort、limit、function 等能力模型
- 方言适配层
  - 负责将统一 SQL 语义转换为目标数据库方言 SQL
- 执行编排层
  - 负责子计划拆分、远端执行调度、本地结果整合
- 平台支撑层
  - 负责元数据持久化、计划缓存、校验日志、审计日志与诊断信息

### 4.4 第二阶段补充借鉴原则

在保持“Calcite 负责规划、平台负责执行编排”主路线不变的前提下，第二阶段补充吸收 Flink 与 Trino 在联邦查询中的成熟思路。

借鉴 Trino 的设计点：

- 采用比静态布尔能力更细粒度的 connector 能力协商模型
- 在优化阶段显式引入统计信息、代价估算和 Join 策略选择
- 将执行计划拆分为可观测的阶段 DAG，而不是只保留单一 SQL 文本
- 在 Join 场景引入运行时动态过滤，尽量减少探测侧无效扫描
- 在诊断层提供类似 `EXPLAIN` 的计划、下推、阶段与回退原因展示

借鉴 Flink 的设计点：

- 对维表式、小结果集式关联引入异步查找、批量查找与本地查找缓存思路
- 对跨源读取的一致性问题引入统一查询时间点和快照读取能力建模
- 对长链路子计划执行引入受控异步编排，而不是串行阻塞式执行
- 对中间结果处理引入流式传递与必要时落盘缓冲的组合策略

### 4.5 单机部署资源基线

本系统必须支持在普通单台服务器上独立部署运行，默认资源基线按以下配置考虑：

- 4 核 CPU
- 16G 内存

设计约束如下：

- 第一阶段全部能力必须可在该基线下稳定运行
- 第二阶段联邦 SQL 能力必须以“可受控降级运行”为目标，不得默认依赖分布式集群
- 对跨源 Join、本地补算、批量查询、中间结果整合等高风险场景，必须优先采用限流、分批、流式处理、落盘缓冲和失败保护
- 当资源不足时，应优先返回明确错误或降级结果，不允许以进程 OOM 作为系统行为

## 5. 模块详细设计

### 5.1 数据源管理模块

职责：

- 维护 `DS_CONNECTION`
- 维护 `DS_CATALOG`
- 管理连接测试与启停状态

核心能力：

- 新增数据源连接
- 编辑数据源连接
- 测试数据源连接
- 配置一个连接下的多个目标库
- 启用或停用连接

处理规则：

- `connectionCode` 全局唯一
- 保存连接时必须做连通性测试
- 停用连接前必须检查是否存在已发布服务引用
- 仅 `ENABLED` 状态连接可参与服务发布

### 5.2 数据服务配置模块

职责：

- 维护 `DS`
- 维护 `DS_SOURCE`
- 维护 `DS_PARAM`
- 维护 `DS_FIELD`
- 维护 `DS_CACHE_POLICY`

核心能力：

- 创建服务草稿
- 维护服务来源
- 维护参数定义
- 维护返回字段定义
- 维护缓存策略
- 维护服务 SQL 或联邦 SQL
- 发布服务
- 停用服务

处理规则：

- 服务编码 `serviceCode` 全局唯一
- 服务状态只允许 `DRAFT`、`PUBLISHED`、`DISABLED`
- 已发布服务变更时必须生成新版本，不覆盖历史版本
- 未通过发布校验的服务不得进入 `PUBLISHED`
- SQL 必须通过配置维护，不通过代码为单个业务场景写死实现

### 5.3 查询执行模块

职责：

- 按 `serviceCode` 加载服务配置
- 校验请求参数
- 执行数据库查询
- 处理缓存命中与回写
- 返回统一响应结构

处理规则：

- 仅允许调用 `PUBLISHED` 状态服务
- 批量查询单次上限必须可配置，默认建议值为 100
- 批量查询结果必须能够标识每条输入与输出的对应关系
- 单次查询结果上限、查询超时、批量规模上限必须支持系统级或服务级配置

### 5.4 联邦查询模块

职责：

- 按 `DS_SOURCE` 组合查询来源
- 执行跨来源关联处理
- 将结果转换为统一字段结构

处理规则：

- 必须支持同类型数据库之间的关联查询
- 必须支持不同类型数据库之间的关联查询
- 优先采用数据库侧关联执行
- 当底层数据库无法直接完成关联时，必须由服务端完成结果整合
- 关联键必须在 `DS_FIELD` 中显式声明

### 5.5 联邦 SQL 规划与优化模块

职责：

- 解析联邦 SQL
- 校验联邦 SQL 的语义合法性
- 生成联邦查询逻辑计划
- 对逻辑计划进行优化
- 输出可执行物理计划

实现约束：

- 第二阶段统一基于 Apache Calcite 承担 Parser、Validator、Planner 和 Optimizer 能力
- 该模块只负责规划、优化和下推决策，不直接替代底层 JDBC 执行职责

核心能力：

- SQL 解析
- SQL 校验
- 统计信息装载
- 代价估算
- 来源识别
- Join Reorder
- Join 策略选择
- Filter Pushdown
- Project Pushdown
- Partial Aggregation Pushdown
- Dynamic Filter 规划
- 物理执行计划生成

处理规则：

- 联邦 SQL 必须先通过校验才能发布
- 优化器必须保证优化前后语义一致
- 同一数据源内可闭包执行的子树必须优先整体下推评估
- 优化阶段必须同时输出逻辑计划、优化计划、阶段计划和下推失败原因
- 当统计信息缺失时必须退化到启发式规则，不能阻塞计划生成
- 数据源不支持的能力不得强制下推
- 无法下推的逻辑必须回退到服务端执行层处理

### 5.6 数据源能力管理模块

职责：

- 维护平台侧数据源能力模型
- 为联邦 SQL 下推决策和计划拆分提供依据
- 统一管理不同数据库类型的函数、类型和算子支持边界

核心能力：

- 维护 join 能力
- 维护 join 作用域能力
- 维护 filter 能力
- 维护 project 能力
- 维护 aggregate 能力
- 维护 sort、limit、offset 能力
- 维护函数兼容能力
- 维护类型兼容能力
- 维护读取一致性与快照能力
- 维护异步 lookup、批量 lookup 与 lookup cache 能力

处理规则：

- 能力模型必须独立于 Calcite 原生规则维护
- 下推决策必须同时参考 Calcite 规划结果和平台能力模型
- 能力模型不能只表达“是否支持”，还必须表达作用域、约束条件、阈值和推荐执行模式
- 运行期实际执行结果可反向修正能力模型中的推荐模式，但不得绕过发布期硬性边界
- 未声明支持的能力不得静默下推
- 能力校验失败必须在发布前暴露

### 5.7 SQL 方言适配模块

职责：

- 统一联邦 SQL 表达
- 处理不同数据源 SQL 方言差异
- 将统一逻辑表达转换为目标数据源可执行语句

核心能力：

- 类型系统适配
- 函数语义适配
- 标识符与关键字适配
- SQL 片段生成

处理规则：

- 用户不需要分别维护多套数据库方言版本
- 平台负责将统一 SQL 语义转换为目标方言
- 若目标数据源不支持某表达式，必须返回明确校验或执行错误

### 5.8 联邦执行编排模块

职责：

- 对优化后的联邦计划做子计划拆分
- 识别可在单一数据源内闭包执行的子树
- 调度远端 JDBC 执行
- 对未下推节点执行本地补算

核心能力：

- 计划拆分
- 阶段 DAG 生成
- 执行依赖排序
- 远端 SQL 执行
- 异步 lookup / 批量 lookup 执行
- 运行时动态过滤传播
- 中间结果缓冲与必要时落盘
- 本地 join / filter / aggregate / sort
- 统一结果装配

处理规则：

- 子计划拆分必须以数据源边界为核心依据
- 同一数据源内可闭包执行的聚合、过滤、投影、排序应优先留在单一子计划内
- 可下推节点优先在数据库侧执行
- 跨源 join 默认允许回退到本地执行层
- 小结果集维表关联可优先采用 lookup join，而不是一律拉全量后本地 join
- 本地 join 必须区分 broadcast、repartition、lookup 三种策略，按统计信息或启发式选择
- 中间结果超过内存阈值时必须支持落盘或临时缓冲，避免单机内存放大
- 异步并发度必须可控，避免对单一数据源形成突发压测
- 本地执行层必须具备结果集上限、超时和内存保护
- 在 4 核 CPU、16G 内存基线下，执行编排默认应采用保守并发策略，避免多个大查询同时触发本地补算
- 单次联邦查询的本地补算内存预算、缓冲阈值、落盘阈值、结果集上限必须可配置，且需提供安全默认值

### 5.9 缓存模块

职责：

- 管理查询结果缓存
- 根据版本与参数生成缓存键
- 负责缓存过期和失效

处理规则：

- 缓存默认采用本地缓存，本期不展开分布式缓存实现
- 缓存键固定为 `data-service:{serviceCode}:v{version}:{paramHash}`
- 仅缓存成功查询结果
- 缓存时间必须支持按服务配置，不得写死为全局固定值
- 发布新版本后旧版本缓存自动失效
- 缓存失效后必须重新查询源数据库

### 5.10 权限与审计控制模块

职责：

- 管理平台角色与权限校验
- 控制管理接口与查询接口的访问边界
- 控制敏感配置、发布能力、诊断能力的访问范围
- 记录关键操作审计日志
- 控制审计列表查看与审计详情查看边界

核心能力：

- 角色权限校验
- 接口鉴权与授权
- 敏感字段脱敏展示
- 审计事件记录与查询

处理规则：

- 平台管理员可管理数据源连接、服务配置、发布与停用
- 数据服务开发人员可维护服务草稿、联邦 SQL、校验与预览执行，但是否可发布由权限配置决定
- 调用方仅允许访问已授权的统一查询接口，不允许访问管理接口
- 测试连接、查看连接详情、查看联邦计划与诊断信息等能力必须受权限控制
- 审计日志必须覆盖配置变更、发布、停用、测试连接、预览执行、权限变更等关键操作
- 审计列表查看权限必须独立控制，不得默认开放给所有管理角色
- 审计详情查看权限可与审计列表查看权限分级配置
- 敏感信息在展示、日志和审计中必须脱敏

### 5.11 审计与日志模块

职责：

- 记录配置变更日志
- 记录查询调用日志
- 记录异常日志
- 记录联邦 SQL 校验、优化和执行诊断信息
- 记录统一事件模型下的审计日志并提供检索能力

处理规则：

- 日志必须包含 `traceId`
- 配置变更必须记录操作对象、操作人、操作时间、变更摘要
- 查询日志必须记录 `serviceCode`、耗时、结果码、缓存命中情况
- 联邦查询日志必须记录计划摘要、下推情况和执行阶段信息
- 审计日志必须按统一事件模型写入 `DS_AUDIT_LOG`
- 审计日志保留周期必须支持配置，建议不少于 180 天
- 审计日志中涉及敏感配置时只允许保存脱敏后的摘要信息
- 审计日志必须支持按服务、连接、操作人、事件类型、时间范围检索
- 审计日志与业务查询日志必须分离存储，避免相互覆盖或语义混淆

## 6. 核心数据模型设计

### 6.1 表设计清单

| 表名 | 作用 |
| --- | --- |
| `DS_CONNECTION` | 数据源连接 |
| `DS_CATALOG` | 目标库映射 |
| `DS` | 逻辑数据服务 |
| `DS_SOURCE` | 服务来源定义 |
| `DS_PARAM` | 服务参数定义 |
| `DS_FIELD` | 返回字段定义 |
| `DS_CACHE_POLICY` | 缓存策略定义 |
| `DS_SQL_TEXT` | 联邦 SQL 原文与版本定义 |
| `DS_SQL_PLAN` | 联邦 SQL 逻辑计划与物理计划存储 |
| `DS_SQL_VALIDATE_LOG` | 联邦 SQL 校验结果记录 |
| `DS_SOURCE_CAPABILITY` | 数据源能力定义 |
| `DS_DIALECT_RULE` | 数据库方言规则定义 |
| `DS_AUDIT_LOG` | 关键操作审计日志 |

### 6.2 表关系

- `DS_CONNECTION` 1:N `DS_CATALOG`
- `DS` 1:N `DS_SOURCE`
- `DS` 1:N `DS_PARAM`
- `DS` 1:N `DS_FIELD`
- `DS` 1:1 `DS_CACHE_POLICY`
- `DS` 1:N `DS_SQL_TEXT`
- `DS` 1:N `DS_SQL_PLAN`
- `DS` 1:N `DS_SQL_VALIDATE_LOG`
- `DS` 1:N `DS_AUDIT_LOG`
- `DS_CONNECTION` 1:N `DS_SOURCE_CAPABILITY`
- `DS_CONNECTION` 1:N `DS_DIALECT_RULE`

### 6.3 关键索引

- `DS_CONNECTION(connection_code)` 唯一索引
- `DS_CATALOG(connection_id, catalog_code)` 唯一索引
- `DS(service_code)` 唯一索引
- `DS_SOURCE(service_id, source_alias)` 唯一索引
- `DS_PARAM(service_id, param_name)` 唯一索引
- `DS_FIELD(service_id, field_name)` 唯一索引
- `DS_SQL_TEXT(service_id, version)` 索引
- `DS_SQL_PLAN(service_id, version)` 索引
- `DS_SQL_VALIDATE_LOG(service_id, created_at)` 索引
- `DS_AUDIT_LOG(service_id, created_at, id)` 索引

- `DS_AUDIT_LOG(event_type, created_at, id)` 索引
- `DS_AUDIT_LOG(operation_result, created_at, id)` 索引

### 6.4 第二阶段新增字段与表设计

#### 6.4.1 `DS` 新增字段

为支持第二阶段联邦 SQL 平台能力，`DS` 建议增加以下字段：

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `sql_type` | VARCHAR(32) | SQL 类型，`SIMPLE_SQL` / `FEDERATED_SQL` |
| `execution_mode` | VARCHAR(32) | 执行模式，`REMOTE_ONLY` / `REMOTE_PLUS_LOCAL` |
| `plan_status` | VARCHAR(32) | 计划状态，`UNPLANNED` / `VALIDATED` / `PLANNED` / `PUBLISHED` |
| `current_sql_version` | INT | 当前已发布联邦 SQL 版本号 |
| `max_batch_size` | INT | 服务级批量查询上限，未配置时走系统默认值 |
| `max_result_rows` | INT | 服务级结果集上限，未配置时走系统默认值 |
| `query_timeout_seconds` | INT | 服务级单次查询超时阈值 |
| `federated_query_timeout_seconds` | INT | 服务级联邦查询超时阈值 |

设计规则：

- 第一阶段普通服务默认 `sql_type=SIMPLE_SQL`
- 第二阶段联邦服务必须设置 `sql_type=FEDERATED_SQL`
- 若存在本地补算节点，则 `execution_mode=REMOTE_PLUS_LOCAL`
- 服务发布成功后，`plan_status` 必须同步进入 `PUBLISHED`
- 服务级批量上限、结果集上限和超时配置可覆盖系统默认值
- 查询执行只允许读取已发布版本，不得直接读取草稿配置内容

用途：

- 保存联邦 SQL 原文、版本、草稿态和发布态信息

建议字段：

| --- | --- | --- |
| `id` | BIGINT | 主键 |

| `created_at` | TIMESTAMP | 创建时间 |
| `updated_by` | VARCHAR(64) | 更新人 |
| `updated_at` | TIMESTAMP | 更新时间 |

约束建议：

- 唯一索引：`(service_id, version)`
- 唯一约束：同一 `service_id` 仅允许一条 `is_current=true`

设计规则：

- 联邦 SQL 变更必须新增版本，不覆盖历史文本

用途：

- 保存平台关键操作的审计日志，用于问题追踪、责任定位、发布追溯和安全审查

建议字段：

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `service_id` | BIGINT | 关联 `DS.id`，无关联服务时可为空 |
| `connection_id` | BIGINT | 关联 `DS_CONNECTION.id`，无关联连接时可为空 |
| `event_type` | VARCHAR(64) | 事件类型，如 `CREATE_SERVICE`、`UPDATE_SERVICE`、`PUBLISH_SERVICE`、`DISABLE_SERVICE`、`TEST_CONNECTION`、`VALIDATE_FEDERATED_SQL` |
| `target_type` | VARCHAR(32) | 目标对象类型，如 `SERVICE`、`CONNECTION`、`FEDERATED_SQL`、`CACHE_POLICY` |
| `target_id` | VARCHAR(64) | 目标对象标识，可存服务编码、连接编码或版本标识 |
| `operator` | VARCHAR(64) | 操作人或系统标识 |
| `operator_role` | VARCHAR(32) | 操作角色，如 `ADMIN`、`DEVELOPER`、`SYSTEM` |
| `operation_result` | VARCHAR(16) | 操作结果，`SUCCESS` / `FAIL` |
| `trace_id` | VARCHAR(64) | 跟踪标识 |
| `request_ip` | VARCHAR(64) | 请求来源地址 |
| `change_summary` | VARCHAR(1024) | 变更摘要或操作摘要 |
| `detail_json` | TEXT | 结构化明细，保存变更前后摘要、版本信息、校验结果摘要等 |
| `created_at` | TIMESTAMP | 创建时间 |
| `created_by` | VARCHAR(64) | 创建人或系统标识 |

推荐事件类型：

- `CREATE_CONNECTION`
- `UPDATE_CONNECTION`
- `ENABLE_CONNECTION`
- `DISABLE_CONNECTION`
- `TEST_CONNECTION`
- `CREATE_SERVICE`
- `UPDATE_SERVICE`
- `PUBLISH_SERVICE`
- `DISABLE_SERVICE`
- `VALIDATE_FEDERATED_SQL`
- `PLAN_FEDERATED_SQL`
- `PREVIEW_EXECUTION`
- `CHANGE_PERMISSION`

约束建议：

- 索引：`(service_id, created_at, id)`
- 索引：`(connection_id, created_at, id)`
- 索引：`(operator, created_at, id)`
- 索引：`(event_type, created_at, id)`
- 索引：`(operation_result, created_at, id)`
- 索引：`(trace_id)`

检索与分页索引建议：

- 审计列表默认应按 `created_at desc, id desc` 倒序分页，避免同一时间戳下分页结果抖动
- 若数据库支持倒序索引，可优先设计 `(created_at desc, id desc)` 作为默认分页索引
- 高频组合检索应优先设计并命中以下索引路径：`(service_id, created_at desc, id desc)`、`(connection_id, created_at desc, id desc)`、`(operator, created_at desc, id desc)`、`(event_type, created_at desc, id desc)`、`(operation_result, created_at desc, id desc)`
- 当查询条件同时包含“服务 + 时间范围”“操作人 + 时间范围”“事件类型 + 时间范围”“结果状态 + 时间范围”时，应优先走对应组合索引，避免仅按时间全表扫描
- 列表检索应优先返回摘要字段，避免在分页列表中读取大字段 `detail_json`；详情查询再按主键读取完整记录
- 审计归档、分区或冷热分层策略不应改变保留期内数据的检索条件与分页语义

设计规则：

- 审计日志必须覆盖配置变更、发布、停用、连接测试、联邦 SQL 校验、预览执行和权限变更等关键操作
- 审计日志必须支持按服务、连接、操作人、事件类型、时间范围检索
- `detail_json` 应采用结构化格式，避免仅保存纯文本描述
- 涉及敏感信息时，`change_summary` 与 `detail_json` 只允许保存脱敏后的摘要，不允许记录明文凭据
- 审计日志应与业务查询日志分离保存，避免相互覆盖或语义混淆
- 建议增加按保留周期分区或归档清理策略，避免长期累积导致检索性能下降
- 列表分页查询应优先走时间倒序与筛选字段组合索引，详情查询走主键或唯一标识查询

#### 6.4.8 `DS_AUDIT_LOG.detail_json` 结构建议

用途：

- 统一约束审计明细字段结构，便于检索、审计展示、问题追踪和后续归档

建议结构：

```json
{
  "before": {
    "summary": "变更前摘要",
    "maskedFields": ["password", "secretKey"]
  },
  "after": {
    "summary": "变更后摘要",
    "maskedFields": ["password", "secretKey"]
  },
  "versionInfo": {
    "serviceVersion": 3,
    "sqlVersion": 5
  },
  "validation": {
    "stage": "CAPABILITY",
    "result": "PASS",
    "message": "all checks passed"
  },
  "planSummary": {
    "pushdownNodes": 4,
    "fallbackNodes": 1
  },
  "execution": {
    "durationMs": 128,
    "cacheHit": false,
    "resultRows": 120
  },
  "permissionChange": {
    "role": "DEVELOPER",
    "action": "GRANT_PUBLISH"
  },
  "extensions": {}
}
```

字段说明：

- `before`：变更前摘要，仅保存脱敏后的关键摘要
- `after`：变更后摘要，仅保存脱敏后的关键摘要
- `versionInfo`：服务版本、联邦 SQL 版本等追溯信息
- `validation`：校验阶段、结果与摘要
- `planSummary`：计划与下推摘要
- `execution`：执行耗时、缓存命中、结果规模等运行摘要
- `permissionChange`：权限变更场景的角色与动作摘要
- `extensions`：保留扩展字段，支持后续兼容演进

设计规则：

- `detail_json` 必须优先保存结构化摘要，不直接堆叠长文本
- `before` 与 `after` 不允许记录明文密码、令牌、连接串密钥等敏感值
- 不同 `event_type` 可按需裁剪字段，但顶层结构命名应保持一致
- 前端审计详情展示应优先基于 `detail_json` 结构化渲染，而不是依赖字符串解析

## 7. 后端实现设计

### 7.1 分层与目录职责

- `controller`
  - 管理 HTTP 接口
  - 查询 HTTP 接口
- `service`
  - 应用服务编排
  - 发布校验
  - 查询执行
  - 联邦 SQL 规划与优化编排
  - 联邦执行编排
- `repository`
  - `DS_*` 元数据表访问
  - 注解式 MyBatis SQL
- `domain`
  - 领域对象
  - 枚举
  - 校验器
- `infrastructure`
  - 数据源连接管理
  - 动态 SQL 执行
  - 联邦 SQL Planner
  - 联邦 SQL Optimizer
  - 数据源能力注册表
  - 方言适配器
  - 子计划拆分器
  - 本地结果整合器
  - 本地缓存
  - 日志与审计

### 7.2 连接管理设计

核心组件：

- `DatasourceConnectionManager`
- `JdbcExecutorFactory`
- `DynamicQueryExecutor`

处理逻辑：

1. 根据 `connectionCode` 读取连接配置
2. 根据 `dbType` 选择对应驱动
3. 初始化或复用连接池
4. 根据 `catalog` 切换目标库上下文
5. 执行查询

### 7.3 服务加载设计

处理逻辑：

1. 根据 `serviceCode` 查询最新 `PUBLISHED` 版本
2. 加载 `DS`
3. 加载关联 `DS_SOURCE`
4. 加载关联 `DS_PARAM`
5. 加载关联 `DS_FIELD`
6. 按需加载 `DS_CACHE_POLICY`
7. 按需加载联邦 SQL 计划与校验信息
8. 组装运行时服务对象

### 7.4 参数校验设计

校验内容：

- 服务是否存在
- 服务是否已发布
- 必填参数是否齐全
- 参数类型是否正确
- 批量条数是否超限

失败结果：

- 返回 `PARAM_INVALID` 或 `SERVICE_NOT_FOUND`、`SERVICE_DISABLED`

### 7.5 第一阶段动态 SQL 执行设计

执行原则：

- SQL 模板从 `DS.sqlTemplate` 读取
- 参数名从 `DS_PARAM.sqlPlaceholder` 读取
- 所有请求参数转为绑定参数 Map
- 执行器统一返回 `List<Map<String, Object>>`
- 同一个数据服务的 SQL 由配置维护，可在不改代码的前提下调整

执行步骤：

1. 解析服务 SQL 模板
2. 构建命名参数映射
3. 执行参数一致性检查
4. 调用对应数据库执行器查询
5. 返回原始结果集

### 7.6 第二阶段联邦 SQL 执行设计

执行目标：

- 支持一个服务直接维护一条联邦 SQL
- 支持自动优化和多源统一执行

核心组件：

- `FederatedSqlParser`
- `FederatedSqlValidator`
- `FederatedSqlPlanner`
- `FederatedSqlOptimizer`
- `DatasourceCapabilityRegistry`
- `PlanSplitter`
- `FederatedPlanExecutor`
- `RemoteQueryExecutor`
- `LocalResultAssembler`
- `DialectAdapterRegistry`

执行步骤：

1. 读取服务定义中的联邦 SQL
2. 基于 Apache Calcite 解析 SQL 并生成抽象语法树
3. 基于 Apache Calcite 校验语法、来源、字段、函数和统一 SQL 语义
4. 装载数据源能力、基础统计信息和历史执行摘要
5. 基于 Apache Calcite 生成逻辑计划
6. 执行 Join Reorder、Join 策略选择、Filter Pushdown、Project Pushdown、Partial Aggregation Pushdown
7. 生成阶段 DAG、物理执行计划、下推决策和回退原因
8. 由平台执行层按数据源拆分子查询
9. 对可并发阶段执行受控并发调度
10. 通过 JDBC 执行数据库侧下推查询，并在适合场景下执行异步 lookup / 批量 lookup
11. 在运行期传播动态过滤条件，减少后续无效扫描
12. 对未下推部分在服务端完成整合，必要时对中间结果落盘
13. 输出统一结果和阶段执行摘要

处理规则：

- 优化器以降低跨源数据搬运和减少无效扫描为目标
- 优先选择“单源闭包执行 + 小结果集汇合”的策略，避免过早拉取大明细结果
- 小表维度关联优先评估 lookup join 与 lookup cache，而不是默认全量 Join
- 跨源读取若配置统一查询时间点，则各子查询必须尽量使用一致的快照或时间点参数
- 数据源能力不足时必须允许部分下推、部分回退
- 联邦 SQL 执行前必须具备可视化校验或诊断结果
- 若计划估算结果显示本地补算数据量超过单机阈值，应在执行前给出告警、限制执行或要求更严格的过滤条件
- 当前阶段不引入 Flink 等独立联邦执行运行时

### 7.7 第二阶段能力模型设计

设计原则：

- 数据源能力必须显式建模，不依赖隐式规则命中
- 能力模型既用于发布校验，也用于执行期计划拆分

能力类别：

- join 能力
  - `JOIN_INNER`
  - `JOIN_LEFT`
  - `JOIN_RIGHT`
  - `JOIN_SCOPE`
  - `JOIN_LOOKUP`
- filter 能力
  - `FILTER_COMPARISON`
  - `FILTER_IN`
  - `FILTER_LIKE`
  - `FILTER_DYNAMIC`
- project 能力
  - `PROJECT_SIMPLE`
  - `PROJECT_EXPRESSION`
- aggregate 能力
  - `AGGREGATE_COUNT`
  - `AGGREGATE_SUM`
  - `AGGREGATE_AVG`
  - `AGGREGATE_PARTIAL`
- 结果集能力
  - `ORDER_BY`
  - `LIMIT`
  - `OFFSET`
- 扩展能力
  - `WINDOW_FUNCTION`
  - `FUNCTION_DATE_TRUNC`
  - `FUNCTION_COALESCE`
  - `LOOKUP_ASYNC`
  - `LOOKUP_BATCH`
  - `LOOKUP_CACHE`
  - `READ_SNAPSHOT`
  - `READ_AS_OF_TIME`

使用规则：

- 发布前必须根据服务实际 SQL 引用能力项做完整校验
- 查询时必须根据能力项决定哪些算子远端执行、哪些本地回退
- 能力命中时必须继续判断其约束条件是否满足，如 Join 作用域、lookup 行数阈值、聚合闭包范围
- 查询运行后的阶段摘要可反向沉淀为优化建议，但不自动修改已发布规则

### 7.8 结果映射设计

映射原则：

- 以 `DS_FIELD.fieldName` 作为最终字段名
- 以 `sortOrder` 作为输出顺序
- 不暴露底层数据库表名和列名

处理步骤：

1. 获取原始结果集
2. 根据 `sourceAlias`、`sourceColumn` 查找映射规则
3. 做字段重命名
4. 做类型转换
5. 输出统一对象列表

### 7.9 缓存实现设计

缓存流程：

1. 根据 `serviceCode`、`version`、`params` 计算缓存键
2. 查询本地缓存
3. 命中则直接返回
4. 未命中则执行查询
5. 将结果写入缓存

失效机制：

- TTL 到期失效
- 服务发布新版本时缓存命名空间切换
- 服务停用时清理对应缓存

### 7.10 发布校验设计

发布前必须完成以下校验：

- `DS` 基本信息完整
- `DS_SOURCE` 至少满足服务类型最低要求
- `DS_PARAM` 与 SQL 占位符完全一致
- `DS_FIELD` 可映射查询列
- `DS_CACHE_POLICY` 在启用缓存时完整可用
- 关联的数据源连接与目标库均为 `ENABLED`
- 关联查询具备可执行的关联方案，能够在数据库侧或服务端完成结果整合
- 联邦 SQL 已通过语法校验、语义校验和执行计划生成
- 联邦 SQL 已通过数据源能力校验
- 联邦计划已生成子计划拆分结果

### 7.11 审计日志写入与检索设计

核心组件：

- `AuditLogService`
- `AuditLogRepository`
- `AuditEventFactory`
- `AuditLogQueryService`

写入流程：

1. 管理接口、发布流程、校验流程、预览执行流程产生审计事件
2. `AuditEventFactory` 统一组装 `eventType`、`targetType`、`targetId`、`operator`、`traceId`
3. 对敏感字段执行脱敏与摘要化处理
4. 组装 `change_summary` 与 `detail_json`
5. 写入 `DS_AUDIT_LOG`

检索流程：

1. 接收审计检索条件
2. 按 `serviceId`、`connectionId`、`operator`、`eventType`、`operationResult`、时间范围组装查询条件
3. 列表查询优先命中筛选字段 + `created_at desc, id desc` 组合索引，并按时间倒序分页返回摘要结果
4. 按权限控制字段可见范围，敏感摘要继续脱敏展示
5. 详情查询按主键读取完整记录，并按需返回 `detail_json`

处理规则：

- 审计写入失败不得影响主业务事务提交时序的可控性，但必须记录补偿或告警日志
- 审计事件模型必须由平台统一组装，不允许各模块自行拼装不一致字段
- 审计检索默认按时间倒序返回，并支持分页
- 审计列表查询默认不读取大字段 `detail_json`，应仅返回列表展示所需摘要字段
- 审计详情展示默认读取 `change_summary` 与 `detail_json`，避免直接拼接底层异常堆栈
- 审计检索接口只允许具备审计列表查看权限的授权角色访问

### 9.1 数据源配置流程

### 9.2 第一阶段服务配置与发布流程

1. 创建服务草稿
2. 保存 `DS`
3. 配置 `DS_SOURCE`
4. 配置 `DS_PARAM`
5. 配置 `DS_FIELD`
6. 配置 `DS_CACHE_POLICY`
7. 执行发布校验
8. 记录发布审计事件
9. 发布成功并生效新版本

### 9.3 第一阶段审计检索流程

1. 进入审计日志列表页或调用审计检索接口
2. 校验当前用户是否具备审计列表查看权限；进入详情前继续校验是否具备审计详情查看权限

5. 返回脱敏后的摘要列表
6. 进入详情页后按主键读取结构化 `detail_json`
7. 无权限访问列表或详情时返回 `ACCESS_DENIED`

### 9.4 第一阶段单次查询流程

1. 接收请求
2. 加载服务定义
3. 校验参数
4. 处理缓存
5. 执行 SQL
6. 映射结果
7. 封装统一响应

### 9.5 第一阶段批量查询流程

1. 接收 `batchParams`
2. 校验数量上限
3. 逐条执行查询
4. 汇总查询结果并保留输入输出对应关系
5. 返回统一批量结果

### 9.6 第一阶段基础跨库关联流程

1. 加载来源定义
2. 构建关联 SQL
3. 优先尝试在数据库侧执行关联
4. 无法直接关联时由服务端完成结果整合
5. 映射输出字段
6. 返回统一结构

### 9.7 第二阶段联邦 SQL 配置与发布流程

1. 创建或编辑数据服务
2. 录入联邦 SQL
3. 执行联邦 SQL 语法校验
4. 执行来源识别与语义校验
5. 执行数据源能力校验
6. 生成逻辑计划、优化计划和子计划拆分结果
7. 生成统计摘要、阶段 DAG、Join 策略与下推失败原因
8. 展示优化结果、下推摘要、本地补算摘要与阶段摘要
9. 发布前校验通过
10. 记录校验与发布审计事件
11. 生成新版本并发布

### 9.8 第二阶段联邦 SQL 查询流程

1. 接收统一查询请求
2. 加载已发布联邦 SQL 服务定义
3. 解析入参与绑定参数
4. 加载或生成执行计划
5. 装载统计摘要、能力约束与推荐执行模式
6. 对逻辑计划执行优化并选择 Join / lookup 策略
7. 按数据源能力与边界拆分子计划和阶段 DAG
8. 并发执行可并发的远端下推查询与异步 lookup
9. 在运行期传播动态过滤条件
10. 在服务端整合未下推结果，必要时执行中间结果缓冲或落盘
11. 统一字段映射
12. 写入缓存并返回响应

### 10.1.1 错误码明细建议

| 错误码 | 类别 | 含义 | 典型场景 |
| --- | --- | --- | --- |
| `PARAM_INVALID` | 参数错误 | 请求参数缺失、类型错误或校验失败 | 必填参数缺失、批量参数格式错误 |
| `SERVICE_NOT_FOUND` | 服务状态错误 | 服务不存在或编码无效 | `serviceCode` 未配置 |
| `SERVICE_DISABLED` | 服务状态错误 | 服务未发布或已停用 | 调用了草稿态或停用态服务 |
| `SERVICE_CONFIG_INVALID` | 配置错误 | 服务配置不完整或配置冲突 | 参数定义与 SQL 占位符不一致 |
| `DATASOURCE_UNAVAILABLE` | 数据源错误 | 数据源不可连接或目标库不可用 | 连接测试失败、运行时连接中断 |
| `FEDERATED_SQL_VALIDATE_FAILED` | 校验错误 | 联邦 SQL 校验未通过 | 语法、语义、能力校验失败 |
| `QUERY_EXECUTION_FAILED` | 执行错误 | 查询执行失败 | 远端 SQL 执行异常、本地补算异常 |
| `RESOURCE_LIMIT_EXCEEDED` | 资源保护错误 | 触发结果集、批量规模或内存预算限制 | 结果集超限、批量规模超限 |
| `QUERY_TIMEOUT` | 资源保护错误 | 查询执行超过时限 | 单次查询或联邦查询超时 |
| `ACCESS_DENIED` | 权限错误 | 当前角色无权访问目标接口或数据 | 非授权用户访问管理接口，或无审计列表/详情权限时访问审计接口 |
| `AUDIT_LOG_WRITE_FAILED` | 审计错误 | 审计日志写入失败 | 审计持久化异常、归档失败 |
| `AUDIT_LOG_QUERY_FAILED` | 审计错误 | 审计检索失败 | 审计查询条件异常、底层检索失败 |

- `POST /api/admin/data-services/{id}/federated-sql/plan`
- `GET /api/admin/data-services/{id}/federated-sql/capabilities`
- `POST /api/admin/data-services/{id}/publish`
- `PUT /api/admin/data-services/{id}/disable`

接口要求：

- 管理接口与查询接口分离
- 所有响应结构与需求规格及详细设计定义保持一致
- 错误码严格复用规格书定义
- 管理接口仅用于配置维护，不提供业务数据写入能力
- 管理接口必须基于角色与权限做访问控制
- 查询接口与管理接口必须采用不同的鉴权边界与审计策略
- 审计接口属于管理接口子集，但审计列表查看与审计详情查看权限必须独立控制，不得等同于普通管理权限

## 11. 异常与安全设计

### 11.1 异常处理

配置阶段异常：

- 数据源不可连接
- 目标库不存在
- 服务编码重复
- SQL 模板非法
- 联邦 SQL 语法非法
- 联邦 SQL 语义非法
- 联邦 SQL 能力校验失败
- 联邦 SQL 计划生成失败
- 联邦 SQL 子计划拆分失败
- 参数占位符不匹配
- 字段映射不完整

运行阶段异常：

- 服务不存在
- 服务未启用
- 参数不合法
- 批量超限
- 查询超时
- 数据源不可用
- 联邦 SQL 下推失败
- 联邦计划执行失败
- 本地补算超限

### 11.2 安全控制

- 连接密码仅保存密文
- 配置展示对敏感字段脱敏
- 动态 SQL 禁止字符串拼接执行
- 联邦 SQL 必须由系统统一解析与执行，不允许绕开校验链路直接执行
- 查询接口禁止非查询语句
- 管理接口与查询接口路由隔离
- 系统仅提供查询能力，不暴露数据写入能力

## 12. 性能设计

- 连接池按数据源复用
- 高频服务启用本地缓存
- 单批次查询上限必须可配置，默认建议值为 100
- 单次查询结果上限必须可配置，默认建议值不超过 10000 行
- 单次查询超时阈值与联邦查询超时阈值必须可配置，默认建议值分别不超过 30 秒和 60 秒
- `serviceCode`、`connectionCode`、外键字段必须建立索引
- 查询超时支持连接级和服务级配置
- 批量查询的整体开销应低于等量单条重复调用
- 联邦 SQL 执行优先减少跨源数据搬运
- Join Reorder、Filter Pushdown、Project Pushdown 必须作为联邦执行主优化手段
- 统计信息、代价估算、动态过滤和 Join 策略选择应作为第二阶段重点优化点
- 小表维度关联优先复用 lookup cache 和批量 lookup，减少全量远端扫描
- 远端执行并发度必须可按数据源限流，避免把执行优化变成数据源压测
- 中间结果应支持流式传递与必要时落盘，避免单次查询占满堆内存
- 计划缓存可作为第二阶段优化点
- 联邦查询诊断信息必须可观测、可回溯
- 本地补算必须具备内存上限与结果集上限保护
- 系统性能设计必须以单机 4 核 CPU、16G 内存为基础约束进行容量规划
- 默认线程池、远端执行并发度、本地补算并发度、lookup 并发度都必须设置上限，且上限默认值应适配单机资源
- 对可能产生大中间结果的执行链路，必须优先使用流式处理和落盘缓冲，避免一次性全量载入内存
- 当达到内存预算、结果集预算或执行超时阈值时，系统应快速失败并返回明确错误码，而不是继续扩张资源占用
