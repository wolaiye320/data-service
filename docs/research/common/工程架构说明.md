## 2. 设计依据与约束

### 2.1 需求依据

工程脚手架必须完整承接以下需求约束：

- 系统仅提供查询能力，不提供写入能力
- 系统必须对外提供统一查询 API
- 系统必须支持 Oracle、MySQL、PostgreSQL 等异构数据库接入
- 系统必须支持连接配置、SQL 配置、服务配置、缓存、发布、权限、审计和前端管理界面
- 第一阶段先建设基础数据服务能力，第二阶段在第一阶段基础上建设联邦 SQL 平台能力
- 第一阶段验收完成后方可进入第二阶段
- 系统必须支持单机独立部署运行，默认资源基线为 4 核 CPU、16G 内存
- 查询执行必须满足只读约束、参数化执行、安全校验和资源保护要求

### 2.2 设计依据

工程脚手架必须与详细设计中的以下内容保持一致：

- 分阶段实施架构
- 模块详细设计中的职责边界
- 元数据模型与表结构
- 后端分层与目录职责
- 联邦 SQL 规划、优化、方言适配、执行编排的模块分工
- 审计、日志、缓存、权限与资源保护处理规则

### 2.3 项目规则约束

工程脚手架在落地时必须遵循以下项目规则：

- Java 包名前缀统一使用 `cn.dtkeys`
- Flyway 迁移文件位置统一为 `src/main/resources/db/migration/`
- Flyway 文件命名遵循 `V{N}__{description}.sql`
- MyBatis Repository 必须使用注解方式定义 SQL，不使用 XML Mapper
- 新增工程方案应优先补充现有架构文档，不新建零散研究文档
- 前后端结构应遵循关注点分离、模块化和可测试性原则

## 3. 工程总体形态

### 3.1 总体形态

系统建议采用前后端分离、后端多模块、前端独立管理端的工程形态。

建议形态如下：

- 后端：单仓多模块工程
- 前端：独立管理端工程
- 元数据库：与后端应用协同演进的持久化存储
- 外部业务数据库：由后端按配置接入并执行查询

### 3.2 采用该形态的原因

- 第一阶段可快速落地连接管理、服务配置、统一查询、缓存和前端配置能力
- 第二阶段可在现有骨架上扩展联邦 SQL、能力模型、方言适配、执行编排和诊断能力
- 避免第一阶段与第二阶段采用两套完全不同的工程结构，降低推翻式重构风险
- 有利于把公共能力、业务能力、联邦能力和部署装配能力隔离管理

### 3.3 系统边界

#### 系统输入

- 管理端配置请求
- 业务侧统一查询请求
- 系统元数据配置
- 外部业务数据库连接信息

#### 系统输出

- 统一数据查询响应
- 配置管理结果
- 发布结果与校验结果
- 审计日志、调用日志、诊断日志

#### 外部依赖

- Oracle、MySQL、PostgreSQL 等业务数据库
- 系统元数据库
- 前端管理端应用

### 3.4 项目环境与命名约定

以下内容属于当前项目实例的环境约定，供开发、联调、测试和自动化任务统一使用。

#### 项目命名基线

- 当前项目正式名称：`data-service`
- Java 包名前缀：`cn.dtkeys.dataservice`
- 前端工程目录名：`data-service-web`
- 若历史文档、规则、脚本中仍存在 `linkinsight` 相关表述，应以当前项目命名为准进行修正，不再继续沿用旧项目名

#### 服务端口

- 后端默认端口：`8081`
- 前端默认端口：`3001`

#### 环境拓扑与命名映射

- 系统元数据库对应的 MCP：`data_service`
- 业务数据库对应 MCP `bankdb` 下的 `public` schema
- 业务数据库 `bankdb` 转换成的数据集市：`datamart`

#### 默认作用域

- 未明确指定时，业务库查询默认作用域为 `bankdb.public`
- 未明确指定时，系统元数据操作默认走 `data_service`
- 涉及数据集市的任务默认目标为 `datamart`

## 4. 总体分层

### 4.1 接入层

职责：

- 提供管理接口与统一查询接口
- 负责请求接入、参数校验、统一响应封装、错误码映射
- 承担与前端管理端、业务调用方的协议对接

### 4.2 应用层

职责：

- 编排服务发布、查询执行、缓存处理、预览验证和联邦执行流程
- 协调领域服务与基础设施能力
- 负责用例级流程调度，不承载底层持久化与 SQL 执行细节

### 4.3 领域层

职责：

- 承载数据源、逻辑服务、参数、字段、缓存策略、版本、权限边界等核心模型
- 承载规则校验、状态流转和发布约束
- 对外表达“系统规则”，不直接依赖控制器和数据库实现细节

### 4.4 基础设施层

职责：

- 持久化系统元数据
- 管理数据库连接池和目标库访问
- 执行动态 SQL 和联邦子计划
- 提供缓存、日志、审计、诊断、方言适配和资源保护实现

### 4.5 分层依赖原则

- 接入层依赖应用层，不直接依赖 Repository
- 应用层依赖领域层，并组合基础设施能力完成流程编排
- 领域层不感知 Web 框架和具体持久化细节
- 基础设施层为应用层和领域层提供实现支撑
- 联邦 SQL 相关规划、优化、方言适配、执行编排不得散落在管理接口层或普通 CRUD 服务中

## 5. 后端工程脚手架

### 5.1 后端顶层模块建议

建议后端采用以下模块划分：

| 模块名 | 主要职责 |
| --- | --- |
| `data-service-app` | 启动入口、Spring Boot 装配、模块聚合、运行配置 |
| `data-service-interfaces` | Controller、DTO、统一响应、错误码、接口协议对象 |
| `data-service-application` | 应用服务、查询编排、发布编排、校验编排 |
| `data-service-domain` | 领域模型、规则、状态流转、领域服务、校验器 |
| `data-service-infrastructure` | Repository、数据源连接、动态 SQL 执行、缓存、日志、审计 |
| `data-service-federation` | 第二阶段联邦 SQL 解析、优化、方言适配、执行编排、诊断 |
| `data-service-common` | 通用异常、上下文、常量、枚举、工具、公共模型 |

### 5.2 模块职责说明

#### `data-service-app`

负责：

- Spring Boot 启动类
- 模块装配与 Bean 组合
- 环境配置加载
- 基础中间件启用

不负责：

- 业务规则实现
- Repository 细节实现
- SQL 执行细节

#### `data-service-interfaces`

负责：

- 管理接口和统一查询接口
- 请求 / 响应 DTO
- 统一响应模型和错误码映射
- 接口层参数基础校验

建议承载的接口域：

- 数据源连接管理接口
- 目标库管理接口
- 数据服务配置接口
- 参数 / 字段 / 缓存策略接口
- 服务发布 / 停用接口
- 统一查询接口
- 联邦 SQL 校验 / 预览 / 计划查看接口
- 审计和诊断查看接口

#### `data-service-application`

负责：

- 服务加载与运行时对象组装
- 发布编排与发布前校验
- 统一查询执行编排
- 批量查询编排
- 基础跨库查询编排
- 第二阶段联邦查询编排
- 缓存命中与回写流程编排

#### `data-service-domain`

负责：

- `DS_CONNECTION`、`DS_SERVICE`、`DS_SOURCE`、`DS_PARAM`、`DS_FIELD` 等领域对象抽象
- 服务状态流转规则
- 发布约束、只读约束、参数规则、字段规则
- 第一阶段与第二阶段能力边界相关规则

#### `data-service-infrastructure`

负责：

- 注解式 MyBatis Repository
- 数据源连接池管理
- 目标库切换
- 动态 SQL 执行
- 本地缓存实现
- 日志、审计、诊断信息落库
- 基础资源保护实现

#### `data-service-federation`

负责：

- 联邦 SQL Parser / Validator
- 联邦 SQL Planner / Optimizer
- 数据源能力注册
- SQL 方言适配
- 子计划拆分与阶段 DAG 生成
- 远端执行调度与本地补算
- 下推摘要、回退原因、阶段摘要生成

说明：

- 第一阶段可预留该模块或以子包方式预留扩展位
- 第二阶段优先将联邦能力集中在该模块，避免污染第一阶段简单查询链路

#### `data-service-common`

负责：

- 通用异常定义
- 错误码枚举
- Trace / 上下文模型
- 通用工具
- 可复用常量与公共基础对象

### 5.3 模块依赖关系

建议依赖方向如下：

- `data-service-app -> interfaces / application / infrastructure / federation / common`
- `data-service-interfaces -> application / common`
- `data-service-application -> domain / infrastructure / federation / common`
- `data-service-domain -> common`
- `data-service-infrastructure -> domain / common`
- `data-service-federation -> domain / infrastructure / common`

约束：

- `interfaces` 不直接调用 `repository`
- `domain` 不依赖 `interfaces`
- `federation` 相关能力不下沉到普通配置管理模块中临时实现
- 禁止形成循环依赖
- 若需要跨模块复用能力，优先抽象到合理共享的位置，而不是复制实现

### 5.4 分阶段最小落地组合

#### 第一阶段建议最小模块组合

- `data-service-app`
- `data-service-interfaces`
- `data-service-application`
- `data-service-domain`
- `data-service-infrastructure`
- `data-service-common`

第一阶段重点落地：

- 数据源连接管理
- 服务配置与发布
- 统一查询 API
- 批量查询
- 基础跨库关联
- 本地缓存
- 前端配置界面对接
- 权限、审计、日志、基础资源保护

#### 第二阶段扩展模块组合

在第一阶段基础上扩展：

- `data-service-federation`
- 必要时增强 `application`、`domain`、`infrastructure` 中与联邦相关的扩展点

第二阶段重点落地：

- 联邦 SQL 校验
- 联邦 SQL 规划与优化
- 方言适配
- 联邦执行编排
- 计划展示与诊断
- 联邦平台化前端能力

建议基础包前缀统一为：

以后端模块为例，建议采用以下包结构：

### 6.3 分层约束

- Controller 只处理协议层转换、参数接收和响应输出
- Application Service 负责用例编排，不直接承载底层 JDBC 与 SQL 拼装细节
- Domain 负责规则和状态，不直接依赖 Web 或数据库框架
- Repository 只负责元数据持久化，不承担业务编排
- Federation 包负责联邦专属能力，避免将第二阶段复杂逻辑散落到普通 Query Service

## 7. 前端工程脚手架

### 7.1 前端工程定位

前端建议采用独立管理端工程，负责承载系统配置、发布、审计、联邦 SQL 管理和诊断展示能力。

### 7.2 前端目录建议

建议目录如下：

- `src/pages`：页面入口
- `src/modules`：按业务域组织页面与局部组件
- `src/services`：API 请求封装
- `src/components`：通用组件
- `src/types`：DTO、枚举、页面模型
- `src/router`：路由定义
- `src/utils`：工具函数
- `src/store`：全局状态（如需要）

### 7.3 前端业务域划分

#### 第一阶段页面域

- 数据源连接管理
- 目标库管理
- 数据服务管理
- 参数配置
- 返回字段配置
- 缓存策略配置
- 发布与停用管理
- 审计日志查询

#### 第二阶段扩展页面域

- 联邦 SQL 编辑
- 联邦 SQL 校验结果展示
- 联邦查询计划展示
- 执行摘要与回退原因展示
- 联邦审计与诊断增强页

### 7.4 前后端对齐原则

- 前端 API 调用必须按后端统一响应结构适配
- DTO、枚举、错误码、状态流转命名与后端保持一致
- 第一阶段先打通配置与发布主流程，第二阶段在现有页面骨架上扩展联邦能力
- 新增用户可见业务功能时，若前端未同步建设，应视为待确认事项，而不是默认已完整交付

### 7.5 API 资源命名原则

- 新增接口路径应体现业务域边界，并与对应页面、模块、测试名称尽量保持一致
- 资源路径优先使用名词表达资源对象，动作语义优先通过 HTTP 方法表达，避免在路径中滥用动词
- 同一业务概念在 API、页面、文档、测试中的命名应保持一致，避免一处多名

## 8. 配置、存储与基础设施挂载方式

### 8.1 元数据存储

系统元数据库负责存储以下核心表：

- `DS_CONNECTION`
- `DS_CATALOG`
- `DS_SERVICE`
- `DS_SOURCE`
- `DS_PARAM`
- `DS_FIELD`
- `DS_CACHE_POLICY`
- `DS_SQL_TEXT`
- `DS_SQL_PLAN`
- `DS_SQL_VALIDATE_LOG`
- `DS_SOURCE_CAPABILITY`
- `DS_DIALECT_RULE`
- `DS_AUDIT_LOG`

### 8.2 Flyway 迁移挂载

Flyway 迁移文件统一放置于：

- `src/main/resources/db/migration/`

要求：

- 每次 Schema 变更新增迁移文件，不修改已提交迁移
- 元数据表、审计表、联邦扩展表均通过 Flyway 维护
- 新增迁移需配套集成测试验证字段映射

### 8.3 Repository 规范

- 元数据访问统一放在 `repository` 包
- 使用 MyBatis 注解方式定义 SQL
- 不使用 XML Mapper 文件
- 复杂 SQL 建议使用 Java Text Blocks 提升可读性

### 8.4 数据源与执行器挂载

建议将以下能力归属 `infrastructure`：

- `DatasourceConnectionManager`
- `JdbcExecutorFactory`
- `DynamicQueryExecutor`
- `RemoteQueryExecutor`
- `LocalResultAssembler`

### 8.5 缓存挂载

- 第一阶段默认采用本地缓存
- 缓存能力挂载在 `infrastructure.cache`
- 缓存键应承接服务标识、版本和参数哈希
- 缓存策略配置来源于元数据配置，而不是写死在代码中

### 8.6 审计、日志与诊断挂载

- 配置变更、发布、停用、测试连接、预览执行、权限变更等事件写入 `DS_AUDIT_LOG`
- 查询调用日志、异常日志和审计日志应分离存储
- 第二阶段联邦计划、下推摘要、回退原因和阶段摘要由联邦模块生成并落库

### 8.7 环境配置分层

建议至少区分：

- `local`
- `test`
- `prod`

配置分层中应包含：

- 元数据库连接配置
- 动态数据源访问默认参数
- 查询超时、批量上限、结果集上限
- 本地缓存参数
- 联邦执行资源预算和并发控制参数

### 8.8 安全与只读约束挂载

## 10. 部署脚手架与运行形态

### 10.1 部署单元

- 前端管理应用
- 后端服务应用
- 系统元数据库
- 外部业务数据库

### 10.2 部署关系

- 前端管理应用调用后端管理接口和诊断接口
- 业务调用方调用后端统一查询接口
- 后端服务访问系统元数据库读取服务配置与校验结果
- 后端服务访问外部业务数据库执行查询或联邦子计划
- 后端服务在本地维护缓存、日志和诊断摘要

### 10.3 单机基线要求

默认部署基线：

- 4 核 CPU
- 16G 内存

工程脚手架必须从一开始就预留以下控制点：

- 单次查询超时阈值
- 批量查询规模上限
- 结果集上限
- 联邦执行本地补算内存预算
- 中间结果缓冲与落盘阈值
- 远端执行并发上限

### 10.4 发布与回滚挂载点

工程应预留以下发布能力挂载点：

- 启动前元数据迁移执行
- 发布前服务校验
- 发布后回归检查清单
- 发布记录与审计留痕
- 回滚预案与回退验证

### 10.5 部署演进原则

- 前后端可以按阶段演进为分离部署，但应保持既有接口契约和模块边界稳定
- 后端可在保持模块职责与依赖方向不变的前提下继续拆分部署单元
- 若后续引入缓存、消息、检索或其他新型基础设施，应先同步更新技术选型说明书和本工程架构说明

## 11. 分阶段演进策略

### 11.1 第一阶段最小骨架策略

第一阶段以“配置驱动查询系统”为目标，优先落地：

- 基础后端工程骨架
- 元数据迁移体系
- 数据源连接管理
- 服务配置与发布能力
- 统一查询 API
- 批量查询与基础跨库能力
- 本地缓存
- 前端配置主流程
- 权限、审计、日志和基础资源保护

第一阶段不要求：

- 通用联邦 SQL 自助编辑平台
- 完整联邦 SQL 优化器
- 完整方言兼容与执行计划诊断体系

### 11.2 第二阶段扩展策略

第二阶段在不推翻第一阶段结构的前提下扩展：

- 联邦 SQL 元数据
- 联邦 SQL 校验与发布前检查
- 逻辑计划与优化计划
- 数据源能力模型与方言适配
- 联邦执行编排与动态过滤 / lookup 优化
- 联邦计划展示、诊断与审计增强
- 平台级自助配置能力

### 11.3 第一阶段预留扩展点

建议第一阶段即预留以下扩展点：

- 服务类型区分普通 SQL 与联邦 SQL
- 发布校验链路具备可扩展编排入口
- 查询执行编排与联邦执行编排分层隔离
- 诊断与审计结构具备扩展字段
- 前端页面结构为第二阶段联邦页签 / 页面预留入口

### 11.4 禁止的演进方式

- 不允许第一阶段与第二阶段采用两套完全不同的领域模型
- 不允许将联邦能力临时散落在第一阶段简单查询实现中，后续再整体搬迁
- 不允许以推翻现有接口协议、元数据结构和发布体系为代价推进第二阶段

### 12.10 模块间依赖关系图（示意）

```text
                +-------------------+
                |  data-service-app |
                +---------+---------+
                          |
          +---------------+---------------+
          |                               |
          v                               v
+-------------------------+     +----------------------+
| data-service-interfaces | --> | data-service-common  |
+------------+------------+     +----------------------+
             |
             v
+-------------------------+
| data-service-application|
+------+-----------+------+
       |           |       \
       v           v        v
+-------------+ +-------------------------+ +-----------------------+
| domain      | | data-service-infrastructure | | data-service-federation |
+------+------+ +-------------+-----------+ +-----------+-----------+
       |                      |                         |
       +----------------------+-------------------------+
```

依赖解读：

- `app` 负责启动与装配，聚合其他模块
- `interfaces` 只通过 `application` 暴露业务能力，不直接访问 `repository`
- `application` 是编排中心，连接 `domain`、`infrastructure` 和第二阶段 `federation`
- `domain` 负责规则和模型，避免反向依赖上层
- `infrastructure` 提供持久化、执行器、缓存、审计、日志等实现支撑
- `federation` 在第二阶段承载联邦 SQL 专属能力，并通过 `application` 接入主流程

- 《数据服务架构与详细设计》定义模块职责、数据模型、处理规则、接口设计和关键实现约束

三者关系应保持如下顺序：

- 先以需求规格书确认边界
- 再以工程架构说明确定工程脚手架
- 最后以架构与详细设计细化模块实现与代码落地方式
