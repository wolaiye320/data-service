# Learned Rules

该文件用于沉淀用户在协作过程中新增的、可稳定复用的项目规则。

## 写入规则

- 只记录明确、稳定、可重复适用的规则
- 记录项目内长期有效的约束，不记录一次性例外
- 新规则应尽量简洁、可执行、可验证

## 当前内容

- 本项目当前正式名称为 `data-service`，不再是 `linkinsight`。
- 生成、修改或引用项目相关名称时，必须以当前仓库中的实际命名为准，例如 `data-service`、`data-service-web`、`cn.dtkeys.dataservice`。
- 若发现历史文档、规则、脚本或示例中残留 `linkinsight` 命名，应优先修正为当前项目命名，或改写为与项目名解耦的通用表述。
- 当用户要求把其他项目文档中的通用原则补入“本项目对应文档”时，若本项目不存在对应文档，应优先新建对应文档，而不是把该主题挤入其他文档。
- 当用户已明确主线方向后，若后续任务可连续推进，则应直接继续实现，不为常规下一步停下来询问；只有遇到需要用户决策、审核、授权或存在高风险分支时才暂停确认。
- `data-service-web` 本地 Playwright E2E 必须统一通过 `pnpm test:e2e:local` 执行；按文件或按用例过滤时使用 `pnpm test:e2e:local -- ...` 透传参数
- 禁止把 `TOKEN=$(curl ...)`、`bash -lc '... npx playwright test ...'`、临时登录拼接脚本等动态 shell 组合作为标准 E2E 执行入口
- 菜单页、看板页等首屏聚合页面的 E2E，不能只断言页面元素可见；必须同时断言关键首屏 API 返回成功
- 前端不得通过静默 `catch`、默认假数据、降级常量等方式掩盖核心接口失败；若产品明确允许降级，也必须有显式错误态和单独测试说明
- 新增或修改 MyBatis / Repository 自定义 SQL 时，必须补真实数据库集成测试，验证字段真实存在、关联条件正确、查询可执行
- 测试报告声明“已完成 E2E”时，必须同时列出已覆盖接口、未覆盖场景、skip/fixme 与风险项，不能只写通过结论
- 通用规范文档正文应尽量保持项目无关；项目特有路径、类名、脚本入口、组件落点等约定必须集中收口到单独章节或附录，避免散落在正文多个位置
- `docs/research/common/测试规范.md` 正文应只沉淀通用测试原则、分层要求、门禁要求与审查口径；联邦数据服务等项目特有场景展开、闭环步骤、接口名、数据库组合、环境差异样例，应放入“项目特有落地约定”或专项用例设计文档
- 表格操作列默认必须使用统一的图标按钮组件或封装，采用 `type="text"` + Tooltip + 稳定语义标识；若必须显示文字，必须先在需求或设计文档中显式声明例外原因与适用范围
- E2E 对操作列、工具栏图标按钮等控件，必须优先使用 `aria-label` 或 `data-testid` 等稳定语义定位；禁止使用会把错误 UI 固化下来的按钮可见文案作为长期选择器
- 用户明确要求删除页面、路由或功能入口时，必须彻底删除对应前端页面与路由，不得保留兼容跳转、别名路由或“先重定向再下线”的过渡实现
